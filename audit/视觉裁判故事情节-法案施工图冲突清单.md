# 视觉裁判故事情节 vs 法案/施工图冲突清单

## 1. 故事情节要点提炼

1. AI 应升级为 Visual Mission Judge，每一轮基于原图 + 坐标图一次性完成页面理解、任务判断、风险判断和动作规划。
2. 系统的新身份是解码器 + 机器臂，只解码 AI 返回的白名单动作，不再在代码里到处猜页面语义。
3. 调度真相应从 routeLabel、routePlan、selectedMap、pageReady、feedReady、URL 匹配等碎片门禁，收敛到统一的 actionCode + 受治理输入输出合同。
4. 地图应退回任务框架层，只描述目标、边界、动作手册和停止规则，不再承载细粒度分支和 prompt 选择主权。
5. 点击类动作应优先采用 grid cell 语言，由 Screenshot 提供坐标图和 gridSpecRef，由系统解码成可执行动作；AI 不应输出 raw x/y。
6. 能力登记册依然重要，但应作为白名单动作执行层，而不是被 map/proof/PAV/URL 等多重链路绑成多段微流程。
7. Forensics 需要记录每一轮的原图 ref、坐标图 ref、prompt contract、AI 输出 JSON、动作计划、执行结果与失败原因，形成完整可复盘链条。
8. 任务主循环应尽量收敛为：截图 -> AI 判断 -> 系统解码执行 -> Forensics 记录 -> 下一轮，而不是拆成多个小判断和多层中间 gate。

## 4. 已基本对齐、可作为修法基线的文件

- GrassEye Visual Mission Prompt Contract 施工图：已经明确退役 map-package / task-template / routePlan / routeLabel，主张 actions[].actionCode
- GrassEye Muscle Memory Catalog 肌肉记忆目录施工图：已经明确 AI 只能输出 actionCode，Scheduler 只执行解码后的动作
- module-code-purity.instructions.md 的 Visual Story Coherence 段落：已经把 routeLabel、selectedMapId、activationSnapshotRef 等定义为 active startup/runtime chain 的退役词汇
- GrassEye Screenshot 能力组施工图.md 的 visual mission input 部分：已经明确坐标图 + gridSpecRef + AI 只回 grid cell id 的新语言

## 5. 修复优先级建议

1. 先统一 AI / Orchestration / Startup / Screenshot / Forensics 的 routeLabel 退役口径，避免系统同时跑两套调度语言。
2. 再清理 selectedMapId、selectedMapVersion、activationSnapshotRef、map_package_readiness_check 等 retired map 真相，切断旧地图主权。
3. 最后重构 click/PAV 多段链，把 visual mission path 收敛成“grid cell -> decoder -> safety guard -> action execution -> forensics record”的短链。
