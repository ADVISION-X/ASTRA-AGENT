

# 第二步提示词：修复 + 防复发 + 真实重启 + 重新分析

````txt
你现在执行 GrassEye 调试闭环第二阶段：

Fix + Recurrence Prevention + Real Restart Verification + Fresh Log Re-Analysis

本阶段必须基于第一阶段输出：

tmp/debug-loop/root-cause-analysis/phase-1-report.md
tmp/debug-loop/root-cause-analysis/root-cause-matrix.md
tmp/debug-loop/root-cause-analysis/enforcement-gap-matrix.md

如果第一阶段报告不存在，立即停止并输出：

BLOCKED_MISSING_PHASE_1_ROOT_CAUSE_REPORT

不得跳过第一阶段直接修代码。

目标：

根据第一阶段挖掘出的 blocker，逐项完成：

1. 最小生产修复。
2. 施工图细节补齐，仅限施工图，不改法案。
3. inspector / real-code-inspection 固化。
4. 生产代码突变验证。
5. 回滚突变。
6. 运行 audit / typecheck / lint / ci。
7. 真实重启系统。
8. 真实触发一次任务。
9. 读取最新日志。
10. 对最新日志重新完整执行第一阶段分析。
11. 如果最新日志还有新 blocker，输出下一轮修复清单，不得假装 READY。

总原则：

修复一个问题，就必须让这个问题以后不能复发。

禁止：

- 禁止修改法案文件。
- 禁止扩张法案。
- 禁止新增冗余 inspector。
- 禁止一问题一 inspector。
- 禁止每个 lawId / clauseId 单独全项目扫描。
- 禁止使用 grep / regex / includes 作为核心执法逻辑。
- 禁止 warning-only P0。
- 禁止 generated fake PASS。
- 禁止用普通测试文件固化成果。
- 禁止只加单元测试不补 inspector。
- 禁止只修生产代码不补执法。
- 禁止只补 inspector 不做生产突变验证。
- 禁止无证据声称防复发。
- 禁止为了过 CI 降低校验。
- 禁止删除或弱化现有 inspector。
- 禁止豁免。
- 禁止 suppress / eslint-disable / ts-ignore / any 逃逸。
- 禁止让 debug-loop 成为第二套 runtime。
- 禁止用模拟启动替代真实重启。
- 禁止用旧日志替代最新日志。
- 禁止修完后不重新分析最新日志就宣称 READY。

第一步：读取第一阶段报告

逐个读取 BLOCKER-N。

为每个 blocker 建立修复卡：

## FIX-N

- blockerId：
- 日志证据：
- 法案要求：
- 施工图要求：
- 生产根因文件：
- 执法缺口文件：
- 为什么没拦住：
- 修复策略：
- 防复发策略：
- 生产突变验证策略：
- 修复后真实重启验证点：
- 修复后最新日志应不再出现的同类问题：

第二步：最小生产修复

对于定位到根因问题的代码文件，一律判定为垃圾文件，
对于垃圾文件，只有一种选择
物理删除后重构

为什么？
在代码纯洁度法案的管理下，单个代码文件都已经足够小，
在小文件里面做补丁、缝缝补补、这个不是修复问题，这个是制造复杂的蜘蛛网

修复的原则只有一条
100%遵守法案要求+遵守施工图要求+终端日志中反馈的根因=删除后重构成生产级代码文件

物理删除重构只适用于：
1. owner-local implementation file；
2. 非 public contract；
3. 非 generated 文件；
4. 非 registry/source-of-truth；
5. 重写后 public API 不变；
6. 有 inspector/real-code-inspection 防复发。

第三步：施工图补齐

只允许修改：

docs/法案辅助文件/**

不得修改：

.github/instructions/cursor-rules/**

施工图补齐要求：

- 只补当前问题的执行细节。
- 不新增大法案。
- 不扩大系统范围。
- 必须写清楚：
  - 正确链路。
  - 禁止链路。
  - inspector 应覆盖什么。
  - real-code-inspection 应覆盖什么。
  - 结构化日志必备字段。
  - READY 标准。
  - 修复后必须真实重启、触发任务、重新执行第一阶段日志分析。

第四步：执法脚本补齐

优先复用现有 owner inspector。

允许补：

- scripts/audit/domains/<owner>/required-shape.ts
- scripts/audit/domains/<owner>/forbidden-shape.ts
- scripts/audit/domains/<owner>/boundary-attack.ts
- scripts/audit/domains/<owner>/anti-escape.ts
- scripts/audit/domains/<owner>/owner-inspection-harness.ts
- scripts/audit/domains/_shared/**

要求：

1. AST 级：
   - 使用 ts-morph Project / SourceFile。
   - 检查 imports、call expressions、object literal fields、exported symbols、function bodies、route handlers。
   - 不得用 grep 作为核心逻辑。

2. Symbol 级：
   - 追踪关键函数是否被调用。
   - 识别 wrapper / alias / re-export。
   - 检测绕过 governed public interface 的直接调用。

3. Import graph 级：
   - 禁止 forbidden owner imports。
   - 禁止 Commander 直接 import raw Orchestration / Nerve Bus dispatcher / browser executor。
   - 禁止 map-plugin-package import provider adapter / secret resolver / orchestration runtime truth。

4. Structured JSON 级：
   - 对 map package JSON、prompt contract JSON、catalog JSON 使用 schema/canonical parser。
   - 不允许字符串搜索替代 JSON 结构解析。

5. Anti-escape：
   - 检查 any / ts-ignore / eslint-disable / dynamic import / require / suppression。
   - 检查 inspector 被删除或 manifest 解绑。
   - 检查 real-code-inspection 被清空。
   - 检查 generated fake PASS。

第五步：生产代码突变验证

这是强制条件。

每个防复发 inspector 必须做一次真实生产代码错误注入验证。

流程：

1. 在真实生产文件中临时制造最小错误。
2. 运行对应 inspector / audit 命令。
3. 必须观测到 FAIL。
4. 保存证据：

tmp/debug-loop/regression-proofs/<blockerId>/
├── regression-description.md
├── mutated-file.patch
├── inspector-fail-output.txt
├── re-inspect-proof.txt
├── inspector-pass-output.txt
└── proof-summary.md

5. 回滚故意错误。
6. 再次运行 inspector，必须 PASS。

禁止只用 test fixture。
禁止只 mock。
禁止没有 FAIL 输出就声称防复发。

第六步：运行静态命令

按 package.json 实际存在的 scripts 运行：

- npm run audit:build
- npm run audit
- npm run typecheck
- npm run lint
- npm run ci:full
- git diff --check

如果某个 script 不存在，列出实际 scripts，不得伪造。

如果 audit / ci:full 因非本 blocker owner 失败：

- 不得假装通过。
- 记录到：
  tmp/debug-loop/fix-verification/non-current-owner-ci-blockers.md
- 当前 blocker 的修复仍必须完成真实重启验证和最新日志分析。

第七步：真实重启系统

这是强制条件。

必须执行真实重启，不允许模拟。

流程：

1. 停止旧服务。
   - 如果已有 grasseye:start 进程，必须停止。
   - 确认 127.0.0.1:4173 已释放或被 startup port_clear 接管。
2. 执行：

```bash
npm run grasseye:start
````

3. 捕获完整终端输出到：

tmp/debug-loop/post-fix-runtime-verification/runtime-log.txt

4. 必须看到真实启动链：

* dependency_check
* update_preflight_check
* map_package_readiness_check
* local_ai_runtime_presence_check
* local_ai_model_roster_check
* local_ai_start_or_connect
* local_ai_health_probe
* ai_capability_readiness_gate
* port_clear
* app_server start
* APP_SHELL_HEALTH_PASSED
* open_console
* mission_runtime_available
* terminal_structured_log_relay
* waiting_for_human_command

如果启动失败：

* 不得继续任务触发。
* 直接进入“最新日志第一阶段分析”。
* 输出 POST_FIX_STARTUP_BLOCKED。
* 最新日志分析必须找出启动 blocker。

第八步：真实触发一次任务

启动成功后，必须真实触发任务。

优先顺序：

1. 如果系统有两个默认任务：

   * facebook-seeding-video-discovery
   * tiktok-seeding-video-discovery

则至少触发一个任务；如果本轮修复点涉及共同链路，如 Commander / Nerve Bus / Orchestration / runId / preflight / envelope，则两个都触发。

2. 不允许只打开页面不启动任务。
3. 不允许 mock API。
4. 不允许直接调用内部函数替代用户侧任务启动。
5. 必须通过 Commander Console / runtime API 的真实用户侧启动链路。

任务触发日志必须捕获到：

* HUMAN_COMMAND_VALIDATED
* MISSION_READINESS_CHECK_STARTED
* MISSION_PREFLIGHT_STARTED
* MISSION_PREFLIGHT_PASSED 或 FAILED
* COMMANDER_COMMAND_ENVELOPE_BUILT
* NERVE_BUS_ENVELOPE_CREATED
* NERVE_BUS_DISPATCH_STARTED
* COMMAND_ACCEPTED 或 COMMAND_REJECTED

如果修复已经进入更深阶段，还应继续捕获：

* ORCHESTRATION_START_RECEIVED
* MISSION_ACTIVATION_SNAPSHOT_FROZEN
* MAP_STEP_SELECTED
* CAPABILITY_CALL_STARTED
* CAPABILITY_CALL_COMPLETED / FAILED / REVIEW_REQUIRED
* POST_ACTION_VERIFICATION_STARTED / PASSED / FAILED / REVIEW_REQUIRED
* FORENSICS_RECORD_WRITE_REQUESTED
* FORENSICS_RECORD_WRITTEN
* STEP_TRANSITION_EVALUATED
* MISSION_FINALIZED / REVIEW_REQUIRED / FAILED

第九步：对最新日志重新完整执行第一阶段分析

这是强制条件。

修复后最新日志必须被当作全新的输入，重新完整执行第一阶段：

Runtime Log Blocker Mining & Root Cause Analysis

不得只检查“原 blocker 是否消失”。

必须重新分析所有新日志，重新输出：

tmp/debug-loop/post-fix-runtime-verification/fresh-root-cause-analysis/
├── runtime-timeline.md
├── blocker-list.md
├── law-blueprint-mapping.md
├── root-cause-matrix.md
├── enforcement-gap-matrix.md
└── phase-1-report.md

分析要求与第一阶段完全相同：

* 列出所有新 blocker。
* 每个 blocker 都要有日志证据。
* 每个 blocker 都要对照法案。
* 每个 blocker 都要对照施工图。
* 每个 blocker 都要定位生产代码。
* 每个 blocker 都要分析 inspector / real-code-inspection 为什么没拦住。
* 每个 blocker 都要归类为什么没拦住。
* 每个 blocker 都要给下一轮修复建议。

如果原 blocker 消失，但出现新 blocker：

* 本轮不能输出 READY。
* 输出：

NEXT_DEBUG_LOOP_REQUIRED

并把新 blocker 作为下一轮第一阶段报告的输入。

如果原 blocker 仍存在：

* 输出：

FIX_NOT_EFFECTIVE

并说明为什么修复无效。

如果没有 blocker，且任务进入可接受状态：

可接受状态包括：

* command accepted。
* mission started。
* task 因真实平台登录墙 / captcha / 安全检查进入 review_required。
* task 因受治理 policy fail-closed。
* task 完成。

但必须证明：

* 不是 silent defaulting。
* 不是 preflight 漏检。
* 不是 schema 放宽。
* 不是 command envelope 缺字段。
* 不是 runId / missionId / activationSnapshotRef 为 null。
* 不是 missing ownerResponsible / actionableMessage。
* 不是 proof/ref 缺失。

第十步：最终报告

输出：

tmp/debug-loop/post-fix-runtime-verification/
├── runtime-log.txt
├── runtime-timeline.md
├── task-trigger-summary.md
├── fresh-root-cause-analysis/

│   ├── law-blueprint-mapping.md

│   ├── enforcement-gap-matrix.md
│   └── phase-1-report.md
├── remaining-blockers.md
└── verification-summary.md

每个修复项按以下格式报告：

FIX_AND_RESTART_VERIFIED_READY

READY 条件：

* 第一阶段 P0 blocker 已修复。
* 每个修复都有生产代码重构。
* 每个修复都有 inspector / real-code-inspection 固化。
* 每个修复都有生产突变验证。
* 突变后 FAIL，回滚后 PASS。
* 静态命令达到本轮允许标准。
