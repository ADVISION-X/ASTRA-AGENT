

# 第一步提示词：日志挖掘 + 根因分析

```txt
你现在执行 GrassEye 调试闭环第一阶段：

Runtime Log Blocker Mining & Root Cause Analysis

本阶段只做分析，禁止修复代码。

目标：

读取最新一次真实系统启动日志、任务运行日志、结构化终端日志、debug bundle、Forensics refs，挖掘当前系统所有阻塞点，并逐个追溯：

1. 日志中暴露的问题是什么？
2. 对应法案原本要求是什么？
3. 对应施工图原本要求是什么？
4. 当前系统实际行为违反了什么？
5. 根因在哪个生产文件、哪个函数、哪个链路？
6. 根因对应哪个 inspector / negative proof / audit script 没拦住？
7. 为什么执法脚本没有提前拦住？
8. 应该修生产代码、施工图、inspector、negative proof、结构化日志中的哪一层？

本阶段禁止：

- 禁止修改任何源码。
- 禁止修改法案。
- 禁止修改施工图。
- 禁止修改 inspector。
- 禁止生成修复 patch。
- 禁止只看最后一条错误。
- 禁止只凭猜测。
- 禁止只说“可能是”。
- 禁止用测试通过/失败代替根因分析。
- 禁止把日志文本当作唯一证据，必须结合代码、法案、施工图、执法脚本。

输入来源：

1. 最新终端日志。
2. tmp/debug-loop/** 最新 runtime/debug bundle。
3. tmp/debug-loop/startup-failures/**，如果存在。
4. tmp/debug-loop/post-fix-runtime-verification/**，如果存在。
5. package scripts 实际输出。
6. git diff 当前工作区。
7. 法案文件：
   - .github/instructions/cursor-rules/**
8. 施工图：
   - docs/法案辅助文件/**
9. 执法脚本：
   - scripts/audit/**
10. 生产代码：
   - src/**

如果缺少真实运行日志，立即停止并输出：

BLOCKED_MISSING_REAL_RUNTIME_LOG

不得用旧日志、模拟日志、测试日志替代。

第一步：建立完整运行时间线

必须从日志中整理完整事件链，至少覆盖：

- dependency_check
- update_preflight_check
- map_package_readiness_check
- local_ai_runtime_presence_check
- local_ai_model_roster_check
- local_ai_start_or_connect
- local_ai_health_probe
- ai_capability_readiness_gate
- port_clear
- app_server start
- APP_SHELL_HEALTH_CHECK_STARTED
- APP_SHELL_HEALTH_PASSED
- open_console
- mission_runtime_available
- terminal_structured_log_relay
- HUMAN_COMMAND_RECEIVED / HUMAN_COMMAND_VALIDATED
- MISSION_READINESS_CHECK_STARTED
- MISSION_PREFLIGHT_STARTED
- MISSION_PREFLIGHT_PASSED / FAILED
- COMMANDER_COMMAND_ENVELOPE_BUILT
- NERVE_BUS_ENVELOPE_CREATED
- NERVE_BUS_DISPATCH_STARTED
- COMMAND_ACCEPTED / COMMAND_REJECTED
- ORCHESTRATION_START_RECEIVED
- MISSION_ACTIVATION_SNAPSHOT_FROZEN
- MAP_STEP_SELECTED
- STEP_PRECONDITION_CHECKED
- CAPABILITY_CALL_STARTED
- CAPABILITY_CALL_COMPLETED / FAILED / REVIEW_REQUIRED
- POST_ACTION_VERIFICATION_STARTED / PASSED / FAILED / REVIEW_REQUIRED
- FORENSICS_RECORD_WRITE_REQUESTED
- FORENSICS_RECORD_WRITTEN
- STEP_TRANSITION_EVALUATED
- MISSION_FINALIZED / STOPPED / FAILED / REVIEW_REQUIRED

如果某些事件没有出现，记录为：

LOG_EVENT_MISSING

并判断原因：

- 系统没有执行到该阶段。
- 执行了但没有结构化日志。
- 日志命名不规范。
- 缺少 traceId / runId / spanId / refs，无法关联。

第二步：列出所有阻塞点

阻塞点包括但不限于：

- startup 失败。
- app shell 健康检查失败。
- map readiness passed 但 app server parse failed。
- MissionReadiness passed 后 command rejected。
- preflight passed 后 command rejected。
- command accepted 但没有 Orchestration start。
- command envelope 字段缺失。
- Nerve Bus envelope 字段缺失。
- runId / missionId / traceId / spanId 为 null。
- activationSnapshotRef 缺失或未冻结。
- map step 选中后没有 capability call。
- action step 没有 PAV。
- PAV 失败但没有 review_required。
- Forensics proof ref 缺失。
- promptContractId / outputSchemaRef 不匹配。
- branch DSL 读取裸字段。
- ordinary UI 暴露内部字段。
- COMMAND_REJECTED 没有 actionableMessage。
- failureReason 没有 ownerResponsible。
- 能力组或子能力不在 catalog。
- silent defaulting。
- runLimit / cancellationToken / emergencyStop latch 缺失。
- inspector 没有覆盖当前生产问题。

每个阻塞点必须按以下格式输出：

## BLOCKER-N：一句话标题

### 1. 日志证据

粘贴原始日志片段，不得只概括。

字段必须逐项填写：

- traceId：
- runId：
- attemptId：
- missionId：
- taskTemplateId：
- selectedMapId：
- requestedPlatformId：
- activationSnapshotRef：
- commandId / envelopeId：
- stepId：
- abilityGroupId：
- childCapabilityId：
- owner：
- ownerResponsible：
- status：
- failureReason：
- actionableMessage：

如果字段不存在，写 MISSING，不得补造。

### 2. 实际行为

说明系统真实发生了什么。

例如：

- MissionReadiness passed，但 command semantic gate 发现 runId=null。
- Nerve Bus envelope 已创建，但 Orchestration start 没有发生。
- 说明问题发生在 Commander envelope 构建、Nerve Bus 运输或 Orchestration command input schema 之间。

### 3. 法案原本要求

必须引用具体法案：

- 法案文件：
- lawId：
- 主题：
- 要求：
- 禁止项：
- 当前违反点：

如果没有找到对应法案，写：

LAW_GAP_CANDIDATE

但不得修改法案。

### 4. 施工图原本要求

必须引用具体施工图：

- 施工图文件：
- 章节：
- 要求：
- 当前违反点：

如果没有找到对应施工图，写：

BLUEPRINT_DETAIL_GAP

### 5. 根因定位

必须定位到生产代码和执法代码。

生产代码：

- 文件路径：
- 函数 / class / route：
- 关键判断：
- 为什么导致当前错误：

执法代码：

- inspector 文件：
- negative proof 文件：
- manifest / owner mapping：
- 当前是否覆盖：
- 为什么没有拦住：

不能只写“应该修 preflight”，必须给路径。

### 6. 为什么执法脚本没有拦住？

必须归类：

A. 法案缺失。  
B. 施工图细节缺失。  
C. 法案存在，但 inspector 未覆盖。  
D. inspector 只做 grep / regex / includes，没有 AST / symbol / import graph / anti-escape。  
E. inspector 覆盖 happy path，没有 negative proof。  
F. negative proof 没有生产代码突变验证。  
G. inspector 被豁免、跳过、warning-only、generated fake PASS。  
H. runtime 日志字段不足，无法定位。  
I. 生产代码绕过 governed public interface。  
J. 其它，必须说明。

### 7. 应修复层级，但本阶段不修

只给建议，不动代码：

- 修生产代码：
- 修施工图：
- 修 inspector：
- 修 negative proof：
- 修结构化日志：
- 是否需要申请修改法案：YES / NO

如果需要改法案，只能写：

LAW_CHANGE_APPLICATION_REQUIRED

不得直接改法案。

第三步：输出矩阵

输出：

| 序号 | 问题点 | 阻塞阶段 | 法案要求 | 施工图要求 | 生产根因文件 | 执法缺口文件 | 为什么没拦住 | 修复优先级 |
|---|---|---|---|---|---|---|---|---|

第四步：优先级

P0：

- 系统无法启动。
- command 能启动但不能停止。
- readiness passed 后 command rejected。
- preflight passed 后 command rejected。
- runId / missionId / activationSnapshotRef 为 null。
- silent defaulting。
- active map 缺 proof / snapshot / hash。
- action step 无 PAV。
- target / secret / prompt 边界泄漏。
- inspector 删除也不报错。
- P0 law 但 inspector warning-only。

P1：

- 日志字段不足。
- ordinary UI 暴露内部字段。
- prompt/output schema 证明链不完整。
- branch DSL 过宽。

P2：

- 文案、命名、报告表达不清。

第五步：输出文件

必须生成：

tmp/debug-loop/root-cause-analysis/
├── runtime-timeline.md
├── blocker-list.md
├── law-blueprint-mapping.md
├── root-cause-matrix.md
├── enforcement-gap-matrix.md
└── phase-1-report.md

最终只允许输出：

LOG_BLOCKER_ANALYSIS_READY

或

LOG_BLOCKER_ANALYSIS_NOT_READY

READY 条件：

- 所有日志阻塞点已列出。
- 每个阻塞点都有日志证据。
- 每个阻塞点都有法案/施工图对照。
- 每个阻塞点都有生产代码根因文件。
- 每个阻塞点都有 inspector / negative proof 缺口分析。
- 每个阻塞点都有“为什么没拦住”的归类。
- 没有进行任何代码修改。
```
