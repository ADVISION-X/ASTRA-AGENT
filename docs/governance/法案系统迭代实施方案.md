## 1. 结论

本项目不是在现有 APEX/GrassEye 质检链旁边新增一套新系统，也不是给现有文件改名。

唯一合法路线是：

```txt

-> 对现役治理、业务法条、Owner、脚本、证据和外部 surface 做完整迁移清册
-> 在仓库外隔离 staging 中建立说明书规定的完整新治理系统
-> 把仍有效的业务规则原子化迁入两份 active 法案

-> 生成精确五个 projection
-> 在隔离 staging 通过 mutants、scope、ownership、projection 和 CHANGE validation
-> 复核真实工作树未漂移
-> 一次性原子应用新系统并物理退休旧治理链
-> 按修订后冻结的 bootstrap 算法完成 post-apply CHANGE 闭合并永久关闭 bootstrap exception
-> 另取人类授权，建立独立 release-proof TASK 并运行 RELEASE quality
-> 只在全部证据闭合后签发 candidate-bound SYSTEM_PROVEN proof package
```

迁移完成后的工作树不得同时保留 APEX/GRASSEYE active law、旧 module instructions、旧 generated-plan 主链、旧 `ci:full` verdict、兼容 reader、别名、fallback、shadow 或第二 report writer。

本文件当前是未跟踪文件，既属于 pre-existing dirty path，又属于迁移 DELETE 目标，所以现在不能直接启动施工。施工前必须由人类在二者中选择并固定一种处理方式：先把本方案提交为可追溯 baseline，再由 existing migration 合法删除；或把本方案移到仓库外作为外层授权附件，并明确处理仓内这条未跟踪路径。该条件未解决时固定返回 `BLOCKED_PREEXISTING_DIRTY_TARGET`，不得由 Codex reset、clean、stash、移动或覆盖。只有方案已经进入 Git 历史时，才可以说后续审计追溯依赖 Git 历史。

existing bootstrap case 不得套用上述 normal task sequence；它只执行 source-spec-amendment 后冻结的 exact bootstrap sequence，并验证 baseline、migration contract、staging、mutants、原子应用、永久失效及新旧引用零。

正向 case 必须真正 close，反向 case 必须以规定 code fail closed；每个 worktree 都证明过程无死锁、真实工作树未出现混合 source/projection、新旧 task identity 未分叉、清理后基线未漂移。Mutants 只证明攻击被拒绝，不能替代本工作包的真实完整流程。

退出门：矩阵逐 case receipt 齐全且结果与预期相同；任一 case 未执行、只测单函数、死锁、混合态或清理失败都阻断切换。

### W11｜Mutants 与独立审查

1. 建立唯一 `tests/governance/mutants/manifest.json` 和 `run-governance-mutants.ts`。
2. 覆盖说明书第 78.1—78.7 节全部固定 mutation 类别，每项绑定唯一 command、timeout 和 exact expectedFailureCode。
3. 每个 mutant 在 OS 隔离 worktree/copy 中只改一个点；执行后销毁并复核原 candidate/source hash。
4. 迁移完成后进行与施工过程隔离的五维审查：语义完整、结构唯一、路由完整、证据真实、反作弊。

退出门：全部 mutant 被正确 code 阻断；未阻断、错误 code、超时、清理失败或原工作树变化都整体 FAIL。

### W12｜旧治理归零与原子切换

在 staging 全部 CHANGE 质量门通过后：

1. 运行完整 normative census 形成的 expectedZeroReferencePaths 和 oldReferenceQueries，证明旧 law/runner/generated/report/entry/compat consumers 和所有未绑定规范文本为零；再次证明本实施方案从第一次新 preflight 起就持续不存在。
2. 删除旧 module instructions、旧 law parser/builder/runner、旧 owner assertion-set receipt 链、旧 `ci:full` summary/report generated 文件、旧 normative blueprints 和 orphan dirs；本方案删除已在 W0/W3 完成，不在此时才做。
3. 确认新旧系统没有任何并存路径、脚本 alias、bridge、fallback、dual-read 或 dual-write。
4. 计算完整 patch、delete list、stagedCandidateId 和 staged CHANGE receipts；existing migration 不得生成 staged RELEASE proof。
5. 再次验证真实工作树仍等于 initialCandidateId，并验证 source-spec-amendment 后法定 bootstrap identity、baseline、migration contract 与 staged CHANGE evidence 完全一致。
6. 由唯一 `bootstrap-existing.ts` 以受控原子 patch 一次应用 source、entry、compiler 和五个 projection；任一步失败恢复旧字节，不留下混合状态。成功后 bootstrap exception 永久失效，不能把旧 runtime identity 交给新 entry。

退出门：真实工作树只含新主链或完整旧主链；bootstrap 事务已经按修订后冻结算法闭合，不存在同一 migration task 的跨 authority 接管，也不允许半迁移终态。

### W13｜真实工作树 CHANGE 闭合与独立 RELEASE 证明

原子应用后，不复用 bootstrap runtime identity。按修订后冻结算法完成 post-apply verification；需要 normal task 时，由新 entry 从头 capture 并创建唯一新 task。诊断命令顺序固定为：

```txt
npm run governance:entry
npm run governance:scope:check
npm run governance:ownership:check
npm run governance:law-history:check
npm run audit:projection:check
npm run quality:check
```

上述独立命令只是诊断性预跑，不能替代 `quality:check` 内部固定顺序。`quality:check` 必须按 scope → source/history/ownership → projection → projectChecks → Static → decisions → mutants → Exam → Dynamic → aggregate 执行，并在自身 execution identity 下重跑 required governance mutants。不得复用 W11 staged receipts，也不得在 final quality 前单独生成供聚合器消费的 mutant receipt。

bootstrap existing migration 的 CHANGE closure 必须由修订后的冻结 source 明确定义，不能由本方案臆测。其闭合后，必须另取人类明确授权、另 capture、另 task lock/baseline/envelope 的 `release-proof` TASK，在 RELEASE context 执行全量 active domains、law、Owner、mutant、Exam 和 Dynamic Proof。不得把 existing migration staging receipt 重标为 RELEASE。

本项目已存在跨仓 contract，因此必须等 AGENT 与 xuanxue-web 各自独立 RELEASE receipt PASS，再由 change-set 校验 pin/hash/participant；任一仓缺失或 FAIL，不得签发整体 SYSTEM_PROVEN。

退出门：最终 candidate 未漂移、所有 Owner report systemProven=true、旧引用零、跨仓参与者闭合，才生成附录 D.3 严格 allowlist 的 candidate-bound proof package：只含 `candidateId`、law receipt hashes、Owner report hashes、mutant receipt set hash、cross-repo participant hashes、compiler version 和 freeze version。禁止时间字段、自然语言 READY、额外字段或新规范内容。

## 9. 失败关闭条件

出现下列任一情况，迁移保持未完成，不得原子应用或声明 SYSTEM_PROVEN：

- 用户未明确授权 existing migration、旧治理删除或必要跨仓变更；
- 本方案仍是与目标相交的未跟踪 dirty path，或 source-spec freeze/PDF 冲突未由人类消解；
- 当前 candidate 与 baseline 漂移，或 dirty target 与授权相交；
- 说明书/AGENTS/freeze/toolchain 任一 hash/pin 不一致；
- 旧 law、Owner、runner、generated、report、surface 或 normative document 分母遗漏；
- active law 不是精确两份，或存在 APEX/GRASSEYE/current retired/shadow law；
- law 无 forbidden、Owner、anchor、spec/evidence binding 或独立 predicate；
- domain/Manifest/inspector/report identity 不一致；
- production file/contract/surface 无 Owner或多 Owner；
- generated 不是精确五件或无法 exact-byte 重算；
- projection checker 自动修复，或 compiler/runner/aggregator/writer 出现第二实现；
- Static、Exam、Dynamic 互相冒充，或 fixture/history 进入生产证据；
- mutant 未被 exact expected code 阻断；
- required Dynamic Proof 因外部环境无法完成；
- 跨仓 participant/pin/hash 未闭合；
- W10 任一真实 Git 事务 case 未完整执行或出现死锁/混合态；
- 原子应用无法证明完整回滚；
- 迁移后仍保留本方案或其它未绑定规范性文本。

外部环境阻断 required Dynamic Proof 时，固定结论为 `NOT_PRODUCTION_PROVEN`，不能把静态或旧运行证据补成成功。
