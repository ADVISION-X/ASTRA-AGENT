## 0. 本说明书的唯一身份


本说明书不是业务法案，不定义某个产品应该具备什么功能，也不替代项目的基础法案、功能法案、施工图、规格、契约或代码。

本说明书只拥有一个主权：

```txt
定义“法案系统本身必须如何建设、如何运行、如何防止 Codex 漂移、如何阻断第二链路”。
```

本说明书必须让一个从未接触项目的 Codex 在读完后能够直接回答并执行：

```txt

```

本说明书不是可供 Codex“参考发挥”的原则集合。所有出现“固定”“必须”“只能”“不得”“精确”的条款均为施工合同；Codex 不得补写另一种等价实现，不得把未写明的区域理解为自由发挥区。

# 第一部分｜最高秩序与不可变公式

## 1. 法案系统的七件套

完整法案系统固定由以下七类对象组成，缺一项即未建成：

```txt
1. 冻结的《法案系统建设说明书》；
2. 一份《基础法案.md》；
3. 一份《功能法案.md》；
4. 由唯一 compiler 生成的 law registry；
5. 每个 capabilityDomain 唯一的 Owner Manifest；
6. lawId 对应的机器施工图 anchor、规格、Static/Exam/Dynamic 原子证据 binding；
7. 对当前候选逐 lawId 产生二元裁决的质量系统。
```

唯一公式固定为：

```txt
法案系统
=
权威正文
+ 明确边界
+ 唯一 Owner
+ 完整索引
+ 任务防漂移
+ 可复放证据
+ 失败关闭执法
```

以下组合均不构成法案系统：

```txt
只有文档，没有机器执法；
只有测试，没有 active lawId；
只有索引，没有权威正文；
只有 Owner 名称，没有 lawId 绑定；
只有正向目标，没有禁止面；
只有 PASS 汇总，没有逐法条回执；
只有 Codex 提示词，没有法案与施工图；
只有目录和空壳，没有真实 predicate；
只有静态检查，却宣称真实运行已经成立。
```

## 2. 每条规则必须同时回答五个问题

每条 active lawId 必须精确回答：

```txt
要什么；
不要什么；
谁负责；
怎么证明；
违反后怎么办。
```

任何不能写出明确“不要什么”的要求，不得进入 active 法案。它只能继续讨论，不能取得治理主权。

### 2.1 边界闭合的唯一判定

“说清楚”固定等于同时写清正边界和负边界，不能只写目标，也不能只写禁令：

| 治理对象 | 要：必须做 | 不要：绝对禁区 |
|---|---|---|
| 法案 | `summary`、唯一 Owner、required evidence、违法后果 | `forbidden[]`、不得被下级覆盖 |
| 施工图 | 终态对象、拓扑、目录、合同、状态、恢复和完成标准 | 不建设对象、禁止反向依赖、禁止第二 Owner/第二真相 |
| 规格 | 精确字段、枚举、状态、错误、surface、contract identity | 未声明字段、宽松默认、兼容副本、隐式状态 |
| 索引与 projection | 精确 source projection、导航、原子 binding 和 deterministic bytes | 新增规范、人工维护、PASS/READY、第二索引 |
| 质检 | 正确证据类型、完整分母、逐法条 receipt、失败关闭 | 证据互相冒充、漏项放行、warning/partial/fake PASS |
| 运行逻辑 | 唯一入口、固定状态机、候选绑定、输出位置、清理和终止条件 | 隐式分支、第二 runner、候选漂移、未声明写入和双重终态 |

边界判定规则固定：

1. “没有写不要”不等于默认禁止；它表示边界未闭合，必须 FAIL。
2. “没有写要”不等于执行者可以自行补全；它表示生产义务未定义，必须 FAIL。
3. 合法可选项必须进入精确枚举并同时写明选择者、前置条件和失败语义；不得把“可选”当作自由发挥区。
4. 同一对象在两个位置出现不同的必做、禁区、状态、字段、错误码或输出位置时，不得择一实现；规范自身必须先完成 source-spec-amendment。

## 3. 终态原则

active 法案只描述完整生产系统持续成立的终态，不描述开发阶段。

以下词语或同义语不得在规范性句子中取得有效含义：

```txt
第一期、第二期、阶段一、阶段二、MVP、foundation、preview、planned、以后再做、后续接入、暂不支持、先搭壳、先跑起来、默认关闭、人工晋级、条件成熟后开放、可先留空、待完善。
```

当前实现没有达到 active lawId 时，唯一合法结论为：

```txt
缺失 / 不合规 / FAIL / 必须继续建设。
```

不得通过修改名称、加入 feature flag、保留 fallback、建立兼容桥或降低 inspector 强度把缺失改写成合法状态。

## 4. 权威顺序与两类人类授权

必须把“人类授权”拆成两种不同主权，禁止混为一谈。

### 4.1 本次任务范围主权

人类对本次任务的原文只决定：

```txt
本次目标；
允许触碰的对象；
是否允许 law-amendment；
是否允许 source-spec-amendment；
是否允许 bootstrapMode=blank / existing；
是否属于 release-proof；
是否属于跨仓 change-set。
```

任务原文不得直接降低现役法案、改变 Owner、跳过证据或授权第二链路。若普通任务原文与 active law 冲突，固定结果为 `USER_REQUEST_CONFLICTS_WITH_ACTIVE_LAW`。

### 4.2 规范内容主权

项目规范顺序固定为：

```txt
冻结的《法案系统建设说明书》
-> 《基础法案.md》
-> 《功能法案.md》
-> 系统总施工图
-> capabilityDomain 施工图
-> 规格与机器契约
-> 本次 Task Envelope
-> Owner Manifest 与 generated enforcement bindings
-> 实现代码
-> 当前候选证据
-> 历史记录与讨论材料
```

解释规则固定为：

1. 人类明确授权“修订法案”只打开被点名法条及法定闭包的写权限；新内容仍必须符合本说明书。
2. 人类明确授权“修订本说明书”只打开 source-spec-amendment 事务；不得同时施工业务功能。
3. 下级对象与上级冲突时，修改或删除下级对象；不得建立 compatibility、fallback、shadow 或 bridge。
4. 当前代码永远不能反向证明法案应该降低。
5. generated artifact 只投影，报告只证明，消费端副本只缓存；三者均不得取得源头主权。
6. 历史报告、旧提示词、工单、会议纪要和 Git 历史只用于追溯，不能取得当前主权。

# 第二部分｜固定技术底座与目录


## 5. 治理子系统的固定实现技术

### 5.1 一仓一套精确工具链

每个仓库只能有一个治理运行时和一个 canonical package manager。freeze manifest 必须记录完整版本，入口逐项核对。

```txt
语言：TypeScript，strict=true。
哈希：SHA-256。
文本：UTF-8、无 BOM、LF。
路径：仓库相对 POSIX 路径；有效 UTF-8；Unicode NFC；禁止绝对路径和反斜杠。
JSON：第 30 节 canonical JSON。
AST：TypeScript compiler API。
```

空白仓库默认：

```txt
Node.js：24 的完整补丁版本，写入 .nvmrc；
package manager：pnpm 的完整版本；
lockfile：pnpm-lock.yaml。
```

既有仓库迁移固定规则：

```txt
保留该仓当前唯一生产 package manager 和精确 Node pin；
不得把治理迁移顺带变成 Node/npm/pnpm 全仓迁移；
只有人类另行明确授权 toolchain source-spec-amendment 才能更换；
同一仓不得同时保留 npm 与 pnpm 两条治理命令主链；若 packageManager、lockfile、现役用户入口三者不能确定唯一结果，existing bootstrap 必须返回 CANONICAL_PACKAGE_MANAGER_AMBIGUOUS，等待人类逐字点名后再迁移；
业务依赖可保留原策略，治理子系统新增或直接使用的依赖必须精确 pin。
```

允许的 canonical package manager 只有：

```txt
pnpm
npm
```

脚本逻辑名在所有仓一致；调用形式由 freeze manifest 唯一决定：

```txt
pnpm：pnpm <script-name> [-- args]
npm：npm run <script-name> -- [args]
```

### 5.2 治理依赖

治理子系统直接依赖集合精确为：

```txt
typescript
tsx
@types/node
zod
fast-glob
yaml
```

规则固定：

```txt
治理依赖必须使用完整精确版本，不得使用 ^、~、*、tag 或未解析 workspace range；
主业务可继续使用其它库，但治理 parser、compiler、runner、manifest parser、report writer 不得建立第二实现；
仓库存在 ts-morph 不等于治理系统可以使用它；治理 AST 只认 typescript compiler API；
普通任务不得升级治理工具链；升级必须走 source-spec-amendment、staging、全量 mutants 与新 freeze。
```

主业务系统使用其它语言时，治理子系统仍只保留这一套 TypeScript 实现；不得按业务语言复制第二治理系统。

### 5.3 projectChecks

`projectChecks` 只是 quality 的前置进程检查，不拥有 law verdict。每项只允许：

```json
{
  "checkId": "typecheck",
  "scriptName": "typecheck",
  "requiredContexts": ["CHANGE", "RELEASE"],
  "allowedEphemeralWritePatterns": []
}
```

规则固定：scriptName 必须是 package.json 中唯一脚本；禁止 shell 拼接、网络下载、修改 source、修改 projection/report 或产生第二 PASS；允许写入的只能是 `.gitignore` 已排除且在 record 中精确列出的 cache/build path。运行前后 candidateId 必须相同。existing migration 以旧唯一质量工作流的真实调用图为分母，所有仍有效的 typecheck/lint/test/build-readiness 检查必须迁入本数组或由 active law 明确退役，不得由 Codex自行删减。

# 第三部分｜冻结文件与两份 active 法案正文


## 7. 本说明书的冻结机制

`docs/governance/GOVERNANCE-FREEZE.json` 顶层只允许：

```json
{
  "schemaVersion": 2,
  "status": "SPEC_FROZEN",
  "specPath": "docs/governance/法案系统建设说明书-冻结定稿版.md",
  "specSha256": "<64 lowercase hex>",
  "freezeVersion": "FROZEN-FINAL-V3.1",
  "amendmentAuthority": "explicit-human-only",
  "entryFile": {
    "path": "AGENTS.md",
    "sha256": "<64 lowercase hex>"
  },
  "packageManager": {
    "name": "pnpm",
    "version": "<exact version>"
  },
  "toolchain": {
    "node": "<exact version>",
    "typescript": "<exact version>",
    "tsx": "<exact version>",
    "zod": "<exact version>",
    "fastGlob": "<exact version>",
    "yaml": "<exact version>",
    "typesNode": "<exact version>"
  },
  "projectChecks": [
    {
      "checkId": "typecheck",
      "scriptName": "typecheck",
      "requiredContexts": ["CHANGE", "RELEASE"],
      "allowedEphemeralWritePatterns": []
    }
  ],
  "derivatives": {
    "pdf": {
      "enabled": false,
      "path": null,
      "sourceSha256": null,
      "fileSha256": null
    }
  }
}
```

冻结规则：

1. `specSha256` 对本说明书原始 UTF-8 字节计算 SHA-256；文件不得自写自身 hash。
2. `entryFile.sha256` 对完整 `AGENTS.md` 原始字节计算。
3. 工具链和 package manager 必须是 lockfile 与实际运行时的完整版本，不得保留示例值。
4. `projectChecks` 按 checkId 排序且无重复；quality 只能通过 canonical package manager 调用这些 package scripts。blank 精确包含 typecheck；existing 必须包含旧唯一质量工作流实际调用的全部只读或仅写 ignored-cache 检查，不得静默删除。
5. `governance:entry` 每次任务核对全部 hash、版本和 projectChecks。
6. `SPEC_FROZEN` 只说明规范文本被锁定，不说明实现已经通过。
7. `SYSTEM_PROVEN` 与一个 candidateId 和 RELEASE context 绑定；任何 candidate 变化立即失效。
8. `SYSTEM_PROVEN` 不写回 freeze manifest，不反向取得规范主权；需要留档时只导出不可变 proof package。
9. 只有用户原文明确包含“授权修订《法案系统建设说明书》”并点名范围时，才允许 source-spec-amendment。
10. source-spec-amendment 必须走第 39.2 节 staging transaction；不得在真实工作树暴露中间不一致。
11. PDF 默认关闭。开启时只作为 Markdown 的非权威派生物并绑定 source hash；PDF 不存在或未更新不得阻断默认关闭的冻结交付。

### 8.2 shadow-law detector

6. task-context 位于 gitignored runtime，只复制带 hash 的权威原字节，不构成第三法案源。
7. existing migration 后，旧 instructions、README、manual、policy、constitution、guardrails 和 special rules 只能删除规范内容、降为纯描述导航或移入 `docs/history/**`，并保证生产入边为零。

scanner 不做语义猜测，不接受人工“意思相同”豁免。

# 第四部分｜lawId 与法条原子语法


## 12. lawId 固定格式、lawKey 与历史谱系

lawId 正则固定为：

```regex
^LAW-[A-Z0-9]+(?:-[A-Z0-9]+)*-[0-9]{3}-V[1-9][0-9]*$
```

映射规则：

```txt
capabilityDomain = lower-kebab-case
lawId domain segment = capabilityDomain 转大写
lawKey = 删除末尾 -V<major> 的 lawId
```

示例：

```txt
capabilityDomain: account-person-workspace
lawKey: LAW-ACCOUNT-PERSON-WORKSPACE-001
lawId: LAW-ACCOUNT-PERSON-WORKSPACE-001-V1
```

编号与版本规则：

1. 每个 domain 从 `001` 单调递增。
2. V1 的 `supersedesLawId` 必须为 `null`。
3. Vn（n>1）必须精确 supersede 同 lawKey 的 V(n-1)，不得跳号。
4. requirement、forbidden、appliesTo、Owner、evidenceModes、failure 条件或规范语义任一变化，major 必须加一。
5. 新 major 进入当前工作树时，旧 block、binding、check、spec 当前引用必须在同一 amendment 中物理删除。
6. 当前工作树只允许 active 最新版本；历史只在 Git。
7. 无关语义必须申请新编号，不得复用旧 lawKey。

`law-history-check.ts` 的唯一算法：

```txt
1. 只读取当前 HEAD 可达的全部祖先 commit，不读取其它本地分支、远端 ref 或网络；
2. 枚举两份法案路径在这些 commit 中出现过的唯一 blob；
3. 用当前版本 parser 兼容读取可识别历史 block；无法解析的历史 blob只记录为历史格式，不取得当前主权；
4. 对每个完整 lawId 计算规范指纹：capabilityDomain + tier + evidenceModes + summary + appliesTo + excludes + forbidden + dependsOnLawIds；
5. 同一完整 lawId 出现两个不同规范指纹 -> LAW_HISTORY_ID_REWRITTEN；
6. Vn 缺少 V(n-1) 历史或 supersedes 不匹配 -> LAW_HISTORY_LINEAGE_BROKEN；
7. 当前新 V1 的 lawKey 已在历史出现 -> LAW_HISTORY_KEY_REUSED；
8. 检查只读，不自动改号、不访问网络。
```

## 13. 每条 active 法条的精确 Markdown 结构

下面使用 `law-record-example` 只为避免本说明书自身被 active parser 误识别。active 两份法案中的实际 fence label 必须是 `law-record`，其它结构和字节顺序精确相同：

````law-record-example
### [LAW-<DOMAIN>-001-V1] <中文标题>

```law-record
{ ...canonical law JSON... }
```

#### 要

- <与 summary 字节相同的句子>

#### 不要

- <与 forbidden[0] 字节相同的句子>

#### 证据

- <与 evidenceModes[0] 字节相同的枚举值>

#### 违法后果

- <由 tier 对应的固定句子>
````

`law-parser.ts.parseFrozenMetaLawTemplates` 必须把上述内层 `law-record` 视为被外层示例 fence 包裹的数据，不得把它计入 active block；active `law-parser.ts` 只接受两份法案中未嵌套、未缩进、行内容精确等于三个反引号加 `law-record` 的 fence。

法条 section 不得增加背景故事、当前实现盘点、开发步骤、TODO、方案比较、未来考虑、兼容说明、临时豁免或未进入 metadata 的隐藏要求。实现落位进入 blueprint；字段与 machine contract 进入 spec；任务范围进入 runtime Task Envelope；原因追溯进入非权威历史记录。

## 14. law-record JSON 精确字段


每个 block 只允许：

```json
{
  "schemaVersion": 2,
  "lawId": "LAW-<DOMAIN>-001-V1",
  "supersedesLawId": null,
  "status": "active",
  "tier": "P0",
  "capabilityDomain": "<lower-kebab-case>",
  "enforcementMode": "static",
  "evidenceModes": ["static.ast"],
  "summary": "必须……",
  "appliesTo": ["src/<domain>/**"],
  "excludes": [],
  "forbidden": ["不得……"],
  "dependsOnLawIds": [],
  "routingTags": ["<lower-kebab-case>"]
}
```

字段约束：

### 14.1 schemaVersion、status、supersedesLawId

```txt
schemaVersion 固定整数 2；
status 固定 active；
V1 supersedesLawId=null；
Vn 精确指向同 lawKey 的 V(n-1)。
```

### 14.2 tier

只允许 `P0`、`P1`、`P2`；全部都是失败关闭，不存在 warning law。

### 14.3 enforcementMode 与 evidenceModes

`enforcementMode` 只允许 `static`、`exam`、`dynamic`、`composite`。

```txt
只有 static.* -> static
只有 exam.* -> exam
只有 dynamic.* -> dynamic
存在两类或三类 -> composite
```

`evidenceModes` 只允许：

```txt
static.filesystem
static.text
static.ast
static.types
static.contract
static.dependency
static.config
static.json
static.yaml
static.sql
static.migration
exam.golden
exam.property
exam.state-machine
dynamic.browser
dynamic.service
dynamic.database
dynamic.storage
dynamic.provider
dynamic.authorization
dynamic.recovery
dynamic.performance
```

数组非空、无重复、按上表排序。

### 14.4 summary

```txt
以“必须”或“只能”开头；
只描述一个可独立裁决的不变量；
12 至 240 个 Unicode code point；
不得出现建议、尽量、可能、一般、视情况、以后、后续、暂时、可选、原则上；
不得写开发步骤、文件清单、阶段或任务范围。
```

### 14.5 appliesTo 与 excludes

```txt
仓库相对 POSIX glob；有效 UTF-8 NFC；不得绝对路径、..、反斜杠、负向 glob、brace、extglob、字符组或问号；
只允许精确文件、目录 /**、目录 /**/*.<literal-extension>；
数组字典序、无重复、无包含冗余；
appliesTo 非空；
只有 project-governance、law-system、audit-system 元法条允许根级 **/*；
excludes 只能排除 appliesTo 内明确子面，不得排除生产主链逃避执法。
```

### 14.6 forbidden

1 至 16 项；每项以“不得”或“禁止”开头；一项一个违法条件；不得包含阶段豁免。

### 14.7 dependsOnLawIds

只能引用当前 active lawId；不得自引；依赖图无环；跨域依赖必须同时存在于双方 blueprint machine block；不得分散 Owner。

### 14.8 routingTags

1 至 16 个 lower-kebab-case；只用于 exact route 导航；不得作为 PASS 证据；不得使用相关、通用、其它、misc 等模糊词。

## 15. 人读镜像必须与 JSON 精确一致

`law-parser.ts` 必须验证：

```txt
标题 lawId == metadata.lawId；
所在 capabilityDomain heading == metadata.capabilityDomain；
lawId domain segment == capabilityDomain 大写；
“要”唯一 bullet == summary；
“不要”bullets == forbidden，数量、顺序、字节一致；
“证据”bullets == evidenceModes，数量、顺序、字节一致；
“违法后果” == tier 固定句子；
section 中无其它规范性 bullet；
supersedesLawId 与 major 版本关系成立。
```

任一不一致必须 FAIL，不得选择相信其中一边。

## 16. tier 固定违法后果文本与 parser 算法

人读镜像固定使用：

```txt
P0：任一要求不成立、任一禁止条件出现或任一必需证据缺失，即产生 P0 finding；对应质量入口必须非零退出，并阻断合并、发布和用户交付。
P1：任一要求不成立、任一禁止条件出现或任一必需证据缺失，即产生 P1 finding；对应质量入口必须非零退出，并阻断合并和发布。
P2：任一要求不成立、任一禁止条件出现或任一必需证据缺失，即产生 P2 finding；对应质量入口必须非零退出，并阻断合并。
```

### 16.1 law-parser 的精确解析算法

```txt
1. 读取原始字节；拒绝 BOM、非 UTF-8、非 NFC 路径和 CRLF；
2. 验证 front matter 从首字节开始，以精确 ---\n 打开和关闭；
3. 唯一 yaml parser 解析，禁止重复 key；
4. 逐行维护 Markdown fence 状态；
5. 只有精确行 ```law-record 打开法条 block；只有精确行 ``` 关闭；
6. 禁止未关闭、嵌套、缩进 fence 和 block 内注释；
7. block 必须是单一 JSON object，禁止未知字段；
8. 找到最近 level-3 law heading，一个 heading 精确一个 block；
9. 找到最近 level-2 capabilityDomain heading；基础法案和功能法案算法相同；
10. 验证第 15 节镜像、domain、major 与 supersedes；
11. 记录原始 lineStart/lineEnd、metadata hash、section hash；
12. EOF 后拒绝孤立 heading、孤立“要/不要/证据/违法后果”；
13. 任一解析错误只产生结构冲突，不生成部分 registry。
```

### 16.2 其它 parser

`manifest-parser.ts`、`blueprint-parser.ts`、`spec-parser.ts` 必须拒绝重复 key、未知字段、空字符串、非法路径、未替换占位符和默认补值。

`shadow-law-detector.ts` 必须在 compiler 生成前执行；`law-history-check.ts` 必须在 projection check 与 quality check 中执行。

# 第五部分｜capabilityDomain、Owner 与 Manifest


## 17. capabilityDomain 命名与创建

capabilityDomain 正则固定为：

```regex
^[a-z0-9]+(?:-[a-z0-9]+)*$
```

每个 capabilityDomain 必须代表一个能够独立回答下列问题的完整责任域：

```txt
它拥有哪一种事实或能力；
它创建什么；
它读取什么；
它修改什么；
它裁决什么；
它明确不得接管什么。
```

不得创建以下 domain：

```txt
common、shared、utils、misc、core2、platform2、general、helpers、temporary、legacy、compat。
```

新 capabilityDomain 只有在用户明确授权新增能力域，并且现有 domain 无法合法承接时才允许创建。Codex 不得为了整理代码、追求优雅或减少文件行数自行新增 domain。

## 18. 物理容器 Owner 与逻辑 law Owner 分离

固定关系：

```txt
基础法案.md / 功能法案.md 的文件完整性 Owner = law-system
每个 law-record block 的逻辑 Owner = metadata.capabilityDomain
```

因此：

```txt
一个物理文件可以容纳多个逻辑 Owner；
一个 lawId 只能有一个逻辑 Owner；
Owner 不得通过拥有法案文件路径接管其它 lawId；
Audit 必须按 lawId block 定位主权，不得按 Markdown 文件整体绑定。
```

## 19. Manifest 固定路径与固定文件名

每个 active capabilityDomain 精确存在：

```txt
scripts/audit/domains/<capabilityDomain>/manifest.json
scripts/audit/domains/<capabilityDomain>/inspector.ts
scripts/audit/domains/<capabilityDomain>/predicates.ts
```

目录名、manifest.capabilityDomain、inspector literal capabilityDomain、report capabilityDomain 必须完全相同。

不得设置 alias、prefix fallback、umbrella owner 或共享 report。

## 20. Manifest 精确 schema：一个 lawId 一个原子 binding

Manifest 顶层只允许：

```json
{
  "schemaVersion": 2,
  "capabilityDomain": "<lower-kebab-case>",
  "status": "active",
  "allowedLawIds": ["LAW-..."],
  "blueprintRefs": ["docs/blueprints/domains/.../...-BLUEPRINT.md"],
  "specRefs": ["docs/specs/.../...spec.json"],
  "lawBindings": {
    "LAW-...": {
      "blueprintRef": "docs/blueprints/domains/.../...-BLUEPRINT.md#anchor:law.LAW-...",
      "specRefs": ["docs/specs/.../...spec.json"],
      "staticCheckId": "<domain>.<check-id>",
      "examBindings": [
        {
          "examId": "<domain>.<exam-id>",
          "evidenceModes": ["exam.property"],
          "frequency": "EVERY_RELEVANT_CHANGE"
        }
      ],
      "proofBindings": []
    }
  },
  "ownedPaths": ["src/<domain>/**"],
  "observedPaths": [],
  "evidenceModes": ["static.ast", "exam.property"]
}
```

`proofBindings` 元素精确为：

```json
{
  "proofId": "<domain>.<proof-id>",
  "evidenceModes": ["dynamic.service"],
  "frequency": "EVERY_RELEVANT_CHANGE"
}
```

约束固定：

1. schemaVersion=2，status=active。
2. `allowedLawIds` 精确等于该 domain 当前全部 active lawId。
3. `lawBindings` keys 与 `allowedLawIds` 精确相等。
4. 每个 law binding 只有一个稳定 blueprint anchor；anchor 必须存在。
5. `specRefs` 顶层精确等于全部 law binding specRefs 的去重并集。
6. law 含 static.* 时 `staticCheckId` 必须为唯一字符串；不含 static.* 时必须为 `null`。
7. law 的 exam.* 必须被 `examBindings.evidenceModes` 精确覆盖；无 exam.* 时数组必须为空。
8. law 的 dynamic.* 必须被 `proofBindings.evidenceModes` 精确覆盖；无 dynamic.* 时数组必须为空。
9. binding 不得声明法条未要求的 evidenceMode。
10. checkId、examId、proofId 全项目唯一，格式 `<domain>.<lower-kebab-case>`。
11. frequency 只允许 `EVERY_RELEVANT_CHANGE`、`RELEASE_CANDIDATE`。
12. `blueprintRefs` 精确等于全部 binding 使用的 blueprint 文件集合。
13. `evidenceModes` 精确等于 domain 法条 evidenceModes 去重并集。
14. `ownedPaths` 是 primary 写主权；`observedPaths` 只读，不赋予写权。
15. Manifest 不得包含 owner、entry、reportPath、PASS 条件、豁免或新法案义务。
16. 不得再使用分离的 `lawBlueprintBindings`、`lawCheckBindings`、lawIds/checkIds 平行数组作为主权映射。

### 20.1 ownedPaths / observedPaths 唯一 pattern

只允许精确文件或目录 `/**`。禁止根级宽泛 Owner、glob 元字符、尾随斜杠、`.`、`..`、符号链接越界、大小写 alias 和“最具体者优先”。任何命中重叠直接失败。

## 21. 候选文件角色与 candidate-aware ownership

每个 candidate path 必须按以下顺序取得一个且只有一个 `fileRole`：

```txt
1. AGENTS.md、两份 active law、冻结说明书、freeze manifest -> GOVERNANCE_AUTHORITY；
2. docs/blueprints/**、docs/specs/** -> BLUEPRINT_OR_SPEC；
3. scripts/audit/generated/** -> GENERATED_PROJECTION；
4. scripts/audit/reports/** -> AUDIT_REPORT；
5. .governance/runtime/** -> RUNTIME_IGNORED；
6. tests/** -> TEST_ONLY；fixtures/** -> FIXTURE_ONLY；examples/** -> EXAMPLE_ONLY；docs/history/** -> HISTORY_ONLY；
7. 其余 PRESENT/DELETED path -> PRODUCTION。
```

机器规则：

1. 角色判定由 `ownership-check.ts` 基于状态感知 candidate records 执行，不属于纯 compiler。
2. compiler 只验证 Manifest claims 无重叠和 law bindings 完整，不得返回候选级 `UNOWNED_FILE`。
3. 非生产角色只要被生产 import、package script、运行配置、发布包、代码生成、迁移或业务状态写入消费，立即升级为 PRODUCTION。
4. PRESENT 的 PRODUCTION 文件必须精确命中一个 Manifest `ownedPaths`。
5. DELETED record 不读取工作树字节；删除权限由 baseline Owner、pathClaim、surface delta 和 retirement closure 验证。
6. rename 规范化为旧 path DELETE + 新 path PRESENT；不得保留 alias 或双入口。
7. symlink 只 hash link target text，禁止越出仓库根；submodule、unmerged index、特殊设备 file mode 直接 blocked。
8. path 必须是有效 UTF-8、Unicode NFC、仓库相对 POSIX；大小写折叠冲突或同一路径多编码表示直接 blocked。

固定结果：

```txt
PRODUCTION PRESENT 零 Owner -> UNOWNED_PRODUCTION_FILE；
PRODUCTION PRESENT 多 Owner -> MULTIPLE_PRIMARY_OWNERS；
非生产路径被生产消费但未升级 -> ROLE_ESCALATION_REQUIRED；
DELETED 无合法 retirement claim -> UNAUTHORIZED_PRODUCTION_DELETE；
新增一级目录无人类架构/domain 授权 -> NEW_TOP_LEVEL_PATH_UNAUTHORIZED。
```

Codex 不得先创建路径、入口或配置再补 Owner。

## 29. hash 的精确算法

```txt

specSha256 = spec 原始 canonical JSON bytes；
manifestSha256 = manifest 原始 canonical JSON bytes；
bindingSha256 = canonical atomic law binding bytes。
```

## 30. canonical JSON

对象 key 按 Unicode code point 升序递归排序；数组按本合同指定顺序；缩进 2；单 LF 结尾；禁止尾空格、注释、NaN、Infinity、undefined 和时间字段。


任一冲突返回完整排序 conflicts 且不返回可写 artifact bytes；不得新增 warning 旁路。

## 33. audit:build 的唯一写入协议


`audit:build`：

```txt
运行第 32.1 节 source-integrity preflight；
在内存调用唯一 compiler；
若有冲突，stderr 输出按 code/path/lawId 排序的冲突并非零退出；
若无冲突，把五个 artifact 写入同文件系统临时目录；
逐文件 fsync；
验证临时目录文件集合精确为五个；
验证临时字节可重新解析；
以受控替换方式更新 generated 目录；
替换失败必须恢复旧五文件；
不得留下部分新、部分旧的 generated 集合。
```

临时目录缺失、多出或错名任一文件时，`audit:build` 唯一返回 `GENERATED_FILESET_INVALID`；该 code 由 build wrapper 拥有，不得由 pure compiler、Owner inspector 或 final aggregator 返回。

`audit:build` 不得写 Owner report。

## 34. projection check

`audit:projection:check` 必须：

```txt
运行第 32.1 节 source-integrity preflight；
读取现有五个 generated 文件；
以内存调用同一 compiler；
比较文件集合与 exact bytes；
比较前后工作树 hash，证明检查无写入；
缺失、多余、手改、陈旧、无法重算均非零退出。
```

当前 generated 目录文件集合不是精确五件时，projection check 同样返回 `GENERATED_FILESET_INVALID`；集合正确但任一 exact byte 不一致时返回 `GENERATED_PROJECTION_STALE`。两个 code 不得互换。

projection checker 不得自动调用 `audit:build`，不得修复 generated，不能输出第二 verdict artifact。

# 第八部分｜Codex 任务防漂移系统

## 35. Codex 落笔前的固定事务

任何任务，包括 read-only 与 release-proof，都必须先建立可复放任务身份；只有 `.governance/runtime/**` 写入可发生在仓库治理入口之前。

固定顺序：

```txt
1. request-capture：写入人类请求原字节；
2. governance:entry：验证 freeze、entry、现役治理与 lock 冲突；
3. governance:task:start：建立事务锁、baseline 与初始 envelope；
4. Codex 只读分析；
5. task-proposal：声明完整初始路径、closures、surfaces；
6. governance:scope:propose；
7. governance:route；
8. 验证并全文读取 task-context；
9. ROUTED 后才允许首个仓库写入。
```

### 35.1 request-capture

唯一脚本 `request-capture.ts` 从标准输入接收外层编排器已经合成的完整人类授权文本，原字节写入 `user-request.txt`。禁止摘要、翻译、润色、加入系统消息、开发者消息、工具输出或 Codex 计划。

### 35.2 task lock 与崩溃恢复

`task-lock.json`：

```json
{
  "schemaVersion": 2,
  "taskId": "<16 lowercase hex>",
  "initialCandidateId": "<64 lowercase hex>",
  "userRequestSha256": "<64 lowercase hex>",
  "state": "INITIALIZING",
  "closedCandidateId": null,
  "finalEvidenceSetSha256": null
}
```

状态只允许 `INITIALIZING`、`OPEN`、`CLOSED`、`ABANDONED`。

`task-start.ts` 使用同目录 transaction 临时文件、fsync 和原子 rename：先 O_EXCL 建 `INITIALIZING` lock，再生成 baseline/envelope，全部回读一致后改为 OPEN。崩溃后同 userRequestSha256 只能在临时文件 hash 可重算时恢复；否则 `INCOMPLETE_TASK_INITIALIZATION`。不得删除 lock 规避。

CLOSED 必须写入最终 candidateId 与全部 component/final receipt hash 的集合 hash；candidate 改变后该 CLOSED 只代表历史任务，不代表当前候选。


### 35.4 taskType 与 bootstrapMode 的唯一分类

`taskType` 只允许 `source-spec-amendment`、`law-amendment`、`release-proof`、`read-only`、`implementation`。按以下顺序首次命中即停止：

```txt
1. 人类原文逐字包含“授权修订《法案系统建设说明书》”并点名范围 -> source-spec-amendment；
2. 人类明确要求新增、修改、升级或退役 active lawId/基础法案/功能法案 -> law-amendment；
3. 人类明确要求生产发布证明，且除 runtime evidence 外不允许仓库写入 -> release-proof；
4. 人类明确使用“只读”并禁止仓库写入 -> read-only；
5. 其它 -> implementation。
```

Codex 不得自行提升到 amendment，也不得把 amendment 降为 implementation。

`bootstrapMode` 只允许 `none`、`blank`、`existing`：

```txt

existing：仓库已有生产代码或旧治理，且人类明确授权一次性迁移；
none：其余任务。
```

blank/existing 只建设或迁移治理，不得同时施工新业务能力。`read-only`、`release-proof` 的 repo write/delete paths 必须为空。

### 35.5 explicitTargets

### 35.8 Envelope 写权

只有 task-start 创建，scope-propose 原子更新。Codex 只能写 runtime proposal，不得手改 envelope。任何字节无法由 baseline、request、approved proposal 和法定算法重算，返回 `TASK_ENVELOPE_TAMPERED`。

## 36. task baseline 与状态感知文件记录

baseline 顶层保留 taskId、initialCandidateId、gitHead、workspaceStateSha256、freezeSha256、lawCorpusSha256、files、preExistingDirtyPaths、generatedArtifacts。

`files[]` 每项：

```json
{
  "path": "repo/relative/path",
  "presence": "PRESENT",
  "contentKind": "REGULAR",
  "sha256": "<hash or null>",
  "size": 0,
  "mode": "100644",
  "indexOid": "<git oid or null>",
  "indexState": "CLEAN",
  "worktreeState": "CLEAN"
}
```

presence：PRESENT、DELETED。contentKind：REGULAR、SYMLINK。index/worktree state：CLEAN、MODIFIED、ADDED、DELETED、RENAMED、UNTRACKED。

算法使用 `git status --porcelain=v2 -z`、`git ls-files --stage -z` 与 untracked enumeration；tracked deletion 记录 indexOid/mode，不读取不存在的工作树文件。rename 在候选 hash 中表现为 old DELETE + new PRESENT。

preExistingDirtyPaths 与目标相交仍 blocked；Codex 不得 reset、clean、stash、restore、覆盖或移动用户基线。

## 37. task-proposal 与初始完整施工分母

首次 proposal 顶层：taskId、proposedWritePaths、proposedDeletePaths、pathClaims、proposedSurfaces、initialClosures、scopeExpansions。其中 scopeExpansions 必须为空，但 initialClosures 可以非空。

固定流程：

```txt
只读扫描唯一 Owner、合同、调用边、proof 和旧路径；
列出最小且完整的初始闭包；
把已知 generated、contract、proof、retirement 一次性纳入 initialClosures；
scope:propose 验证并原子写 envelope；
route 成功后才写。
```

禁止以“可能需要”为由预授权全仓；禁止把应在初始闭包声明的路径故意延后成 expansion。

## 38. 合法 post-route scope expansion

只有任务已 ROUTED 且只读阶段无法预先确定的真实闭包，才允许增加 EXPANSION phase path；原因码精确为五个：

### 38.1 GENERATED_PROJECTION

```txt
已获准 source/Manifest/blueprint/spec/declaration 变化；
唯一 compiler 在内存证明固定五文件 expected bytes 改变；
path 只属于固定五个 projection；
report/cache/summary 不得伪装 projection。
```

### 38.2 OWNER_CLOSURE

```txt
新增 path 与已获准 triggerPath 属于同一 primary domain；
存在可复放 import/export/call/data-ownership edge；
不修改会产生精确 compile/runtime-contract/governance failure code；
不得用于整理、抽象、去重、重命名或未来复用。
```

### 38.3 CONTRACT_CLOSURE

```txt
已获准实现改变唯一 typed contract/schema/migration 的输入、输出、状态、错误、持久化或版本；
contract provider path 是唯一主权源；
全部消费者由 dependency graph 精确枚举；
不得建立 v2 copy、compat schema、optional fallback、dual-read 或 dual-write。
```

### 38.4 PROOF_CLOSURE

```txt
active law atomic binding 明确要求对应 Static/Exam/Dynamic component；
现有 declaration/实现缺失、对本候选失效或确定性失败；
新增 path 位于固定 proof 目录并绑定唯一 checkId/examId/proofId；
不得建立第二 verdict、runner、fixture truth 或报告写入者。
```

### 38.5 OLD_PATH_RETIREMENT

```txt
旧 path 与新 path 承担同一 active role；
新 path 已在 envelope；
旧入口、注册、导出、配置、测试、文档与 surface 引用可穷举；
本次把全部引用降为零；
不得保留 alias、forwarder、feature flag、deprecated facade 或 rollback branch。
```

每项 expansion 精确记录：reasonCode、path、lawId、triggerPath、triggerRef、counterfactualFailure、explanation、approvedEnvelopeSha256。triggerPath 必须已获准，evidence 必须来自当前 candidate，counterfactualFailure 必须是可复现 code。

新增 dependency/network/browser/native-host 等 surface 时，path expansion 与 proposedSurface 必须同时批准。每项 expansion 在首次触碰前执行 scope:propose 和重新 route；旧记录不得删除、改 lawId、改 admission 或改 phase。cleanup/refactor/style/future-proofing/compatibility 均不是合法理由。

## 39. 唯一路由、amendment transaction 与 existing bootstrap


### 39.1 普通 route

route 只接收当前 exact-byte registry、envelope、baseline、五个 projection。它必须：

```txt
验证 lock/request/baseline/envelope；
基础法案全文进入 context；
现有 path 通过 ownedPaths 找唯一 primary domain；
新 path 通过最近已存在父目录和 blueprint/spec 声明找唯一 domain；
把 proposedSurfaces 的 ownerDomain 加入 primary domains；
无 path 时按 explicit lawId/domain/artifact/command/surface exact route，禁止仅依赖模糊 tag；
加入 primary domain 全部 active lawId；
加入 observer domains；
递归展开正向依赖，删除/law amendment 时加入反向闭包；
固定加入 project-governance、law-system、audit-system 全部 active lawId；
从 Manifest 原子 binding 获取 blueprintRefs、specRefs、static/exam/proof declarations；
生成 context 与 receipt，回读 hash；
ROUTED 前不写仓库。
```

### 39.2 law/source-spec amendment staging transaction

唯一脚本 `amendment-transaction.ts`，状态：PREPARED -> STAGING -> STAGED_VALIDATED -> APPLIED -> POST_VERIFIED | ABORTED。

```txt
1. 在旧 authority 下完成 request、baseline、pre-route 和完整 amendment plan；
2. 创建 OS 临时目录中的隔离工作树，绑定 initialCandidateId；
3. Codex 只在 staging 修改说明书/法案及其完整闭包；真实工作树保持不变；
4. staging 内生成新 freeze（source-spec 时）、新 manifests/blueprints/specs/declarations 和五个 projection；
5. 使用 staged 新 authority 生成 post-route，并执行 parser、compiler、history、mutants、quality；
6. 计算完整 patch、删除清单和 stagedCandidateId；
7. 再次验证真实工作树仍等于 initialCandidateId；
8. 以受控原子 patch 应用全部文件；任一步失败恢复旧字节；
9. 在真实工作树重算 projection、post-route、scope 和 quality；
10. 成功后关闭 task；失败保留 OPEN 且不得留下 source/projection 混合状态。
```

source-spec amendment 中 PDF 只有 `enabled=true` 才在 staging 生成；默认 false 不要求 PDF。

### 39.3 bootstrapMode=existing 一次性受限入口

既有仓在新 entry 尚不存在时，允许唯一 bootstrap 例外：只可创建本说明书固定治理路径、runtime baseline/migration contract，并删除被 migration contract 穷举的旧治理路径；不得改业务功能语义。

`bootstrap-existing.ts` 必须：

```txt
验证人类原文含明确 existing 治理迁移授权；
捕获全仓状态感知 baseline；
列出全部旧法案源、instructions、registry、Owner map、compiler、runner、generated、report writer、CI 入口；
为每项给出 MIGRATE/DELETE/HISTORY_ONLY/KEEP_NON_NORMATIVE 决策和 evidenceRef；
列出全部生产根与拟 domain Owner；
禁止新增业务 domain、surface 或功能；
在隔离 staging 中一次性建立新系统并把旧引用降为零；
通过 migration mutants 后原子应用；
例外完成即永久失效，后续只走正常 entry。
```

```txt
把 dependency、listener、outbound host、browser permission 或 Native Host 藏在普通 path diff；
在消费仓复制跨仓 contract 主权；
在真实工作树暴露 amendment 中间 source/projection 不一致；
把 initial closure 故意延后伪装 expansion；
把 tracked deletion 当读取错误而取消 retirement；
删除/改写 task lock、baseline、envelope、route receipt 或 task-context 逃避检查。
```

## 43. 完整任务而非阶段任务

获准能力必须在同一 task 闭合唯一实现、合同、surface、持久化、错误恢复、旧路径、projection、当前 CHANGE context 必需的 Static/Exam/Dynamic 和 final aggregate。外部环境使当前必需 Dynamic 无法完成时，结果固定 `NOT_PRODUCTION_PROVEN`，不得声称任务完成。

任务通过 CHANGE context 只证明本次变更闭合；只有第 63 节 RELEASE context 可产生 `SYSTEM_PROVEN`。这不是阶段交付，也不允许把缺失实现留到以后。

## 44. 最终 scope check 完整算法

输入固定为 baseline、Task Envelope、route receipt、task-context、当前 Git index/worktree、五个 projection、surface extractor registry 和 cross-repo pin。顺序：

```txt
1. 重算 request/envelope/route/context hash，验证同一 OPEN task；
2. 以 baseline 状态感知 records 计算 PRESENT/DELETED/rename/mode/symlink/staged/unstaged/untracked 实际 delta；
3. 实际 WRITE 必须属于 proposedWritePaths，实际 DELETE 必须属于 proposedDeletePaths；
4. 每个 pathClaim 与 write/delete 集合、action、phase、admission 精确一致；
5. INITIAL closure 在首次 route 前批准；EXPANSION 在首次触碰前批准并重新 route；
6. generated 变化只在 GENERATED_PROJECTION claim 下且 exact bytes 来自唯一 compiler；
7. 说明书/freeze/AGENTS 只在 source-spec amendment staging，active law 只在 law/source-spec amendment staging；
8. preExistingDirty path 的 path/hash/mode/index/worktree state 与 baseline 完全一致；
9. 新顶级目录、新 domain、新 dependency 和所有 surface 均有明确授权、唯一 Owner、lawId、blueprint anchor、spec 与 extractor；
10. 每个新增 PRESENT production file 精确一个 Owner；每个 DELETE 有合法 retirement；
11. 从 baseline 与当前 candidate 提取实际 surfaces，按 action/kind/identity 与 proposedSurfaces 精确相等；identity 改名必须旧 DELETE + 新 ADD；
12. extractor 无法解析潜在 surface-bearing 文件即失败，不得当作无 delta；
13. route 依赖的 law/Manifest/blueprint/spec/declaration 变化使普通 route stale；amendment 只能使用 STAGED_AMENDMENT post-route；
14. cross-repo contractId/version/provider commit/hash/changeSet participant 与 pin 精确一致；
15. proposed path/surface 未实际完成时，不得以任务完成关闭 lock。
```

scope failure code 只允许：

```txt
TASK_ID_MISMATCH
RUNTIME_ARTIFACT_TAMPERED
SCOPE_DIFF_OUTSIDE_ENVELOPE
INITIAL_CLOSURE_INVALID
SCOPE_EXPANSION_AFTER_WRITE
GENERATED_BYTES_NOT_FROM_COMPILER
FROZEN_SPEC_MODIFIED_WITHOUT_AUTHORIZATION
LAW_SOURCE_MODIFIED_WITHOUT_AUTHORIZATION
PREEXISTING_DIRTY_PATH_CHANGED
NEW_TOP_LEVEL_PATH_UNAUTHORIZED
NEW_PRODUCTION_FILE_UNOWNED
UNAUTHORIZED_PRODUCTION_DELETE
PATH_CLAIM_MISMATCH
UNAUTHORIZED_SURFACE_DELTA
MISSING_DECLARED_SURFACE_DELTA
SURFACE_BINDING_MISMATCH
SURFACE_DELTA_UNDETERMINED
ROUTE_STALE_AFTER_GOVERNANCE_CHANGE
CROSS_REPO_CONTRACT_UNPINNED
```

任一失败非零退出；“只是格式化、import 排序、自动生成或顺手修复”不得放行。

`NEW_TOP_LEVEL_PATH_UNAUTHORIZED` 只属于本节最终 scope check；route 尚未允许写入时不得使用该 code，必须使用第 41 节的 `NEW_TOP_LEVEL_PATH_NOT_AUTHORIZED`。


# 第十部分｜Static Audit 的唯一主链


## 48. Static Audit 的唯一职责

Static Audit 只以当前候选的静态结构证明 active lawId，包括：

```txt
文件系统；
文本；
AST；
类型；
schema；
合同；
依赖；
配置；
JSON/YAML/SQL；
数据库迁移声明；
目录和 Owner 绑定。
```

Static Audit 不得：

```txt
启动业务服务；
访问浏览器、网络、数据库、对象存储或 provider；
读取历史运行结果作为当前证据；

输出 release verdict；

修改业务源码；
自动修复违法。
```

## 49. CandidateIdentity v2 精确算法

候选枚举固定使用 Git 状态感知三件套，而不是“列出路径后逐个读取”：

```txt
git status --porcelain=v2 -z
git ls-files --stage -z
受 .gitignore 约束的 untracked enumeration
```

每个候选 record 规范为：

```json
{
  "path": "repo/relative/path",
  "presence": "PRESENT",
  "contentKind": "REGULAR",
  "mode": "100644",
  "sha256": "<hash or null>",
  "indexOid": "<oid or null>",
  "indexState": "CLEAN",
  "worktreeState": "CLEAN"
}
```

规则：

1. PRESENT regular hash 原始字节；PRESENT symlink hash 链接目标文本。
2. DELETED 不读取文件，hash 字段 null，保留 indexOid/mode/state。
3. rename 规范化为 old DELETED + new PRESENT；rename hint 不进入 candidateId。
4. file mode、index/worktree state、untracked 都进入 record。
5. 忽略 `.git/**`、`.governance/runtime/**`、reports、artifacts、coverage、依赖与构建缓存；五个 generated 包含。
6. 路径必须有效 UTF-8 NFC；检测大小写折叠冲突。
7. submodule、unmerged conflict、越界 symlink、特殊设备文件直接 blocked。
8. records 按 path + presence 排序，canonical JSON 后参与 hash。

candidateId 精确计算：

```txt
sha256(
  "candidate-schema-v2\n"
  + compilerVersion + "\n"
  + gitHeadOrUNBORN + "\n"
  + canonicalJson(candidateRecords) + "\n"
)
```

绝对路径、时间、机器名不进入。tracked deletion 是合法候选状态，不得因读取失败 blocked。

## 50. candidate mutation sentinel


`candidate-mutation-sentinel.ts` 被 `audit:run` 与 `quality:check` 复用，但两者输出权不同。

`audit:run` 只在以下节点重新计算 candidateId：

```txt
建立 evidence index 前；
index sealed 后；
每个 Owner 执行前；
每个 Owner 执行后；
发布本次 Static component receipt set 前。
```

`quality:check` 在消费 Static receipts 后继续于以下节点重算：

```txt
产生 EvidenceRequirementDecisions 前；
全部 required Exam/Dynamic components 后；
全部 Owner report 写入本次 invocation 临时 sink 后；
`TASK` 正式替换 report cache 前，或 `CI_CANDIDATE` 写 invocation receipt 前。
```

任一变化：

```txt
删除本次 execution evidence root 内的 receipts 与临时 reports；
`TASK` 不更新正式 report cache；`CI_CANDIDATE` 不写 invocation receipt；
返回 CANDIDATE_DRIFT；
非零退出。
```

`audit:run` 永远不生成或发布 Owner report；它只能把 Static component receipts 写入本次 execution evidence root。只有 `quality:check` 的 final aggregator 可以进入 report 节点。

## 51. 唯一 CandidateStaticEvidenceIndex

每次 `audit:run` 只能建立一个运行期 index，固定包含：

```txt
CandidateIdentity；
file catalog；
canonical glob -> immutable sorted file ids；
text index；
JSON/YAML parsed tree；
TypeScript/JavaScript 单一 AST project；
SQL statement index；
dependency graph；
source hash；
parse blockers；
compiled law query catalog；
sealed=true。
```

规则：

```txt
同一文件原始字节只读一次；
同一 representation 最多解析一次；
同一 glob 只编译一次；
同一 law query 只编译一次；
index sealed 后禁止增量补读；
Owner 只能获得只读 view；
Owner 不得直接访问 fs、parser、network、process.env、Date、Math.random；
运行结束销毁 index；
不得跨 run cache。
```

## 52. 生产证据分母

static evidence 的文件分母固定由：

```txt
全部 active law appliesTo/excludes；
全部 manifest ownedPaths/observedPaths；
对应 blueprint/spec refs；
固定治理源码；
```

求并集得到。

任何 discovery、read、decode、parse 失败均是 blocker，不得解释为“文件不存在所以禁止项未出现”。

```txt

fixtures/**
examples/**
artifacts/**
coverage/**
docs/history/**

```

治理 meta inspector 可以读取 tests/governance 源码验证质量系统本身是否有 mutant coverage，但测试内容仍不能证明业务实现成立。

## 53. Inspector 精确合同

每个 `inspector.ts` 只能：

```txt
从 inspector-contract 导入 defineInspector；
从 predicates.ts 导入本 domain predicates；
以 literal capabilityDomain 注册；
以 literal checkId map 注册；
接收只读 evidence view；
返回 assertion results 和 findings。
```

固定形状：

```ts
export default defineInspector({
  capabilityDomain: "<domain>",
  checks: {
    "<domain>.<check-id>": predicate
  }
});
```

禁止：

```txt
动态计算 capabilityDomain；
动态 import inspector；
读取 manifest 决定自己是谁；
直接写 report；
固定返回 PASS；
空 assertions；
catch 后返回通过；
直接读磁盘或启动服务；
调用其它 domain 私有 predicate；
依据文件数量、token、anchor 或 owner 存在直接 PASS。
```

## 54. Law Predicate 精确结果

每个 checkId 对应一个 lawId，并返回：

```json
{
  "lawId": "LAW-...",
  "checkId": "domain.check-id",
  "assertions": [
    {
      "assertionId": "domain.assertion-id",
      "passed": true,
      "evidenceRefs": ["ast:path#..."],
      "message": "精确说明检查的关系"
    }
  ],
  "findings": []
}
```

规则：

```txt
assertions 至少 1 项；
每个 assertionId 全项目唯一；
passed=true 必须至少一个 exact evidenceRef，纯 absence law 必须提供 scope denominator ref；
任一 passed=false 必须产生 finding；
任一 finding 使该 Static component receipt 为 COMPONENT_FAIL；
predicate 抛错等同 EXECUTED_FAIL；
不得返回 coverage percentage；
不得把多个 lawId 合成一个 predicate receipt。
```

## 55. SemanticEvidenceRef 固定格式

只允许：

```txt

```

禁止使用自然语言“见代码”“文件存在”“大概在某处”作为 evidenceRef。

## 56. 证据 requirement decision、component receipt 与 LawQualityReceipt

### 56.1 verificationContext

只允许：

```txt
CHANGE：普通写任务、law/source-spec amendment、existing migration；证明本次变更闭合。
RELEASE：release-proof 或 blank bootstrap 终检；证明当前完整 candidate 可取得 SYSTEM_PROVEN。
```

context 由 taskType/bootstrapMode 确定，Codex 不得手工选择较弱 context：`release-proof` 与 `bootstrapMode=blank` 固定 RELEASE；其它写任务固定 CHANGE。`CI_CANDIDATE` invocation 固定使用 CHANGE，永远不得产生 RELEASE 或 `SYSTEM_PROVEN`。

执行身份字段固定为：

```txt
invocationMode：TASK | CI_CANDIDATE；
TASK：executionId == taskId，taskId 非空，baseSha/headSha 为 null；
CI_CANDIDATE：taskId 为 null，executionId 按第 64 节计算，baseSha/headSha 为精确 40 位 Git SHA；
同一执行链的 decision、component、LawQualityReceipt、Owner report 必须具有完全相同的 invocationMode/executionId/taskId/baseSha/headSha/candidateId/context；
任一不一致按 RECEIPT_EXECUTION_IDENTITY_MISMATCH 失败。
```

执行输出根固定为：

```txt
TASK：.governance/runtime/evidence/<executionId>/**；Owner report 先写该 root 的 temp/reports，再由唯一 report-writer 原子替换 scripts/audit/reports/** current cache。
CI_CANDIDATE：mkdtemp 创建的仓库根 realpath 之外 OS/CI ephemeral execution root；decision、component、LawQualityReceipt、Owner report、mutant receipt 与 ci-invocation-receipt 全部只能写该 root。
```

`report-writer.ts` 是两种 invocation 共用的唯一 canonical serializer/writer。它必须接收显式 `invocationMode + executionRoot + sinkPath`，验证 `CI_CANDIDATE` 的 executionRoot 和 sinkPath 均不位于仓库根内，并拒绝 symlink、相对路径逃逸、repo report cache 与 invocationMode 不匹配。除 freeze 中 `projectChecks[].allowedEphemeralWritePatterns` 精确允许的 ignored cache/build 输出外，CI checkout 不得产生任何写入。

`executionDomainSet` 只按以下规则产生，不得由 runner 手写：

```txt
TASK/CHANGE：route receipt 中 primaryDomains、observerDomains、依赖闭包和三个固定 meta domains 的去重集合；
TASK/RELEASE：law registry 中全部 active domains；
CI_CANDIDATE/CHANGE：law registry 中全部 active domains。
```

每个 executionDomainSet 内 domain 必须产生完整 Owner report；集合外 domain 在该 invocation 不产生 report。只有 TASK/RELEASE 才允许据全部 active domains 声明 `systemProven=true`。

### 56.2 EvidenceRequirementDecision

aggregator 在执行 component 前，为每个 atomic binding 产生非 verdict decision：

```json
{
  "schemaVersion": 1,
  "candidateId": "...",
  "invocationMode": "TASK",
  "executionId": "...",
  "taskId": "...",
  "baseSha": null,
  "headSha": null,
  "verificationContext": "CHANGE",
  "lawId": "LAW-...",
  "bindingId": "domain.binding-id",
  "evidenceModes": [],
  "decision": "REQUIRED",
  "reasonCode": "DELTA_INTERSECTION",
  "triggerRefs": []
}
```

`decision` 只允许 REQUIRED、NOT_REQUIRED；`reasonCode` 只允许 STATIC_ALWAYS、DELTA_INTERSECTION、META_GOVERNANCE_CHANGE、FULL_RELEASE、NO_RELEVANT_DELTA、RELEASE_ONLY_BINDING。

固定算法：

```txt
Static binding 在 CHANGE/RELEASE 均 REQUIRED；
RELEASE context 下全部 Exam/Dynamic binding REQUIRED；
CHANGE context 下 EVERY_RELEVANT_CHANGE 仅在 actual path/surface/spec/contract delta 与 law appliesTo、Owner paths、binding refs 或依赖闭包相交时 REQUIRED；
CHANGE context 下 RELEASE_CANDIDATE 为 NOT_REQUIRED；
source-spec/law amendment 与 existing migration 对三个 meta domain 视为 META_GOVERNANCE_CHANGE；
NOT_REQUIRED 不是 PASS，不产生 component receipt，也不得用于 SYSTEM_PROVEN。
```

### 56.3 component receipt

每个 REQUIRED binding 精确一个 component receipt：

```json
{
  "schemaVersion": 1,
  "candidateId": "...",
  "invocationMode": "TASK",
  "executionId": "...",
  "taskId": "...",
  "baseSha": null,
  "headSha": null,
  "verificationContext": "CHANGE",
  "lawId": "LAW-...",
  "capabilityDomain": "...",
  "component": "static",
  "bindingId": "domain.check-id",
  "evidenceModes": ["static.ast"],
  "outcome": "COMPONENT_PASS",
  "assertions": [],
  "findings": [],
  "targetSetHash": "...",
  "targetCount": 0,
  "cleanupOutcome": "NONE_REQUIRED"
}
```

component 只允许 static、exam、dynamic；outcome 只允许 COMPONENT_PASS、COMPONENT_FAIL；cleanupOutcome 只允许 NONE_REQUIRED、CLEANUP_PASS、CLEANUP_FAIL。Exam/Dynamic 追加运行参数 hash、真实 locator、case/attempt 与脱敏字段。不存在 SKIPPED_PASS、WARNING_PASS。

### 56.4 LawQualityReceipt

唯一 aggregator 为每个 active lawId 产生 context-bound receipt：

```json
{
  "schemaVersion": 3,
  "candidateId": "...",
  "invocationMode": "TASK",
  "executionId": "...",
  "taskId": "...",
  "baseSha": null,
  "headSha": null,
  "verificationContext": "CHANGE",
  "lawId": "LAW-...",
  "capabilityDomain": "...",
  "declaredEvidenceModes": [],
  "requirementDecisionRefs": [],
  "requiredBindingIds": [],
  "components": [],
  "findingCount": 0,
  "failureCodes": [],
  "outcome": "PASS"
}
```

outcome 只允许 PASS、FAIL，且脱离 `verificationContext` 引用 PASS 属于无效陈述。

每个 REQUIRED binding 必须有且只有一个 candidate/execution/context 一致的 COMPONENT_PASS；每个 required evidenceMode 必须被精确覆盖一次。缺失、重复、COMPONENT_FAIL、finding、candidate mismatch、execution identity mismatch、receipt hash 不符、cleanup fail 均 FAIL，并使用：

```txt
REQUIRED_EVIDENCE_MISSING
DUPLICATE_EVIDENCE_COVERAGE
COMPONENT_FAILED
CANDIDATE_MISMATCH
RECEIPT_EXECUTION_IDENTITY_MISMATCH
RECEIPT_INTEGRITY_FAILED
PROOF_CLEANUP_FAILED
```

Static/Exam/Dynamic runner 永远不得写 LawQualityReceipt 或最终 PASS。

## 57. 唯一 context-bound Owner report

每个 `(invocationMode, executionId, candidateId, capabilityDomain)` 必须有且只有一个 Owner report；不得把 TASK current cache 与 CI ephemeral report 当成两个并存 verdict：

```json
{
  "schemaVersion": 4,
  "candidateId": "...",
  "invocationMode": "TASK",
  "executionId": "...",
  "taskId": "...",
  "baseSha": null,
  "headSha": null,
  "verificationContext": "CHANGE",
  "capabilityDomain": "...",
  "lawQualityReceipts": [],
  "findingCount": 0,
  "verdict": "PASS",
  "systemProven": false
}
```

对 `executionDomainSet` 中的每个 domain，`lawQualityReceipts` 精确覆盖 manifest.allowedLawIds；任一 law FAIL、finding、缺 receipt 或 candidate/execution/context mismatch -> report FAIL。集合外 domain 不生成空 report 或伪 receipt。`systemProven=true` 只允许 `invocationMode=TASK`、RELEASE context 且全项目条件满足；CI_CANDIDATE 固定为 false。

`verdict` 只允许 `PASS`、`FAIL`；不得出现 `PARTIAL`、`WARNING`、`SKIPPED`、`READY`、`SYSTEM_PROVEN` 或任何自定义成功态。`systemProven` 是 RELEASE 全项目闭合属性，不是第三种 verdict。

只有 `aggregate-quality.ts` 可调用唯一 `report-writer.ts` 原子写 report；component runner 只写本次 execution evidence。`TASK` report 原子发布到 `scripts/audit/reports/<domain>.report.json` current cache；`CI_CANDIDATE` report 只发布到仓库外 `<executionRoot>/reports/<domain>.report.json`。两者 schema、identity 和 hash 算法完全相同，输出 sink 由 invocationMode 唯一决定。报告不作为下一次 evidence 输入。

## 58. Static 与 final quality 状态机

```txt
candidate capture
-> source/projection/ownership
-> one static index build/seal
-> all Static predicates
-> requirement decisions
-> required Exam/Dynamic components
-> candidate recheck
-> per-law context aggregate
-> per-owner temp reports
-> candidate recheck
-> invocation-bound atomic publish
-> TASK：更新 current report cache 后 task close 或 SYSTEM_PROVEN package
-> CI_CANDIDATE：仓库外写 invocation receipt 后结束。
```

任一漂移删除本次 execution root 的 receipts 和 temp reports；TASK 不更新 current report cache，CI_CANDIDATE 不产生 invocation receipt。

## 59. 三类证据不得互相冒充

```txt
Static Audit 证明静态结构；
Deterministic Exam 证明可重复确定性行为；
Dynamic Proof 证明真实外部运行。
```

不得用 AST 证明真实点击、fixture 证明 provider、截图证明全部算法、Dynamic 重定义 law、Exam 让 Static PASS，或建立第四证据 owner。

## 60. Exam registry、receipt 与 scope

存在 exam binding 时才建立 Exam 目录。literal declaration 精确声明 examId、lawId、evidenceModes、frequency、inputSetSha256、seed、timeoutMs；一个 examId 只绑定一个 lawId。

Exam component receipt 追加 inputSetSha256、seed、caseCount、failedCaseIds。失败非零退出，不写最终 report，不访问不需要的外部系统。

## 61. Dynamic Proof registry、凭证、安全与清理

proof declaration 精确声明 proofId、lawId、evidenceModes、frequency、credentialRefs、sideEffectClass、cleanupPolicy、maxAttempts、timeoutMs、retentionClass。

```txt
sideEffectClass：NONE | REVERSIBLE | IRREVERSIBLE_EXPLICIT_USER_ONLY；
cleanupPolicy：ALWAYS | NONE_REQUIRED；
retentionClass：REDACTED_LOCATORS_ONLY；
```

IRREVERSIBLE 必须有用户原文逐字授权。凭证只从 process environment、OS keychain 或受控 runtime secret provider 读取，不写 repo/receipt/截图/日志。动作使用 executionId/candidateId 派生 idempotency key；CI_CANDIDATE 不得执行 IRREVERSIBLE 动作。cleanup fail 即 component fail。禁止无限 retry/scroll/poll/search，禁止 fixture/mock/预制成功。

## 62. frequency 的唯一机器来源

frequency 只存在于 Manifest atomic exam/proof binding，并由 compiler 投影；只允许 EVERY_RELEVANT_CHANGE、RELEASE_CANDIDATE。blueprint 人读文本和 runner 不得建立第二频率。

## 63. 唯一质量总入口与两种证明边界

逻辑脚本名固定 `quality:check`。context 由第 56.1 节自动确定。顺序：

```txt
request/entry/task identity
-> scope check（写任务）
-> source integrity/history/ownership
-> projection check
-> freeze.projectChecks（按顺序、候选前后无非忽略写入）
-> Static components
-> requirement decisions
-> required governance mutants in isolated worktrees
-> required Exam components
-> required Dynamic components
-> candidate sentinel
-> LawQualityReceipts
-> Owner reports
-> TASK/CHANGE：task close
-> TASK/RELEASE：SYSTEM_PROVEN package
-> CI_CANDIDATE：只通过退出码与仓库外 ephemeral invocation receipt 结束，不写 candidate、source、projection、runtime 或 repo report cache，不关 task。
```

CHANGE context 全部 PASS 只允许关闭本次 task，表述为“本次变更已证明”；required mutant set 只覆盖本次改变的 law/inspector/governance closure。不得表述为整个系统发布就绪。RELEASE context 必须执行完整 mutant catalog。

`SYSTEM_PROVEN` 只在 RELEASE context 且以下全部成立时产生：

```txt
全部 active law 的全部 declared binding 都被 REQUIRED 且 PASS；
全部 Owner report PASS 且 systemProven=true；
全部 required mutants 以 expected failure code PASS；
旧治理/旧入口/兼容引用为零；
candidate 未漂移；
跨仓 change-set 全部 participant RELEASE receipt PASS。
```

quality 只通过一个 aggregator 和一个 report writer，不创建第二 verdict、READY、coverage verdict 或 release verdict。

## 64. CI 固定边界

CI 不是第二质量系统。仓库启用 CI 时只能有一个代码质量主工作流调用同一 `quality:check`，并满足：

```txt
普通 PR 校验使用只读 CI_CANDIDATE invocation；
CI_CANDIDATE 必须是 clean checkout，base/head commit 明确，actual delta 由 Git 计算；禁止任何 candidate、source、projection、governance runtime、Owner report cache 写入、task close 和 SYSTEM_PROVEN；唯一例外是 freeze.projectChecks 明确列出的 gitignored `allowedEphemeralWritePatterns`，且运行前后 candidateId 与 clean tracked/untracked state 必须一致；
CI_CANDIDATE 的 executionId = sha256("ci-candidate-v1\n" + repository + "\n" + baseSha + "\n" + headSha).slice(0,16)；
它运行 source integrity、projection、projectChecks、ownership、全量 Static、与 delta 相交的 EVERY_RELEVANT_CHANGE Exam/Proof 和 required mutants；
发布只能由人类授权的 release-proof task 或受保护的 manual release workflow 进入 RELEASE context；
任何自动 push/PR 事件不得自行提升为 RELEASE；
供应链 workflow 只可构建、发布或 attestation，不得写 LawQualityReceipt、Owner report 或第二 verdict；
CI 不得自动 audit:build 修复 stale projection。
```

同一 aggregator 必须在第 56.1 节仓库外 CI ephemeral execution root 产生一个非规范性 `ci-invocation-receipt.json`，精确结构为：

```json
{
  "schemaVersion": 1,
  "invocationMode": "CI_CANDIDATE",
  "executionId": "<16 lowercase hex>",
  "repository": "owner/name",
  "baseSha": "<40 lowercase hex>",
  "headSha": "<40 lowercase hex>",
  "candidateId": "<64 lowercase hex>",
  "lawQualityReceiptHashes": [],
  "ownerReportHashes": [],
  "mutantReceiptSetHash": "<64 lowercase hex>"
}
```

该 receipt 只绑定本次 CI 执行刚刚在同一 execution root 产生的逐 law/Owner receipts，不得引用历史或另一 execution；不包含 PASS、READY、coverage、release 或 systemProven 字段，不提交仓库，不取得第二 verdict 主权。最终成功或失败只认同一 `quality:check` 进程退出码。它不是 Task Envelope，也不覆盖交互式 scope 证明。跨仓协调器只收集两仓独立 TASK/RELEASE receipts，不建立第二 quality runner。

- 不得让 CI_CANDIDATE 写仓库内 report cache，或让 TASK 与 CI 共用一个可覆盖输出路径。
- 不得在任一参与仓、参与 domain 或跨仓合同未通过时关闭任务。

#### 证据

- static.ast
- exam.property

#### 违法后果

- P0：任一要求不成立、任一禁止条件出现或任一必需证据缺失，即产生 P0 finding；对应质量入口必须非零退出，并阻断合并、发布和用户交付。

只有以下全部成立，才允许宣布系统终态完成：

```txt
正文少而唯一；
法条细而独立；
要与不要完整；
Owner 精确唯一；
blueprint/spec/binding 全机器可读；
索引全而无主权；
Codex 有 request、baseline、初始闭包、route、scope；
修订与既有迁移无事务死锁；
Static/Exam/Dynamic 各守边界；
复合证据缺一必败；
所有 mutants 失败关闭；
旧法案、旧索引、旧 runner、旧 generated、兼容桥与第二链路为零；
两仓独立通过且跨仓合同 pin 一致；
freeze 生效；
普通 Codex 无法修改源头说明书。
```

最终运行公式：

```txt
人类请求原文
-> capture
-> entry + task transaction
-> baseline + complete initial closure
-> route + task context
-> 唯一实现施工
-> path/surface/ownership scope
-> projection
-> Static components
-> EvidenceRequirementDecisions
-> required governance mutants
-> required Exam components
-> required Dynamic components
-> final per-law aggregate
-> per-owner reports
-> participant receipts（跨仓时）
-> PASS | FAIL
```

本说明书的最终原则：

> **Codex 不是治理规则的共同设计者。Codex 只能读取已经冻结且机器闭合的边界，在被授权的精确范围内完成唯一实现，并用当前候选的全部真实证据证明。凡未被明示的扩张、深化、兼容、预留、影子规范和第二路径，一律禁止。**

## C.2 system record 元素 schema


```json
{
  "domainInventory": {"capabilityDomain":"...","manifestPath":"...","blueprintPath":"..."},
  "dependencyEdges": {"fromDomain":"consumer","toDomain":"provider","contractId":"provider.contract"},
  "crossDomainContracts": {"contractId":"...","providerDomain":"...","providerSpecRef":"...","consumerDomains":[]},
  "crossRepoContracts": {"contractId":"...","contractVersion":1,"providerRepo":"owner/name","providerSpecRef":"...","consumerRepos":[]},
  "surfaceExtractorBindings": {"pathPattern":"...","extractorId":"...","surfaceKinds":[]}
}
```

`crossRepoContracts.contractVersion` 必须等于对应 `providerSpecRef` 的 `cross-repo-contract.version`；`providerRepo + providerSpecRef + contractId + contractVersion` 是 topology identity。consumer 的 `contract-pin` 继续负责 commit 与 exact hash，SYSTEM-BLUEPRINT 不复制 pin 或 provider schema。

## C.3 三个 meta domain blueprint 的确定性 renderer

blank bootstrap 不允许 Codex 手写三份 machine record。唯一 renderer 按附录 B Manifest 与 C.1 system record 生成：

```txt
schemaVersion=2；status=active；blueprintId=`domain:<domain>`；capabilityDomain=owner=<domain>；
lawIds=Manifest.allowedLawIds；specRefs=Manifest.specRefs；
anchors=每个 lawId 一个 `{anchorId:"law.<lawId>",kind:"law",lawIds:[lawId]}`；
dependencyEdges=C.1 中 fromDomain 等于本 domain 的边；
providedContracts/consumedContracts=本节合同目录；
prohibitedDependencyEdges=本节反向边目录；
surfaceExtractorBindings=本节 extractor 目录；
所有数组按 canonical key 排序。
```

合同目录精确为：

| contractId | provider domain | provider spec | consumer domain/spec |
|---|---|---|---|
| `project-governance.authority-order` | `project-governance` | `project-governance.authority-order` | `law-system/law-system.single-compiler` |
| `project-governance.candidate-task` | `project-governance` | `project-governance.codex-scope` | `audit-system/audit-system.candidate-drift` |
| `law-system.enforcement-projection` | `law-system` | `law-system.single-compiler` | `audit-system/audit-system.consume-single-plan` |

prohibited dependency edge 精确为：

```txt
project-governance -> law-system
project-governance -> audit-system
law-system -> audit-system
```

这些边表示 lower-authority/provider 反向依赖 consumer，必须为零；audit-system 可以按 C.1 消费 law-system/project-governance，law-system 可以消费 project-governance。

surface extractor 目录精确为：

```json
[
  {
    "extractorId": "governance.package-json",
    "pathPattern": "package.json",
    "surfaceKinds": ["package-dependency", "package-script"]
  }
]
```

C.1 `surfaceExtractorBindings` 与 project-governance domain record 必须使用该精确记录；其它两个 meta domain 为空。
