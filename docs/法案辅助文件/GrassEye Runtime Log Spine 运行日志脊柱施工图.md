# GrassEye Runtime Log Spine 运行日志脊柱施工图

版本: v1.0  
状态: active  
施工阶段: Phase Five  

---

## 1. 为什么存在

GrassEye 是一个 AI 驱动的自动化执法系统。

**用户提供需求 → AI 根据画面 + 能力登记册，指挥系统完成任务 → 系统校验、注入、执行、留证。**

在这条链路上，调试能力是生死线：

- 没有 debug 日志，调试变成无底洞。
- 永远 DEBUG，生产运行变成负担。
- 要做到：调试时看到头发丝，调试成功后只看流程。

Runtime Log Spine = **全系统统一的结构化事件出口**。

它不是能力组，不是 Forensics，不是第二套 persistence，不是 debug 大系统。  
它只是一根**透明神经**：

```
平时告诉你流程走到哪；
出问题时告诉你每一步吃了什么、吐了什么、谁负责；
问题解决后，一键回到安静模式。
```

## 2. FLOW / DEBUG / TRACE 三档模式

### 2.1 模式定义

| 模式 | 触发方式 | 适用场景 |
|------|---------|---------|
| FLOW | 默认（无 env var） | 生产运行 |
| DEBUG | `GRASSEYE_LOG_MODE=DEBUG` | 日常调试 |
| TRACE | `GRASSEYE_LOG_MODE=TRACE` | 头发丝级排查 |

### 2.2 FLOW 模式（生产骨架）

只显示任务生命周期骨架：

```
MISSION_STARTED
ROUND_STARTED
SCREENSHOT_CAPTURED
AI_DECISION_SUMMARY
CAPABILITY_DISPATCH_STARTED / COMPLETED / FAILED
MISSION_STOPPED / COMPLETED / REVIEW_REQUIRED
ERROR
```

短、稳定、可读、不刷屏。

### 2.3 DEBUG 模式（日常调试）

在 FLOW 基础上额外显示：

```
HUMAN_COMMAND_RECEIVED / VALIDATED / REJECTED
SCREENSHOT_CAPTURE_REQUESTED
COORDINATE_GRID_RENDERED
AI_REQUEST_DEBUG
AI_RAW_RESPONSE_DEBUG
AI_PARSE_RESULT_DEBUG
AI_ERROR_DEBUG
GEOMETRY_GUARD_RESULT
BROWSER_ACTION_RESULT
TEXT_INPUT_RESULT
OPEN_RESULT
FORENSICS_RECORD_APPENDED
FORENSICS_ARTIFACT_APPENDED
```

终端只显示 refs/hash/preview，不刷巨大 payload。

### 2.4 TRACE 模式（头发丝模式）

所有事件全显示，额外包含：

```
full prompt refs / hash
full raw response refs / hash
schema validation details
duration breakdown
all owner boundaries
all input/output refs
```

可开可关，不能成为默认。

## 3. RuntimeLogEvent Schema

```typescript
type RuntimeLogEvent = {
  // Identity
  eventId: string;      // auto-generated by logger
  traceId: string;
  spanId?: string;
  parentSpanId?: string;

  // Classification
  level: "debug" | "info" | "warn" | "error";
  modeVisibility: Array<"FLOW" | "DEBUG" | "TRACE">;
  eventType: RuntimeLogEventType;  // from canonical enum only
  owner: RuntimeLogOwner;
  ownerResponsible?: RuntimeLogOwner;

  // Context links
  missionId?: string;
  runId?: string;
  sessionId?: string;
  roundId?: string;
  stepId?: string;
  capabilityCallId?: string;
  nerveBusEnvelopeId?: string;
  platformId?: string;
  abilityGroupId?: string;
  childCapabilityId?: string;

  // Result
  status?: "started" | "success" | "failed" | "review_required" | "skipped";
  reason?: string;
  actionableMessage?: string;

  // Proof attachments — no secrets, no base64 images
  refs?: Record<string, string>;
  metrics?: Record<string, number>;
  hashes?: Record<string, string>;
  preview?: Record<string, string>;
  payload?: Record<string, unknown>;

  // Timing
  createdAt: string;    // auto-generated by logger
  durationMs?: number;
};
```

## 4. AI 四件套

每次 AI 模型调用，必须按序 emit 四个事件：

### 4.1 AI_REQUEST_DEBUG（模型调用前）

必须在 `callLocalModel` 之前 emit。

必须包含：
- `promptHash`：prompt 完整内容的 SHA-256
- `promptPreview`：前 200 字符预览
- `modelName` / `runtimeName`
- `imagePaths` 或 `imageRefs`
- `promptLength`、`timeoutMs`
- `traceId`、`spanId`
- `missionId`（如有）

### 4.2 AI_RAW_RESPONSE_DEBUG（模型返回后，解析前）

必须在丢弃或解析原始回复之前 emit。

必须包含：
- `rawOutputHash`：原始回复的 SHA-256
- `rawResponsePreview`：前 220 字符预览
- `durationMs`
- `status`

### 4.3 AI_PARSE_RESULT_DEBUG（JSON/schema 解析后）

不论解析成功还是失败，都必须 emit。

必须包含：
- `schemaStatus`：`"valid"` | `"invalid"`
- `parserErrors`：错误数组
- `actionCount`：解析出的动作数（成功时）
- `schemaIssueCount`
- `durationMs`

### 4.4 AI_ERROR_DEBUG（AI failure 逃出前）

任何 AI 失败路径（throw 或 return failed/review_required）必须先 emit。

必须包含：
- `reason`：失败原因分类
- `actionableMessage`：可读错误描述
- `ownerResponsible`：谁负责
- `status`：`"failed"` | `"review_required"`

## 5. Terminal / File / Forensics 三层关系

### 5.1 Terminal Sink（实时观察）

- 只负责实时人类可读输出。
- FLOW：每行一摘要。
- DEBUG：摘要 + refs/hash/preview。
- TRACE：更多字段，但仍禁止 secret 和 base64。
- **Terminal 不是 truth。**

### 5.2 File Debug Bundle Sink（有据可查）

默认路径：
```
data/runtime-logs/<missionId>/<runId>.jsonl
```
或开发环境：
```
tmp/runtime-logs/<runId>.jsonl
```

要求：
- DEBUG/TRACE 完整 JSONL 保存。
- full prompt/raw response 可以作为 payload 保存（必须先 redaction）。
- 按 traceId 可回放。

### 5.3 Forensics Sink（长期取证）

日志系统不得直接成为 persistence owner。

如需长期保存，由 Orchestration 将日志 refs 交给 Forensics：
```
forensics-persistence.append-record(recordType="runtime_log")
```

日志系统本身不调用 Forensics 写路径。

## 6. Redaction 规则

### 6.1 禁止进入 terminal 或 bundle 明文

```
cookies
tokens
authorization headers
passwords
API keys
session cookies
base64 image content（任何 data:..;base64, 开头字符串）
```

### 6.2 允许进入

```
hash（SHA-256 等）
size / dimensions
artifactRef
file basename
redacted path
```

### 6.3 实现

`redactRuntimeLogPayload(payload)` 在 `src/lib/runtime-logs/redaction.ts` 中统一实现。

所有 file sink 写入前必须通过 redaction。

## 7. 各模块接入点

### 7.1 Local AI（src/lib/local-ai/call-local-model.ts）

接收 `runtimeLogger?: RuntimeLogger` 和 `traceContext?: TraceContext`。

在 `invokeOllama` 前 emit `AI_REQUEST_DEBUG`。  
在 `invokeOllama` 后 emit `AI_RAW_RESPONSE_DEBUG`。  
在 catch 前 emit `AI_ERROR_DEBUG`。

### 7.2 AI Ability（src/capabilities/ai/）

在 `callLocalVisualMissionModel` 前 emit `AI_REQUEST_DEBUG`（ai-capability owner）。  
在 parse 后 emit `AI_PARSE_RESULT_DEBUG`。  
在 catch 前 emit `AI_ERROR_DEBUG`。

### 7.3 Orchestration

在以下节点 emit FLOW 事件：
- MISSION_STARTED / MISSION_STOPPED / MISSION_COMPLETED / MISSION_REVIEW_REQUIRED
- ROUND_STARTED / ROUND_COMPLETED
- CAPABILITY_DISPATCH_STARTED / COMPLETED / FAILED

### 7.4 能力组边界

每个能力组入口至少 emit：
- CAPABILITY_DISPATCH_STARTED
- CAPABILITY_DISPATCH_COMPLETED 或 CAPABILITY_DISPATCH_FAILED

`runtimeLogger` 由上层（Orchestration）注入，不得在能力组内 import logger 全局单例。

## 8. 禁止 logger 越权

```
禁止：logger import forensics-persistence 私有写路径
禁止：logger import Orchestration mission state
禁止：logger 执行浏览器动作
禁止：logger 成为能力组
禁止：logger 成为 event bus 或 metrics 系统
禁止：logger 写业务数据
禁止：console.log 临时补丁留在能力组中
```

---

## 9. 禁止 console.log 临时补丁

```
console.log / console.error / console.warn / console.debug
```

只允许出现在：
- `src/lib/runtime-logs/sinks.ts`（terminal sink 实现）
- CLI entrypoint（必要输出）

能力组、runtime 模块、AI 模块中不得出现。

## 10. 代码结构

```
src/lib/runtime-logs/          ← <= 8 files
  index.ts                     Public API 出口
  schema.ts                    RuntimeLogEvent 类型
  event-types.ts               RuntimeLogEventType 枚举 + mode visibility sets
  mode.ts                      FLOW/DEBUG/TRACE 模式解析
  redaction.ts                 统一 redaction
  trace.ts                     createTraceContext / forkSpan / withRuntimeSpan
  sinks.ts                     terminal sink + file debug bundle sink
  logger.ts                    createRuntimeLogger / emitRuntimeLog

scripts/audit/domains/runtime-logging/   ← <= 3 files
  config.ts
  inspector.ts
  run-inspector.ts
```

Public API 只允许：
```typescript
createRuntimeLogger(config)
emitRuntimeLog(event)
createTraceContext(input)
withRuntimeSpan(input, fn)
redactRuntimeLogPayload(payload)
```
