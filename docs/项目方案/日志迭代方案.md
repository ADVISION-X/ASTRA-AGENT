## 1. 最终结论

本轮只建设一条窄的“checkpoint 序号冲突诊断事实链”：

```text
Website 在拒绝瞬间已有的判定事实
  -> 现役 ApiError.error.details
  -> AGENT V6 error envelope 严格解析
  -> TypedExecutionFailure 的瞬时只读诊断事实
  -> 唯一 Runtime Log Spine failure
  -> diagnoseRuntimeLog / logs:inspect / 本地 diagnosis API
```

只新增两个事实：

```text
expected_checkpoint_seq
submitted_checkpoint_seq
```

明确不新增：

- `current_checkpoint_seq`：当前规则下与 `expected_checkpoint_seq - 1` 重复；
- `checkpoint_stage`：已有 `operation=job.checkpoint` 与 `typedIdentity.checkpointId`；
- `action`、`next_retry_at`、`retryable`：它们属于 Runtime/Website 权威决策，不属于日志；
- task state、current_reason、attempt verdict、recovery decision；
- 新表、新列、新台账、新日志文件、新 logger、新总线或第二诊断报告。

这是一项纯诊断合同迭代，不改变状态机。

## 2. 当前事实与真实 GAP

### 2.1 日志现场

2026-08-29 20:46:42Z 至 21:03:02Z 的只读样本包含：

- 854 条结构化事件、约 645 KB；
- 628 条 `cloud.claim` 事件，占 73.5%；
- 425 条 `span.started` 与 425 条 `span.terminal`，二者合计占 99.5%；
- 72 条失败，其中 36 条是 `AI_V6_CHECKPOINT_SEQUENCE_INVALID` 阻断事件，另外 36 条是 `MATERIAL_DOWNLOAD_VERIFY_FAILED` / `JOB_EXECUTION_FAILED` 后果事件；
- 两个 job 各观察到 9 轮 `job.execute` 失败；样本末尾没有 `job.terminal`。

现有日志已经能确定：

```text
owner=production-runtime
component=production-checkpoint
operation=job.checkpoint
code=AI_V6_CHECKPOINT_SEQUENCE_INVALID
httpStatus=409
impact=BLOCKING
```

但无法从同一根故障直接得到 Website 期望序号与 AGENT 提交序号，因此只能定位片区，不能直接判断错位量。

### 2.2 Website 已经拥有判定事实

Website 当前在 `job-lifecycle-repository.ts` 中锁定 V6 lease/runtime 权威行后执行：

```text
submitted checkpoint_seq !== durable checkpoint_seq + 1
  -> HTTP 409 AI_V6_CHECKPOINT_SEQUENCE_INVALID
```

因此：

- `expected` 的唯一生产者是 Website `ai-acceptance`；
- `submitted` 来自当前已鉴权 checkpoint request；
- 两者均是拒绝瞬间已用于判定的整数事实；
- 构造错误详情不需要再次查询、预测、重放或改变数据库。

Website 现役 `ApiError` 和 `sendProblem` 已支持 `error.details`，无需新增第二响应 envelope。

### 2.3 AGENT 当前丢失详情的位置

AGENT 当前 `parseJsonEnvelope()`：

- 读取 `error.code` 与 `error.message`；
- 把 HTTP 状态写入 `TypedExecutionFailure`；
- 对 `error.details` 使用 passthrough 但不保留；
- `RuntimeFailure` 又只允许 `kind/code/responsibleOwner/impact/nativeCause/causedByEventId/httpStatus`。

因此 Website 即使返回序号详情，当前 AGENT 也会在进入 Runtime Log Spine 前丢弃。

### 2.4 当前人读入口

- 唯一 JSONL 是机器审计真源；事件哈希链、producerSeq 与 authority hash 必须保留。
- `writeTerminalSink()` 当前输出同一事件的完整 JSON，不是独立人读摘要。
- `npm run logs:inspect`、`diagnoseRuntimeLog()` 和 `/api/production-runtime/diagnosis` 是现役只读诊断入口。
- `GRASSEYE_LOG_MODE` 是当前有效的投影等级开关；样本命令中的 `GRASSEYE_STRUCTURED_LOG_STDOUT` 与 `GRASSEYE_STRUCTURED_LOG_LEVEL` 在当前代码中没有消费者，不能被当作现役控制合同。

本轮不顺手改终端噪音、轮询聚合或环境变量，避免把一个根因信息 GAP 扩大为日志系统重构。

## 4. 最终合同

### 4.1 Website 409 details

仅当 `error.code === AI_V6_CHECKPOINT_SEQUENCE_INVALID` 时，Website 返回：

```json
{
  "schema_version": "xuanxue-ai-checkpoint-sequence-diagnostic.v1",
  "expected_checkpoint_seq": 13,
  "submitted_checkpoint_seq": 11
}
```

约束：

- exact fields，`additionalProperties=false`；
- 两个序号均为大于等于 1 的安全整数；
- 两值不得相等；
- `expected_checkpoint_seq` 必须直接取拒绝事务中已锁定 row 的 `checkpoint_seq + 1`；
- `submitted_checkpoint_seq` 必须直接取当前已鉴权 request；
- 不返回 current_reason、attempt 状态、lease secret、fence、payload、路径或数据库行正文。

### 4.2 AGENT typed failure

`TypedExecutionFailure` 只增加一个闭合的瞬时事实：

```ts
checkpointSequence: null | Readonly<{
  expected: number;
  submitted: number;
}>
```

约束：

- 仅由 `parseJsonEnvelope()` 在精确 code + 精确 details schema 成功时构造；
- 该属性不进入 `SerializedExecutionFailure`，不进入本地 attempt failure，不改变 `current_reason`；
- details 缺失、额外、非整数或 schema/version 不符时，失败关闭为 `AI_V6_CHECKPOINT_SEQUENCE_DIAGNOSTIC_INVALID`，不得猜值或退回文本解析；
- 其它错误码继续不携带任意 details bag。

### 4.3 Runtime Log failure

现役 `RuntimeFailure` 增加一个闭合可选字段：

```ts
checkpointSequence?: Readonly<{
  expected: number;
  submitted: number;
}>
```

约束：

- 只允许出现在 `AI_V6_CHECKPOINT_SEQUENCE_INVALID`；
- 新生产路径出现该 code 时必须存在该字段；
- 其它 code 携带该字段必须 schema-invalid；
- 不允许 `details`、`context`、`metadata`、`payload` 或动态键值 bag；
- 两个整数参加 canonical hash，继续属于同一原始事件与同一 hash chain；
- 历史事件仍由同一个 V2 envelope parser 读取，不建立 V2/V3 双 reader。

### 4.4 版本决定

- JSON 事件 envelope 仍为 `schemaVersion: 2`，类型仍为 `RuntimeLogEventV2`；四种 kind、identity、span 与 hash 语义均未改变。
- 跨仓 provider/dependency 合同发布版本从 `runtime-log-event-v2@2` 升为 `runtime-log-event-v2@3`。
- AGENT provider spec 与 Website dependency spec 必须同时指向 `@3`；最终活动状态只允许一个版本。
- 不新增 `RuntimeLogEventV3`、alias、转换器、兼容 adapter、dual-read/write 或第二 logger。

选择“V2 envelope + @3 合同发布”的理由是：这次只是闭合 failure 的向后可读增量，不值得制造第二事件 envelope 和历史日志双解析链。

### 4.5 诊断结果

`DiagnosedFailure` 对 checkpoint root 暴露：

```json
{
  "code": "AI_V6_CHECKPOINT_SEQUENCE_INVALID",
  "responsibleOwner": "production-runtime",
  "operation": "job.checkpoint",
  "httpStatus": 409,
  "checkpointKind": "accepted",
  "checkpointSequence": {
    "expected": 13,
    "submitted": 11
  }
}
```

其中：

- `checkpointSequence` 来自根故障事件；
- `checkpointKind` 由同一 producer run、同一 spanId 的既有 `span.started.typedIdentity.checkpointId` 只读关联；
- 不从日志推演任务状态、下一动作或恢复结论；
- `logs:inspect` 与 `/api/production-runtime/diagnosis` 复用同一个 `RuntimeDiagnosis`，不另建报告真相。

## 8. 验收合同

### 8.1 正向验收

构造 Website durable `checkpoint_seq=12`、AGENT 提交 `checkpoint_seq=11`：

```text
HTTP status                     = 409
error.code                      = AI_V6_CHECKPOINT_SEQUENCE_INVALID
details.expected_checkpoint_seq = 13
details.submitted_checkpoint_seq = 11
Website durable checkpoint_seq  = 12（拒绝前后不变）
```

AGENT 必须形成一个根故障事件：

```text
operation                       = job.checkpoint
impact                          = BLOCKING
httpStatus                      = 409
checkpointSequence.expected     = 13
checkpointSequence.submitted    = 11
```

`MATERIAL_DOWNLOAD_VERIFY_FAILED` 与 `JOB_EXECUTION_FAILED` 继续通过 `causedByEventId` 作为 consequential failure，不复制 checkpointSequence。

### 8.2 负向验收

以下必须失败关闭：

- Website details 缺失 schema_version；
- expected/submitted 非整数、小于 1 或相等；
- details 有额外字段；
- 其它 error code 携带 checkpointSequence；
- AGENT 通过 message 正则提取数字；
- checkpointSequence 进入 `SerializedExecutionFailure`、current_reason 或数据库；
- 日志产生 retryable、action、next_retry_at、state 或 recovery 字段；
- Website consumer adapter 与 AGENT provider 版本不一致仍判合同通过；
- 新旧 Runtime Log adapter、alias 或 fallback 同时活动。

### 8.3 不变性验收

必须证明本轮前后以下结果完全相同：

- 合法 checkpoint 的接纳、hash 与 checkpoint_seq 推进；
- 非法 checkpoint 的 HTTP 状态、error code、事务 rollback 与 durable row；
- attempt_failure 冻结内容；
- claim、lease、attempt、Outbox、terminal 与 business admission 状态机；
- producerSeq、previousEventHash、eventHash 与 span 原子性；
- 无新数据库对象、无新日志文件、无第二诊断报告。

### 8.4 人工验收

操作者只看 `blockingRoots` 即可回答：

1. 哪个 job/attempt 失败；
2. 哪个 checkpoint kind 失败；
3. Website 期望多少；
4. AGENT 提交多少；
5. 根 Owner、HTTP 状态与后果链是什么。

日志仍不回答“系统接下来应该做什么”；该问题必须读取 Website 当前任务记录与 Runtime 权威。
