# 浏览器交互拒绝回执与认证连坐根治－完整实现方案

状态：可施工（2026-10-22 已获明确授权；建设、原生质量与业务完成分别取证）。日期：2026-10-22（Asia/Dubai）。需求 Owner：AGENT / local-browser-session。

## 1. 需求、授权、终点与非目标

本轮针对两次已确诊事故：单工单交互资格未通过，Extension 已证明零 Provider 输入，但正常 REPLY 被 Node 判为 `BROWSER_AUTH_TRANSCRIPT_INVALID`，撤销共享 authority，继而使其它等待工单失败。穿透下游后，另在真实原 Worker/Node 的受控交错中证明：即使失败 REPLY 合法，REPLY 后仍有异步 Target 退休时，后续 park COMMAND 也能因原 handler 未退出而再次撤权。后一分支是当前代码可复现的相邻缺陷，不冒称已由两笔现场日志证明发生。目标是让拒绝经原认证失败回复结算，并使回执发布成为原命令异步工作的末端；同连接中其它获授权工单继续沿唯一 FIFO/lane 推进。

用户已明确授权按本方案在主仓库 main 修改法案、施工图、代码、质检及必要数据库对象，并执行冻结 CI-FULL 默认链；禁止分支、兼容桥及第二链路。仅实施下列有限片区；本轮不需改变 active law、生产数据库、服务或 Chrome，不从该授权外推 RELEASE 或生产操作。

验收终点分开取得：技术上同一 authority 内拒绝回执经唯一 WAL commit/readback→ACK→原调用 typed failed，兄弟工单不因它失去 authority；业务上原失败事实经现役 Runtime 上报，恢复仍只消费 Website 当前授权，兄弟工单和获准恢复工单的结果沿原 Outbox 取得同 identity 的网站 completed/admission 回执并回读本地 completed。方案完成、隔离复现、CHANGE、READY 与真实业务完成分别报告。

本轮不处理八字 `BROWSER_DOCUMENT_INVALID` 的回答读取问题；不猜测两次事故最初是 loading、discarded、activation generation 还是其它 Tab 条件未通过。该细分事实缺席不影响已由原回执 hash 证明的本轮断裂。不得为此增加 Tab 状态持久化、DOM 采样器或诊断协议。也不删除旧工单、不重放旧 DISPATCHED、不改 N、重连策略、心跳或输入保护节拍。

四维结论：法案已经允许并要求 typed零输入拒绝、真实串行与不连坐；Blueprint需明确失败表示并替换已证不充分的发送/退休顺序；实现重建P1拒绝传播及P5末端发布两片区；质检删除掩盖格式缺口的用例与错误顺序规则，并穿过P12验真实推进。Website跨仓surface、Product Prompt/材料/流程、GPT Child、Provider页面选择器、Runtime恢复状态及Forensics均不改。停止边界依据是P11已有类型/身份/状态输入不变且其分类按effect事实而非新增code，最终结果/Outbox输入不变；P12无新语义，仅必须证明原lane继续。不能以不同Owner作为排除理由。

## 4. 删除审判后的唯一设计与 handoff

### 4.1 目标链

P1在调用ensure前继续assertInput；ensure失败直接抛原错误，不生成“成功返回值里的失败”。物理执行期catch仍必须先await原读回barrier，再给同一异常附原ProviderInputState的started/physicalInputCount后抛出；零输入失败和已开始/部分输入不能混写。删除`interactionRejectedReceipt`及executeMutation两处消费路径；保留`interactionFailure`、native-cause提取及整个ensure/capture/assert执行逻辑。无需新增Error类、失败classifier、字段、enum、接口或包装层。

`executeExtensionCommandReply`已有catch/`mutationExceptionReceipt`就是唯一失败生产者：前置交互拒绝 code=`BROWSER_TARGET_NOT_INTERACTIVE`、native cause取原闭集、terminal=rejected、outcome=no、count=0，wire必须为errorCode而无result，resultHash对canonical `{errorCode}`计算；mutationReceipt与diagnostic的主码相同。输入可能开始时仍保留dispatched/已知count，不能为了no而覆盖state。此方法、Node parser与verifier本轮均无需修改实现。

普通已完成预检的成功、DOM资格拒绝、zero-action、postcondition拒绝与限流special回执仍消费真实preflight；本轮不把它们统一改成exception。Observation与lifecycle保持各自现役语义，不向它们附mutationReceipt，不借交互拒绝加入第三业务门。

P5的唯一发布合同：原slot.fact必须先固定；原DIAGNOSTIC仍只有一个发送点，置于原try。外finally内以try等待原`retireInvalidCommandTarget(reply.body, permit, intentKind)`，其内finally无条件等待同一`sendEncrypted(socket, "REPLY", reply.body)`，这是整个executeCommand最后一项异步工作。诊断或退休抛错仍尝试原REPLY；不改原body/fact，不因清理错误伪造新terminal。成功发送后原Promise完成、原pending集合退休自身，后续网络message turn才可接受park/下一命令；须经原onMessage/receiveTail实证，不以Promise概念推测代替。原flush仍只在handler删除后按原slot/ACK条件执行，不新增REPLY后的cleanup。不提前删除pending、不等自身或ACK、不加入新完成帧/旗标/队列/timer。若真实通道/退休异常仍使handler失败，沿原关闭/drain，不承诺真实故障不断连；原槽补交职责保持。退休只复用原hash、exact identity与既有page-read barrier；不引入native新等待、handler drain或ACK等待，不能以finally为无限等待的可达性证明。
