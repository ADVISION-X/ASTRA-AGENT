### 5.T exact-turn 虚拟化
- **第一直接断裂**：页内函数（`dom-exact-assistant-turn.ts:41-50`）在精确 turn 未挂载时只返回 `exact-user-turn-unavailable`，而法条禁止 poll 时滚动（`功能法案.md:734`、`:783`、`:1017` 的 "自动搜索/滚动/展开"；GPT 施工图 :71、Browser 施工图 :41）。一旦 turn 被虚拟化，就会一直 pending。07a24 耗时 1906 s，最后靠人工滚动才恢复。同链翻译在同一个 chat 中持续续写，会话越来越长，放大了这个问题。
- **裁决**：
  1. **触发条件**：扩展侧先执行一次现役页内读取（`EXACT_ASSISTANT_TURN_FUNCTION` 不变）。只有返回 `pendingCause="exact-user-turn-unavailable"` 且原始计数为 0 时，才进入物化。
  2. **编排位置与硬截止**：遍历由**扩展侧**的 `executeExactAssistantTurnRead`（`dom-exact-assistant-turn.ts:186`）编排。
     - 每一步是一次短的同步 `Runtime.callFunctionOn`（`awaitPromise:false`）：写一次 `scrollTop`，并返回精确 testid 的计数、当前 `scrollTop` 与 `document.visibilityState`。页面内不使用任何计时器或 rAF。
     - **可见性限制**：Chromium 在渲染更新阶段派发滚动事件与 IntersectionObserver 回调，hidden 文档不执行渲染更新，虚拟列表不会因程序化滚动而挂载。因此任一步返回 `visibilityState !== "visible"` 时，立即停止物化，按现役返回 unavailable。这种情况下 T 退化为现役行为，不造成损害。T 的动态验收以 job 窗口未最小化、未被完全遮挡为前提（Browser 在每次 observation 前已激活精确 Tab）。
     - 步间等待由扩展侧 `setTimeout(400)` 完成，截止判断也由扩展侧时钟完成。页面被遮挡或计时器被节流都不影响截止。
     - 预算 `B = min(12_000, commandDeadlineAt − Date.now() − 3_000)`。`B < 4_000` 时不进入物化。每一步之前都重新检查 `Date.now() + 400 + 500 < 截止`，不满足即停止。因此命令必然在帧 deadline 之前回执，不会触发 `browser-authority-websocket.ts:176-180` 的撤销。
     - `commandDeadlineAt` 取扩展已校验的帧 deadline（`websocket-actor.ts:334`），沿 `extension-target-authority.ts:251-305`（`executeRegisteredCommand` → `executeRegisteredCommandCycle` → `executeRegisteredDomIntent`）→ `dom-intent-runtime.ts:320-324` 传入。这些都是扩展内部参数，**不改变 node→扩展的 intent 线协议**（`browser-dom-intent.ts`、`browser-dom-read-intent.ts` 不改）。
  3. **容器**：由第一步的页内调用确定，取已渲染 `[data-testid^='conversation-turn-']` 的最近公共祖先链中，第一个满足 computed `overflow-y ∈ {auto, scroll}` 且 `scrollHeight > clientHeight` 的元素；不存在则停止物化。后续每一步都重新按同一规则定位，不跨调用持有节点引用。
  4. **遍历**：第一步设 `scrollTop = scrollHeight`；之后每步设 `scrollTop = max(0, 当前值 − 0.8 × clientHeight)`。直到某一步返回精确 testid 计数 ≥1，或 `scrollTop = 0`，或到达 48 步，或预算耗尽为止。命中后再执行一次现役页内读取，得到最终结果。
  5. **命中后**：按现役代码原样取 `userRaw`、紧邻 assistant、`generatingRaw`，并做 URL 校验。**身份判据完全不变**：精确 `userTurnId` 唯一，紧邻且唯一的 assistant。
  6. **动作边界**：只经 `Runtime.callFunctionOn` 写页面 `scrollTop` 属性，零 CDP 输入事件、零点击、零导航、零搜索、零展开、零 WAL 行。每个 job 独占 Target，滚动不影响其它 job。
  7. **法条关系**：
     - 本改动不增删 `checkpoint_gpt_text_response` 的判据，不改身份构成，也不以 viewport 作为候选存在的判据（viewport 只是读取手段）。因此不属于 `FROZEN-GPT-TEXT-RESPONSE-TWO-GATES-001` 的改变范围。
     - 但 `:734`、`:783`、`:1017` 明文禁止"滚动"，需按 §7 G-T 修改（其中两条为冻结条款，须有解冻原文）。

### 5.S lease renew 瞬时失败
- **第一直接断裂**：`runtime-execution-heartbeat.ts:94-102` 在 renew 第一次失败时立即 `abort`。当时 Website 签发的 90 s lease 还剩约 70 s，而 V6 的"20 s 续租 + 90 s TTL"本身就是为容忍丢失续租而设计的。
- **独立断裂**：`worker-session.ts:198`、`:214-235` 与 `cloud-client.ts:156` 在解析失败时不带类型，于是非 JSON 的 5xx 被回退码 `LEASE_RENEW_FAILED` 覆盖。这违反 `功能法案.md:1185`："Browser、GPT 与跨仓 HTTP 外层不得用通用 code 覆盖内层原生 reason"。
- **裁决**：
  1. **S2**：两个 `request` 路径和回执解析的失败，统一经同一个私有 helper 转为 `runtimeTransportFailure("AI_PRODUCTION_HTTP_ENVELOPE_INVALID", status, cause)`。已是类型化的失败原样抛出。
  2. **S3 分类**：独立的纯函数 `renewFailureRetryable(error): boolean`，与循环同文件。
     - 以下情况为 **true**：`httpStatus >= 500`；`CLOUD_TRANSPORT_UNAVAILABLE`；`AI_PRODUCTION_HTTP_ENVELOPE_INVALID` 且 status ≥ 500。
     - 其余都为 **false**，维持现役 abort。包括所有 4xx，以及 2xx 回执 schema 失败。
  3. **S3 循环结构**：
     - 循环顶部的 20 s 等待只负责"下一次例行续租"。
     - renew 失败且可重试时，进入**同一次迭代内**的有界重试：`wait(5_000, abort.signal)` 之后先检查 `abort.signal.aborted`（`wait` 在 abort 时会立即返回，见 `runtime-state.ts:38-44`）：已 abort 就按现役结算、不再续租；否则立即再次 renew，不回到顶部。
     - 每次重试前检查 `left = budget.expires_at_monotonic − performance.now()`，要求 `left ≥ 8_000`。
     - 重试请求的 `signal = AbortSignal.any([abort.signal, AbortSignal.timeout(min(30_000, left − 5_500))])`，为此给 `renewProductionLease` 增加可选 `signal` 参数，透传给 `session.request`。
     - 不满足条件时按现役 abort，cause 取最后一次失败。
     - 由于 `expires_at_monotonic` 的现役定义就是 "TTL − 10 s"，本地永远不会越过 Website lease。
  4. **幂等性**：每次重试使用新 `request_id`。Website renew 不改 `lease_version` 与 fence（`job-lifecycle-repository.ts:185-217`），只延长同一 lease，不构成新 attempt 或续跑。需按 §7 G-S 写入法条。
  5. **日志**：每次失败的 renew 各写一个 failed span，code 为类型化 code，有响应时带 httpStatus。
