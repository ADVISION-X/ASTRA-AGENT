## 4. 逐项第一直接断裂与裁决

### 4.1 问题 1：PK `40001`

**现役链路**：

- `business-result-consumer.ts` 的 `commitOneWebsiteAgentBusinessResult` 把整条 PK admission 放进同一个 `withCommercialTransaction` 执行，包括 `consumePublicKnowledgeWithClient` 和 `completePublicKnowledgeRunWithClient`。
- `postgres.ts:34-58` 以 `begin isolation level serializable` 开启事务，最多尝试 6 次，退避上限约 430ms。
- 6 次都失败后，`recordConsumptionFailure` 写入 `retry_not_before=now()+5s`。

**第一直接断裂**：admission 事务内有两处写入，会与 Worker 的并发提交撞在同一行上。

- **① 控制单例**
  - `scheduler-repository.ts:382` 调用 `settlePublicKnowledgeControlState`，更新 `public_knowledge_control_state` 单例。
  - Worker 每轮首先执行 `heartbeatPublicKnowledgeWorker`（`:387-410`），用普通 client 自动提交，更新同一行。
- **② 同一 batch 行**
  - admission 内的 `settleCompletedBatch`（`run-completion-helpers.ts:44-62`）更新 `public_knowledge_daily_batches` 的对应行。
  - Worker 的 claim 事务 `createRunForNextBatch`（`scheduler-repository.ts:101-106`）每建一个 run，都会无条件更新该 batch 行的 `status/started_at/updated_at`。

只要并发提交发生在 admission 快照之后，admission 更新该行时必然得到 `40001`（并发更新）。admission 本身持续数十秒，而心跳每 5 秒加上一轮周期就执行一次，所以 6 次尝试会反复重跑整条长事务，又反复被撞。

**现役权威**：

- Website `AI-ACCEPTANCE-BLUEPRINT.md:155`：PK loop 的单行 CAS 不进入 SERIALIZABLE 事务，并且"serialization conflict 不得成为文章失败"。
- 控制单例的结算、batch 的 running 标记，都没有权威要求与 admission 同事务。

**同一施工面必须一并闭合的潜在缺陷**：`settlePublicKnowledgeControlState` 的 CASE 不保留 `emergency_stopped`。`emergencyStopPublicKnowledge` 会把所有 running 工单改成 paused，因此任一 admission 完成都会把紧急停机改写为 `pause_requested` 或 `paused`。如果把结算原样搬进心跳，这个改写会在 5 秒内发生。

**裁决**：

- **W-PK1**：admission 事务不再写控制单例。结算改由 Worker 心跳用一条带守卫的单行语句执行：
  - 只在 `status in ('running','pause_requested')` 时执行，因此不会改写 `emergency_stopped`；
  - 只在结算值变化时 `version+1`；
  - 操作员设置的 `paused` 与 `emergency_stopped` 保持不变。
- **W-PK1b**：`createRunForNextBatch` 的 batch 更新只在 `status<>'running'` 时执行，也就是只写首次转为 running 的那一次。batch 进入 running 后，Worker 不再写该行。
- **残留冲突**：两个 SERIALIZABLE 事务之间仍可能出现真实的 SSI rw 冲突（§6 P2）；batch 行另有操作员动作写者 `control-repository.ts:196`（run 动作只写 blocked 行）与 `work-order-deletion-repository.ts:135,225`（删除），均为短事务，同归 P2。这类冲突由现役 6 次尝试吸收，不会成为 consumer 级失败。
- **删除**：
  - consumer 外层重试加抖动：冲突源已移除，它没有消费者。
  - 独立心跳表：同行写冲突已解决，不再需要。
  - 修改隔离级别：会改变全仓合同。

### 4.3 问题 3：2839 附件与 IR-78

**事实**：2839 两次失败时，composer 中卡片 4/4、上传全部完成、pending 为 0，所以只能是名称不匹配。

**第一直接断裂**：`reconcile_gpt_attachment_set/observation.ts:209-217` 的 `attachmentSettlementTimeout` 在终态裁决时只把计数行写进失败码后缀，`attachmentSetDifference` 算出的 missing、unexpected、归一化重名三类事实被丢弃。

这导致一个违反冻结 `(n)` 语义的真实原因无法被读回。可能的原因包括：

- 带空格的 `" (n)"`；
- Provider 截断或改名；
- 扩展名变化。

2839 是 continuation 会话，同一 job 在 rev0/rev1 已上传过同名文件，Provider 重名改写的可能性高，但本方案不据此猜测。

**裁决**：

- **W-ATT1**：`attachmentSettlementTimeout` 判定 MISMATCH 时，在现役失败码后缀追加一段封闭形态诊断：

  ```text
  :labels=missing:<n>,unexpected:<n>,dup:<n>,shape:<CODE>[,<CODE>…]
  ```

  每个 unexpected 标签相对批准集合归入下列五类之一。只输出码，不输出任何标签文本。

  | 形态码 | 判定条件 |
  |---|---|
  | `SPACE_PAREN_DIGITS` | 等于 `批准 stem + " (" + 数字 + ")" + ext` |
  | `TOKEN_ABSENT` | 等于该文件未加业务 token 的 `displayName` |
  | `EXT_CHANGED` | stem 相同、扩展名不同 |
  | `PREFIX_OF_APPROVED` | 是某个批准名的真前缀，即被截断 |
  | `UNRELATED` | 以上都不符合 |

  判定顺序固定为表中自上而下；对每个 unexpected 标签，按批准文件的现役顺序逐一比较，取第一个命中的码。已知局限：Provider 截断名称时若插入省略号，`PREFIX_OF_APPROVED` 不命中而归入 `UNRELATED`，本方案不猜测省略号形式。

  这段后缀沿现役通道持久化：`attempt_failure_json`，以及 Website 的 `attempt_failure.code`。Website 对 code 只要求非空字符串（`v6-write-assertions.ts:92`）。
- **W-ATT3（2839 处置，属于生产写，需要授权人当次批准）**：W-ATT1 部署后，读回 2839 的下一次失败码。授权人按读回的形态码二选一：

### 4.4 问题 4：DOM 候选缺失不可诊断

**第一直接断裂**：`dom-coherent-candidate.ts` 中的两个页内函数，`COHERENT_CANDIDATE_FUNCTION`（`:42-80`，供指针、fill、keypress 与限流确认使用）和 `COHERENT_OBSERVATION_POINTER_FUNCTION`（`:136-`），对下列情况一律返回 `BROWSER_DOM_CANDIDATE_MISSING`：

- scope 原始数为 0；
- scope 全部不合格；
- 目标原始数为 0；
- 目标全部不合格。

随后，node 侧有 5 处转换点：

- `dom-intent-runtime.ts:97-110`；
- `dom-pointer-intent-runtime.ts:88-97`、`:136-137`、`:160-161`、`:184-185`。

它们调用 `qualificationReceipt(0, code, "candidate-set")` 时把 `nativeCauseCode` 固定为 null。`browser-mutation-receipt.ts:288-305` 在 candidate-set 阶段也只接受 null。

**范围**：只处理这两个页内函数的生产者。已穷尽的 `executeClickIntent/Hover/DoubleClick/Keypress/Fill` 调用方为：dom-intent 的 click/hover/doubleClick/fill/keypress（`dom-intent-runtime.ts:326-329` 等）、限流确认 `acknowledgeKnownGptRateLimit`（`gpt-rate-limit-dialog.ts:227` 直接返回 `executeClickIntent` 回执）、rename（`gpt-conversation-rename-runtime.ts:114-135`，走自有 decoder）。keypress 经 `dom-pointer-intent-runtime.ts:101-113` 的 `mutationCandidate` 调用 `resolveCoherentMutationCandidate`，同样走 `COHERENT_CANDIDATE_FUNCTION`；其转换点是 `:88-97` 的 `qualifiedNode`（唯一调用方 `executeKeypressIntent` `:407`），WAL 中已有 `ensure_gpt_reasoning_requirement / browser.dom.keypress.v1` 的 MISSING 行。4e0d 与 cf6d 的 `open_gpt_model_selector_v2` 属于 click。

- rename（`gpt-conversation-rename-runtime.ts` + `decodeConversationRenameReceipt`）不在范围内。
- file-input（`extension-file-input-runtime.ts`）不在范围内。

以上路径的回执格式都不变，decoder 规则也按 command kind 限定，不会误伤它们。

**裁决**：

1. **W-DOM1**：新增独立文件 `src/lib/browser/chrome-extension/dom-candidate-missing-stage.ts`，导出只依赖计数的纯分类源码片段 `CANDIDATE_MISSING_STAGE_SOURCE`，输入为 `scopeRaw, scopeEligible, raw, eligible`，组织方式与现役 `dom-mechanical-facts.ts` 导出 `BROWSER_MECHANICAL_FACTS_READER_SOURCE` 相同，由两个页内函数内插使用。放在独立文件是为了给 `dom-coherent-candidate.ts`（464 行）留出红线余量。它输出 4 个码之一：

   | 阶段码 | 条件 |
   |---|---|
   | `BROWSER_DOM_SCOPE_ABSENT` | `scopeRaw=0` |
   | `BROWSER_DOM_SCOPE_INELIGIBLE` | `scopeRaw>0` 且 `scopeEligible=0` |
   | `BROWSER_DOM_SELECTOR_ABSENT` | scope 唯一且 `raw=0` |

### 4.5 问题 5：cause token 丢失

**第一直接断裂**：

- `browser-target-lease-manager.ts:204-211` 的 catch 调用 `browserExecutionFailure(error, …)`，而它的实现（`browser-failure.ts:45-61`）不保留 token：
  - 链上已有 `BrowserExecutionFailure` 或 `TypedExecutionFailure` 时，返回内层对象，或以内层的 `.cause` 重建。带 token 的外层 Error 整个被丢弃，限流 typed 失败（`browser-command-actor.ts:225,391`）就是这种情况。
  - 内层是普通 Error 时，新对象的 `.cause` 是原错误，token 落在 `.cause` 上。4e0d、cf6d 与 rename 都是这种情况。
- 这两种情况下，`failure.ts:96-100` 的 `runtimeLogCauseEventId` 只读顶层，所以 `ability-group.ts:355`、`production-child-tools.ts:342` 都判为 BLOCKING。
- 《十小时》方案 IR-76 的验收用 `fakeBrowser` 夹具绕开了 lease-manager，所以验收通过而生产失败。

**裁决（W-LOG1）**，两处修改缺一不可：

1. `runtimeLogCauseEventId` 沿 `.cause` 链返回最近的 token，带 seen 集合防环。它覆盖所有"以 cause 包装"的层，比如 handler 中的 `executionFailure(…, {cause})`。
2. `browserExecutionFailure` 在返回或重建对象前，先对入参取 `runtimeLogCauseEventId(error)`；返回对象上没有 token 时，就把它挂上。这覆盖"丢弃外层"的分支。

这就是 Runtime Log 施工图第 78 行规定的"不得在跨层转换中丢弃 cause"。

### 4.6 问题 6：rename 清理（授权人裁定暂缓）
