## 0. 终态裁决

本轮只保留一条 canonical 产品链：

甲方：BZ01 -> 现役 BZ02 确定性伴读材料 -> 正式 BZ05  
乙方：BZ01 -> 现役 BZ02 确定性伴读材料 -> 正式 BZ05  
两份 exact BZ05 均完成并与 HH01 双方 exact BZ01 一一匹配  
-> HH02 一次 fresh Provider chat，只做双方关系综合  
-> HH03 每一次追问都是新的 Website Job + fresh Provider chat  
-> Website 用已经入库的根报告、既往追问问答、双方 BZ01/BZ05 与当前问题重新组装 locked-fact context。

终态原则：

1. BZ05 看人，HH02 看关系，HH03 回答关系上的后续问题。
2. 业务连续，Provider 无状态。
3. 上下文不依赖聊天记忆，全部由 Website 持久事实和 exact material package 重建。
4. HH02 不重新做两遍完整 BZ05，不创建 private base，不创建 A/B Hehun 私解产品，不创建第三 Plugin，不创建第二恢复状态机。
5. BZ05 是现役正式产品，不允许合婚内部伪造、复制、影子执行或绕过商业完成门。缺 BZ05 就先完成现役 BZ05。
6. BZ02 不从 BZ05 内部机械来源链删除。用户心智可理解为 BZ01 -> BZ05，但现役 BZ05 仍消费 BZ02 renderer semantic manifest/source PDF，且不增加 AI turn。
7. 不生产婚配分、匹配率、固定关系等级或宿命式确定性婚姻 verdict。
8. 本方案不改变八字已冻结 L0/L1/L2 边界，不改变 BZ05 Skill，不改变 BZ05 Flow，不改变 GPT/Browser/Runtime 核心。

### 2.2 法案是否修改

结论：本轮不修改 active law source。

理由不是“怕改”，而是主权边界正确：

- “HH02 必须消费两份正式 BZ05”属于现役产品 prerequisite / material contract，不应硬编码成根法条。
- LAW-HEHUN-001 中“两个角色的分析步骤”在终态仅指 HH02 当前 relationship synthesis 内的 A/B 对照，不要求 HH02 再承担完整单方 BZ05。
- LAW-HEHUN-005 本身没有限定 parent 必须只能是 HH02；当前“一层追问”是实现/商业 prerequisite 限制，不是法条要求。
- 修改功能法案去写具体 BZ05 product id，会把产品拓扑塞进长期 law，扩大耦合，与法案系统冻结说明书“法律只保存长期必须/禁止、产品合同负责具体业务结构”的分工冲突。

因此“法案系统须精确迭代”的本轮结果是：逐法确认无需语义 amendment，但现役 Hehun Static/Exam/Dynamic 证据必须重建，使法条真正证明新终态，不能继续弱证据 PASS。

## 5. 唯一新实现链

### 5.1 甲乙 BZ05 前置

现役 BZ05 完全复用，不进入合婚施工片区。

用户先有两份 BZ01。每方通过现役 BZ02 -> BZ05 正常链取得正式 BZ05。合婚不绕过：

- BZ02 source PDF binding；
- BZ05 SubjectBundle；
- BZ05 entitlement；
- BZ05 fresh Provider turn；
- BZ05 canonical report；
- BZ05 HTML/PDF/JSON；
- BZ05 Delivery Manifest；
- BZ05 business completion。

这是终态最重要的减法：复用完整 BZ05，而不是复制 BZ05。

### 5.2 HH01

HH01 继续只负责：

- 双方 role；
- 两张 exact BZ01；
- 两份 consent；
- 双人案卷。

HH01 不接 AI，不保存 BZ05，不生成关系结论。

### 5.3 HH02 SubjectBundle

购买 HH02 时提交：

- HH01 Delivery Manifest；
- 两份用户已经拥有的 BZ05 Delivery Manifest；
- 当前关系问题；
- HH01 intake identity。

Website prerequisite resolver 先按 product contract 证明“1 HH01 + 2 BZ05”，再根据 BZ05 的 upstream Bazi resource / formal report lineage 把两个 BZ05 自动映射回 male/female。

SubjectBundle 持久化 derived role binding，并把该 binding 放入 bundle_hash。之后任何 worker 都只读 frozen binding，不重新选 latest BZ05。

### 5.4 HH02 TaskBundle

HehunAnalysisService 必须取得：

- party_a_chart / party_b_chart：原 BZ01 locked resource；
- party_a_bz05 / party_b_bz05：exact canonical BZ05 structured report；
- BZ05 report lineage/hash；
- 双 consent；
- relation question；
- Hehun full READY corpus；
- base questions。

TaskBundle 的职责：

- BZ01 是事实锚；
- BZ05 是单方成熟解释材料；
- Hehun READY corpus 是关系综合的直接原典材料；
- HH02 AI 只负责关系综合，不重算 BZ01，不再做完整单方全盘解读。

### 5.5 HH02 Skill

HH02 Skill 的必经分析关卡：

1. 先核 A/B BZ05 与 A/B BZ01 identity 一致。
2. 分别提取两份 BZ05 的稳定主线、候选分叉、支持、反证、未知边界。
3. 不复写两份全盘报告，只抽取与当前关系问题有关的交叉变量。
4. 分析互动结构、互补、冲突、放大、抵消、时序、条件和现实边界。
5. 对候选组合先提取跨组合稳定关系结论，再写真实分叉与翻转条件。
6. 逐项回答 frozen base question + special question。
7. 引用只使用现役允许的 chart_fact、classical_text、user_input 等基础来源；BZ05 report 作为解释材料进入 evidence_refs/内部依据，不创建第二 citation schema。
8. 专业层和普通层保持同一结论、条件、时序、不确定性。
9. 最终自查不串人、不偷选候选、不打分、不把 BZ05 推断写成 BZ01 机械事实、不泄漏内部推理。

Skill 规定必经关卡，不规定固定权重、固定旺衰、固定婚配法、固定评分、固定目录顺序。

### 5.6 HH03 多轮 fresh

第一问：

HH02 root + 当前问题 -> fresh HH03。

第二问及以后：

HH02 root
+ Q1/A1 ... Qn-1/An-1 的 admitted canonical chain
+ direct predecessor
+ 当前问题
-> fresh HH03。

Website 负责把完整历史重新资料包化。AI 不读取上一轮 Provider conversation。

当前冻结不引入 AI summary/memory/compressor。只要材料容量允许就使用 admitted 原文；若真实 Provider 容量不足，失败关闭并报告 CONTEXT_CAPACITY_EXCEEDED，不偷偷做有损摘要。无限追问深度不在本轮承诺范围。

若任何一方 BZ05 被 supersede/revoked，或 BZ01 current eligibility/consent 已失效：

- 历史 HH02/HH03 仍可按原授权读回；
- 不允许在旧 root 上继续新 HH03；
- 用户必须用 successor BZ05 建新的 HH02 root；
- 禁止静默把旧线程换成新材料。
