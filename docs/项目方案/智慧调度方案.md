## 1. 最终结论

AGENT 不建设一个决定所有任务顺序的“中央智慧大脑”。

最终架构是：

> **Product 重放自己的静态业务逻辑，但不重放已经发生过的不可逆事实；各唯一 Owner 保存自己的事实，Product 只读取经过鉴权的正交事实投影来选择自己的恢复分支。**

这套智慧不体现在优先级，而体现在行动资格：

```text
没有到 nextCheckAt
  -> 不进入 Browser 队列

确实需要 Browser
  -> 进入现役唯一 FIFO

已取得 Browser
  -> 只执行当前安全 Interaction Burst

Provider 已确认接单且需要等待
  -> park exact Target
  -> 释放 Browser
  -> 在 FIFO 外等待

到达 nextCheckAt
  -> 进入同一 FIFO 队尾
  -> exact reacquire
  -> 执行一次短 probe
```

安全只决定“是否有资格入队”，不得改变 FIFO 内的先后顺序。

## 2. 现役事实与真实缺口

当前系统已经具备以下正确基础：

- 十二个 Product Plugin 各自拥有业务 Flow，shared runtime 不得决定下一个 Child；
- Runtime business active capacity 为 10；
- Browser active lane 为 1，最多 10 个 waiter，普通执行与恢复执行共用同一 FIFO；
- Browser Authority 已拥有 exact Target、Document、mutation WAL、park 与 exact reacquire；
- Browser WAL 已持久化 `DISPATCHED / CONFIRMED / REJECTED` 等物理 mutation 事实；
- Forensics Persistence 是唯一 evidence Owner；
- GPT Session Controller 是唯一 continuation Owner；
- Website 是任务公开状态、领域入库和最终完成的唯一 Owner。

当前尚未形成生产闭环的事实是：

1. `wait_for_stable_gpt_text/image` 在一次 Child 内以 250–500ms 轮询，最长持有 Browser 一小时；
2. `ProductionGptChildTools` 按 `sessionKey` 缓存 Browser lease，通常直到 Product settle 才释放；
3. 进程或 lease 中断后，Runtime 会重新从 Product 入口执行，内存 coroutine 不存在；
4. Browser binding、permit、MAC、mutation WAL 与 recovery lookup 尚未完整携带 `pluginVersion`；
5. SEO 的 `actionOrdinal` 运行时从 0 递增，恢复时跳过旧调用会导致后续序号漂移；
6. SEO 的 `evidenceRefs` 是内存数组，重启后无法恢复已经持久化的 1..N 条原证据引用；
7. Forensics 当前只能按已知 `recordRef` 读取，不能从 exact GPT call identity 找回原 record；
8. GPT evidence 当前以含时间字段的 `evidenceHash` 作为 idempotency key，同一 logical call 重读可能生成不同 hash；
9. `persist_gpt_continuation` 生成随机 continuationRef；
10. `advance_gpt_continuation_lane` 在数据库成功、Child 返回前崩溃后，再次调用会因为 lane owner 已释放而 CAS 失败；
11. GPT wait 的 deadline 由每次进入 Child 时的 `Date.now() + timeoutMs` 计算，反复重启会无限延长 bounded wait；
12. 当前只有 `public-knowledge-article-pipeline` 已拥有真实 Product Flow，其余 Product 仍必须 `PRODUCT_FLOW_NOT_IMPLEMENTED` 失败关闭。

因此，本方案解决的是“智慧调度底座与 SEO 最小真实证明”，不能把它冒充为十二个 Product 已全部生产完成。

## 3. 不可破坏的终态原则

### 3.1 一个业务 Flow Owner

每个 Product Plugin 用普通静态 TypeScript 直接拥有：

- Child 顺序；
- 分支、重复与跳过；
- Prompt 与模型策略；
- sessionKey、productStepId、callId；
- 固定 `actionOrdinal`；
- 恢复事实的解释；
- 输出重建与结果组装。

不得把这些提升到 Runtime、GPT、Browser、Mediator、Website 或新的共享 recovery engine。

### 3.2 一个 Browser 队列

`BrowserLaneCoordinator` 继续只做有界 FIFO：

```text
request -> push
lane free -> shift
park / close -> release -> next shift
```

不得增加：

- priority；
- product weight；
- recovery queue；
- reconciliation bypass；
- due-inspection 抢占；
- VIP 或 Provider 类型排序。

普通执行、Provider 巡检和恢复执行只要已具备资格，就进入同一个 FIFO 队尾。

### 3.3 各 Owner 只保存自己的事实

Browser mutation、Forensics evidence 与 GPT continuation 是三组正交事实，不能压成新的统一恢复状态。

不得出现：

```text
call_state
recovery_state
phase
nextStep
resumePoint
stepIndex
flowVersion
reconcileOnly
```

Product 可以读取事实，但只有 Product 能解释这些事实在自己的静态 Flow 中意味着什么。

### 3.4 不可逆动作先持久化、后 dispatch

同一 Provider effect logical identity 下：

- `DISPATCHED`：只允许只读补核；
- `CONFIRMED`：禁止再次发送；
- `REJECTED`：禁止用同一 identity 再次发送；
- Browser/进程/lease/build 变化不得改变 identity；
- 结果未知不得用重试掩盖。

### 3.5 只有 Website 完成业务

AGENT 的以下事实都不等于任务完成：

- Product 返回；
- staged result；
- artifact 上传；
- Outbox delivered；
- completion submission HTTP 200。

只有 Website domain consumer 成功验收、入库并签发 hash-bound admission receipt，任务才是 `completed`。其余情况保持 `failed + current_reason`。

## 4. 唯一 Owner 与边界合同

| 问题 | 唯一 Owner | 允许输出 | 明确禁止 |
|---|---|---|---|
| 业务任务准入、公开状态、领域入库、完成回执 | Website | job、attempt 授权、business admission receipt | 下发 Flow、Prompt、Target、nextStep |
| claim、lease、heartbeat、business active capacity、Outbox | shared runtime | 运输事实、执行 fence、只读事实投影 | 决定 Product 下一 Child、保存恢复流程位置 |
| 业务步骤、分支、顺序、恢复解释、结果组装 | Product Plugin | 静态 Child 调用与 staged result | 读取 Target、Document、WAL row、selector |
| 单个 Child 语义、短 probe、动态 backoff、总等待上限 | GPT Capability | typed result、typed failure、proof | 理解 Product 终态、决定业务下一步 |
| exact Target/Document、物理 mutation、WAL、park/reacquire | Browser Authority | mutation fact、受控 exact reacquire | 决定 Product 分支、给 Product 暴露物理页面身份 |
| 已具备资格者的 Browser 顺序 | Browser FIFO | 单一 FIFO lease | 优先级、恢复旁路、第二 scheduler |
| GPT evidence append/readback/identity lookup | Forensics Persistence | verified evidenceRef/hash、artifact refs | 业务恢复裁决、第二 Evidence Manifest |
| opaque continuation、conversation identity、lane CAS | GPT Session Controller | verified continuation fact | Product Flow、第二 continuation store |
| 严格解析并路由一次 | Mediator | 唯一 Product Plugin | Prompt、Browser 动作、恢复、终态裁决 |

## 5. 身份合同：Effect Identity 与 Sequence Invariant 必须分离

### 5.1 Provider Effect Identity

Provider effect logical identity 继续严格冻结为：

```text
job_id
+ attempt_id
+ plugin_id
+ plugin_version
+ product_step_id
+ call_id
+ child_id
+ input_hash
```

其确定性 `logical_mutation_id` 只能由以上字段计算。

`actionOrdinal` 不得进入 Provider effect logical identity。

### 5.2 Sequence Invariant

`actionOrdinal` 是 Product Flow 的顺序证明：

```text
Effect Identity
  -> 查找唯一既有调用事实

actionOrdinal
  -> 校验该调用是否位于 Product 冻结顺序中的合法位置
```

同一 Effect Identity 找到事实后，如果调用方提供的 `actionOrdinal` 与 Product 冻结顺序不一致，必须以 sequence drift 失败关闭；不得把 ordinal 漂移解释成新调用，也不得生成第二 mutation。

### 5.3 `pluginVersion` 端到端打穿

施工必须一次性把 `pluginVersion` 加入并验证于：

```text
durable plugin identity
  -> BrowserExecutionBinding
  -> execution binding hash
  -> BrowserCommandPermit
  -> permit MAC payload
  -> Extension permit validator
  -> BrowserMutationIdentity
  -> browser_mutations compact WAL row
  -> logicalMutationId
  -> atomicStepRecovery
  -> callRecoveryScope
  -> runtime log typed identity / focused acceptance
```

不能只修改 SQL，也不能仅在 Runtime 内校验后丢失。

### 5.4 两种恢复查询不可混成万能查询

`atomicStepRecovery` 与 `callRecoveryScope` 保留不同职责：

#### `atomicStepRecovery`

用于判断一个 exact mutation call 是否已经发生。它必须先按完整 Effect Identity 查找唯一事实，再独立校验 `actionOrdinal`；Target-local 动作另绑定 target generation。

#### `callRecoveryScope`

只用于 Browser Authority 判断当前 Product step 应精确重领哪个停放 Target。它可以保持 step-level 派生，但至少必须绑定：

```text
job_id
+ current attempt_id
+ plugin_id
+ current plugin_version
+ product_step_id
+ provider effect scope
```

若结果指向多个 `targetRef`、多个不相容 Document 或跨 attempt/version 事实，必须失败关闭。该查询及其 target/document 永远不返回 Product。

### 5.5 Target-local evidence 与跨代次恢复边界

Browser WAL 中 Target-local 物理 mutation identity 继续追加 `target_generation`，用于隔离不同物理页面世代；Forensics 的 GPT call evidence identity 则继续只绑定 exact GPT call identity，不追加 `target_generation`。这两个身份不得混用。

因此同一 attempt 内必须遵守：

- exact target-local call 已有 verified evidence 时，只能返回原 evidenceRef/hash，禁止在新 Target generation 再次执行该 call 的物理 mutation；
- evidence 尚缺失但 Browser WAL 已有 `DISPATCHED / CONFIRMED / REJECTED` 时，仍然禁止重发，只能补核原后置事实并封闭原 evidence；
- 只有 Browser Owner 能证明原 call 从未发生物理 dispatch，且当前精确前置仍成立时，才允许该 call 首次执行；
- 原 exact Target 与所需后置事实仍可恢复时，只读 rehydrate 并继续同一 attempt；`rehydrate` 不得包含重做已有 evidence 的 mutation；
- 原 exact Target 丢失，或下游所需的瞬态前置无法只读恢复时，当前 attempt typed fail-close；只有 Website 安全接受新 attempt 后，才能用新 `attempt_id` 和新 exact call identity 重新生产。

该规则主动收窄了原 Browser Blueprint 对“Target-local 新 Target 代次可重做”的许可。当前已授权候选必须使唯一 `agent-production-runtime`、`gpt` 与 `local-browser-session` 法案/Blueprint 同步保持该窄化语义；代码施工不得通过兼容分支恢复旧许可。

## 6. `readCallFacts`：无持久化、无裁决的正交事实投影

在现有 `ProductGptTools` 边界增加一个只读调用面：

```ts
readCallFacts({
  productStepId,
  callId,
  child,
  actionOrdinal,
  input
}): Promise<ExactGptCallFacts>
```

完整 `jobId + attemptId + pluginId + pluginVersion` 由 durable execution binding 注入，`inputHash` 由同一 canonical hash 实现计算，Product 不得自行伪造 Browser identity。

返回值是正交事实集合，不是恢复状态：

```ts
type ExactGptCallFacts = {
  exactCallIdentityHash: `sha256:${string}`;

  mutation: null | {
    owner: "browser";
    effectScope: "target_local" | "provider_effect";
    outcome: "DISPATCHED" | "CONFIRMED" | "REJECTED";
    terminalAt: string | null;
  };

  evidence: null | {
    owner: "forensics-persistence";
    evidenceRef: string;
    evidenceHash: `sha256:${string}`;
    readbackVerified: true;
    artifactRefs: readonly string[];
  };

  continuation: null | {
    owner: "gpt-session-controller";
    continuationRef: string;
    conversationIdentityHash: `sha256:${string}`;
    laneVersion: number;
    contentReadbackVerified: true;
  };
};
```

`ExactGptCallFacts` 不提供历史 `failure`。当前 Child 的 typed failure 沿现役返回链直接送达 Runtime，并由 Runtime 冻结当前 attempt 的第一次 `attempt_failure`；Product 不读取、不维护 per-call failure history。Browser 的 `REJECTED` 只是 mutation fact，Forensics 的 failure/evidence record 只是取证事实，两者都不被组装成第二失败系统或 Product 流程输入。

实际类型只保留完成恢复所需的安全字段。禁止返回：

- `resumePoint`；
- `nextStep`；
- `phase`；
- 统一 `state`；
- `targetRef`；
- `documentRef`；
- WAL row；
- DOM、URL、selector、Prompt 或原始用户内容。

`readCallFacts` 不写数据库、不创建记录、不安排任务、不决定是否继续。它只验证并组合现有 Owner 已持久化的事实。

## 7. Product-owned Progressive Exact Fact Replay

### 7.1 重启入口

lease 或进程重启后：

```text
Runtime 重新取得同一 accepted attempt 的新 lease
  -> 重新校验 durable plugin identity
  -> 从 Product Plugin execute 入口开始
  -> Product 只读取当前已能用 task + 静态 Product 事实完整构造 exact identity 的调用 facts
  -> 优先检查当前可构造的不可逆锚点，并只读恢复/验证它们的上游输出
  -> 上游输出产生下一调用的动态 input
  -> Product 用完整 input 计算下一 exact inputHash，再读取该 call facts
  -> 逐步验证已知事实构成合法静态前缀/分支
  -> Product 自己选择正常执行、只读重建或结构化失败
```

Runtime、GPT、Browser 与 Forensics 均不得返回 Product 的下一步。

任何新 Browser mutation 前，Product 必须已经渐进回放并验证到当前执行边界，且必须先检查当前已能完整构造 identity 的下游不可逆锚点。不能一边从第一条调用开始执行，一边到后面才发现 submit 已经 `CONFIRMED`。

以 SEO `produce_article` 为例，Product 在可能执行 fresh/profile/attach/write 前，先读取能由 task、静态 Prompt/marker 和冻结调用完整构造的 submit facts；然后按以下依赖顺序渐进向后读取：

```text
research submit fact
  -> submission/wait 只读 rehydrate
  -> 得到 assistantTurnId + responseHash
  -> research checkpoint exact fact
  -> 得到 rawHash / canonical conversation identity
  -> continuation persist exact fact

article submit fact
  -> wait/checkpoint 产生本段动态输出
  -> continuation advance exact fact

image submit fact
  -> wait/checkpoint 产生媒体与 conversation 动态输出
  -> continuation advance exact fact
```

如果后段事实存在，Product 先只读重建并验证前段业务输出与分支；不得重新执行前段页面 mutation。若“后段已发生”与“前段业务分支不允许到达后段”同时成立，则是事实矛盾，必须失败关闭。

这些 progressive preflight 调用是 Product 源码中的直接静态判断，不得抽成全局 call descriptor registry、宽匹配 `job + step + call` lookup、恢复 graph 或 shared interpreter。渐进回放期间 authority 发生漂移时必须重新校验或失败关闭，不得在不一致快照上 dispatch。

### 7.2 Product 的调用写法

每个 Product 必须在实际 TypeScript Flow 调用处直接写固定 ordinal：

```ts
await executeOrReplay({
  actionOrdinal: 1,
  productStepId: "corpus_research",
  callId: "fresh-chat",
  child: "prepare_clean_gpt_chat",
  input: { timeoutMs: 60_000 }
});
```

禁止用 `++actionOrdinal`。禁止在另一份 JSON、Skill、registry 或 shared graph 中复制顺序。

Product 内可以有本产品私有的窄 `executeOrReplay`，但它只能服务本 Product 的静态调用点，不能演变为跨 Product executor、planner、workflow、bus 或 DSL。

### 7.3 正交事实的解释规则

Product 对一个调用的处理固定为：

| 事实组合 | Product 允许行为 |
|---|---|
| 无 mutation、无 evidence、无 failure | 执行该静态 Child |
| verified evidence 已存在 | 恢复原 `evidenceRef`；需要运行值时只做该 Child 许可的只读 rehydrate，不写第二 evidence |
| Provider effect `DISPATCHED` | exact reacquire 后按冻结 postcondition 只读补核；禁止 submit |
| Provider effect `CONFIRMED` | 跳过物理 submit；进入该 Product 已写明的 readback/wait/checkpoint 分支 |
| Provider effect `REJECTED` | 返回 typed failure；同一 identity 禁止再次发送 |
| continuation 已达到本调用期望内容且 evidence 缺失 | 由幂等 persist/advance 返回原成功，再补唯一 evidence |
| facts 互相矛盾、重复、身份或 ordinal 漂移 | fail-close，不猜测恢复位置 |

这里没有全局“恢复算法”。表中动作仍由每个 Product 在自己的静态 Flow 中具体表达。

### 7.4 输出重建

Forensics 的安全 evidence 不持久化 raw Prompt、raw HTML 或完整 GPT 文本。进程重启后，运行值必须从原 Owner 重建：

- 文本：exact reacquire 同一 conversation 和 turnMarker，只读 wait/checkpoint，重新取得 raw text 并严格 parse；
- 生成图片：读取已验证 Forensics artifact，或在同一 exact assistant turn 重新执行受控 authenticated-media readback；
- continuation：读取 GPT Session Controller 的 opaque continuation；
- evidence_refs：从 Forensics exact-call lookup 找回原引用；
- Browser target：只由 Browser Authority 根据内部 recovery scope 精确重领。

Product 不得因为 Forensics 不保存 raw text 就重新 submit。

## 8. Forensics evidence replay 闭环

### 8.1 唯一 evidence identity

GPT evidence 的 Forensics idempotency identity 改为 exact GPT call identity 的确定性 hash，例如：

```text
gpt-call-evidence:v1:<exactCallIdentityHash>
```

不得继续使用包含 `startedAt / endedAt` 的 `proof.evidenceHash` 作为 logical call 的唯一 idempotency identity。

`evidenceHash` 仍然用于证明实际 proof 内容；它不是 call identity。

Forensics record 必须持久化或由 envelope 可验证地绑定 `exactCallIdentityHash`，并把 `actionOrdinal` 作为独立 sequence evidence 保存。`actionOrdinal` 不进入 evidence logical identity；恢复时先取回唯一 record，再校验 ordinal。

生成 artifact 的 idempotency identity 同样由 exact call identity 加受控 suffix 派生：

```text
gpt-call-artifact:v1:<exactCallIdentityHash>:original
gpt-call-artifact:v1:<exactCallIdentityHash>:webp
```

### 8.2 exact-call readback

升级现役 Forensics Owner，使其能够执行：

```text
exact GPT call identity
  -> 派生唯一 evidence recordRef
  -> readback record
  -> 校验 envelope、identity、payload hash、integrity hash
  -> 返回原 recordRef / evidenceHash / artifactRefs
```

这可以复用现有确定性 ref 和 append-only storage，不新增 Evidence Ledger、Evidence Manifest、第二证据表或 Runtime Log proof 正文。

若同一 exact identity 指向不同内容、多个记录或损坏引用，必须以 Forensics identity conflict 失败关闭。

### 8.3 evidence_refs 恢复与排序

Product 按自己源码中固定 `actionOrdinal` 对已验证的成功 evidenceRef 排序，并验证它们构成当前路由的合法静态路径。

```text
重启前 Child 1..15 已完成
  -> Forensics 返回原 1..15 evidenceRef

重启后 Child 16..N 完成
  -> append 16..N 的唯一 evidenceRef

最终 evidence_refs
  -> [原 1..15, 新 16..N]
```

`execution_receipt_hash` 继续绑定最终完整、有序集合。不得把“本进程这一次收集到的 refs”冒充完整执行证据。

## 9. Continuation 的双幂等合同

### 9.1 `persist_gpt_continuation`

continuationRef 必须由 exact persist call identity 确定性派生并保持 opaque，不再使用随机 UUID 作为 logical continuation identity。

持久化规则：

```text
ref 不存在
  -> insert exact plugin / owner / subject / authorization / provider identity

ref 已存在且全部内容相同
  -> readback 验证
  -> 返回原 continuationRef success

ref 已存在但任一绑定或 provider identity 不同
  -> GPT_CONTINUATION_IDEMPOTENCY_CONFLICT
```

### 9.2 `advance_gpt_continuation_lane`

advance 必须同时支持正常 CAS 和内容幂等 readback：

```text
lane 仍由当前 job 持有
AND lane_version 等于预期
  -> 原子写入期望 provider identity
  -> 释放 lane

否则读取当前 continuation：
  当前 provider identity == 本调用期望 provider identity
  AND plugin/binding 相同
  AND lane 已释放
  AND lane version 与本次成功后置事实一致
    -> 证明同一个 advance 已经成功
    -> 返回原 success

其他情况
  -> GPT_CONTINUATION_ADVANCE_CAS_FAILED / DRIFT
```

这使以下故障边界可恢复：

```text
数据库 advance 已提交
  -> lane owner 已清空
  -> 进程在 Child 返回或 evidence append 前崩溃
  -> 重启后相同 exact call 只读证明后置事实
  -> 返回原成功
  -> 补齐唯一 evidence
```

`release_gpt_continuation_lane` 同样必须保持内容幂等：已经由同一调用释放时返回成功；不得把重放安全变成新的 lane 状态机。

## 10. Cooperative Provider Wait

### 10.1 私有协同协议

公开 GPT Child 分母保持 23 个，Product 接口仍然调用：

```ts
await gpt.execute({ child: "wait_for_stable_gpt_text", ... });
```

不新增 `park_gpt_wait`、`resume_gpt_wait`、`poll_gpt_wait` 等公开 Child。

GPT wait Child 内部通过一个产品不可见的窄 execution-context 能力完成：

```text
with exact Browser lease 执行一次短 probe
  -> 完成：返回 success
  -> 未完成：计算 nextCheckAt
             请求 normalProviderWaitYield
             在 FIFO 外等待
             到期后进入同一 FIFO
             exact reacquire
             继续下一次短 probe
```

Owner 分工必须保持：

- GPT wait Child 决定 probe 条件、动态 backoff 和 `nextCheckAt`；
- ProductionGptChildTools 只管理本次 execution 的 lease 交接；
- Browser Authority 只验证 park 前置、保存 exact Target 并执行 reacquire；
- Browser FIFO 只决定已经入队者的先后；
- Product 不知道一次 wait 中间发生过多少次 park/reacquire。

### 10.2 动态 backoff

backoff 必须由可观察事实驱动并保持有界，例如：

```text
没有 user turn / assistant turn
  -> 逐步放宽检查间隔

assistant turn 已出现但仍 generating
  -> 中等间隔

generation control 已消失但内容尚未稳定
  -> 缩短间隔

内容 hash 在稳定窗口内不再变化
  -> 立即成功
```

间隔不是成功条件。成功仍只能由 fresh DOM 的直接稳定性事实证明。

`nextCheckAt` 是本次 coroutine 的瞬时调度值，可以不持久化。未到时间的任务不得在 FIFO 中占位。

### 10.3 跨重启绝对截止时间

bounded wait 的总生命期不得因 lease 或进程重启刷新。

```text
absoluteDeadline
  = exact submit Provider effect 的 durable confirmedAt
  + Product 给定的 timeoutMs
```

其中：

- `confirmedAt` 来自 Browser WAL 中已 terminal Provider effect 的不可变时间事实；
- `terminalAt` 必须是首次进入 `CONFIRMED / REJECTED` 时冻结的不可变字段；现役 `updated_at` 只有在 SQL 和状态机能证明 terminal row 以后绝不再更新时才可直接作为该事实，否则必须在现有 WAL row 内增加 immutable terminal timestamp；
- GPT wait 负责根据该锚点计算 remaining time；
- 重启只重新计算下一次 probe，不重新获得完整 timeout；
- 当前时间已超过 absoluteDeadline 时立即返回 typed timeout；
- Runtime lease deadline、abort 与 absoluteDeadline 任一先到都终止等待。

wait 必须与一个 exact submit effect 绑定。该绑定由 Product 的静态调用关系明确提供，由 execution adapter 验证完整 identity；不得由 Runtime 猜测“最近一次 submit”。

不得为此新增 Provider Wait Ticket、wait 表、terminal-time 第二表或 durable `nextCheckAt`。

## 11. 两种 park 前置必须分开

底层仍复用同一个 Browser park 机制，但入口语义不同。

### 11.1 normalProviderWaitYield

正常 Provider 等待让路必须同时满足：

- 当前 exact submit Provider effect 已 `CONFIRMED`；
- `pendingMutationCount == 0`；
- 当前没有需要立即完成的 mutation postcondition；
- exact Target/Document 与 frozen conversation/turn identity 可持久恢复；
- Browser Authority 成功 park 并撤销 active claim/Workspace。

满足后立即释放 FIFO。

### 11.2 recoveryPark

恢复 park 正是为 unresolved `DISPATCHED` 现场存在：

- 保留原 exact Target/Document 与冻结正负 postcondition；
- 撤销 active claim/Workspace；
- 立即释放 FIFO；
- 只允许同一 job、同一 attempt、同一 pluginVersion 的 recovery scope 精确重领；
- 其他 job 不受该现场阻断。

因此不能把“park 必须零 mutation”写成全局规则。零 mutation 只属于 normal Provider wait yield；recovery park 允许并保护 `DISPATCHED` 现场。

### 11.3 registry 丢失

扩展 service worker 丢失 parked Target registry 时：

```text
当前 attempt fail-close
  -> 不猜 tab
  -> 不创建新 tab 冒充恢复
  -> 不重新 submit 同一 call
  -> 记录精确 typed reason
```

这不是整个业务 job 永久死亡。后续是否接受新 attempt 由 Website 与 attempt 合同决定。

## 12. “绝不重提”的精确边界

正确规则是：

> **同一 attempt、同一 logical Provider effect call 绝不重新提交。**

### 当前 attempt

只要同一 Effect Identity 已是 `DISPATCHED / CONFIRMED / REJECTED`，就不得再次执行物理 submit。Target 丢失、进程重启、lease 更新或 build 改变均不能绕过。

### 新业务 attempt

新的业务 attempt 可以使用新的 `attempt_id` 和新的 Effect Identity 正常执行，但必须同时满足：

- Website 已按现役合同接受该新 attempt；
- accepted attempt 总数未超过上限；
- 前一 attempt 不存在未收束 `DISPATCHED`；
- 前一 attempt 的失败和事实仍可追溯；
- 不以新 attempt 掩盖结果未知的外部动作。

因此：

```text
exact Target 丢失
  -> 当前 attempt fail-close
  -> 同一 attempt/call 禁止重新 submit

前 attempt 已安全收束
+ Website 接受新 attempt
  -> 使用新 attemptId / 新 Effect Identity 正常重试
```

失败是故障现场，不是业务成功，也不是自动永久死路。

## 13. SEO Product 的确定性恢复

SEO 是智慧调度底座的第一个真实消费者。其三段 Flow 与两条 review Flow 保持 Product-owned，不抽成共享流程。

`produce_article` 每次进入时必须先执行本 Product 的 Progressive Exact Fact Replay：先读取当前已能完整构造 identity 的 research/article/image 不可逆 submit 锚点，再从已验证上游输出逐步派生 checkpoint/evidence 与 continuation 的 exact input，判断已经真实到达的最远合法静态片区。未渐进验证到当前执行边界前，不允许执行任何新页面 mutation。

### 13.1 `corpus_research`

Product 从入口读取本段各固定调用的正交事实：

- fresh/profile/attachment/prompt 等 target-local 调用已有 verified evidence 时只恢复原 refs，不在新 Target generation 重做物理 mutation；
- submit 的 mutation fact 不存在时才允许正常交互并提交；
- submit `DISPATCHED` 只允许 exact readback；
- submit `CONFIRMED` 跳过 fresh/attach/write/submit，直接恢复原 conversation 并执行 wait/checkpoint；
- checkpoint 后重新解析 research；
- continuation persist 确定性返回同一 ref；
- `decision=decline` 直接组装 article=null、image=null；
- `decision=proceed` 进入 article_synthesis。

### 13.2 `article_synthesis`

- 从 continuation Owner 取得并验证同一 conversation；
- 若 article submit 已发生，禁止再次 write/submit；
- exact readback/checkpoint 重建 raw article 并严格 parse；
- advance 已提交但 evidence 未写时，以内容幂等返回原成功；
- 完整恢复本段 evidenceRefs 后进入图片段。

### 13.3 `article_image_generation`

- 使用同一 continuation；
- 已提交的图片 turn 不得重提；
- 从 exact assistant turn 或 verified Forensics artifact 恢复图片；
- 保持一张 metadata-free 1200x630 WebP；
- advance 内容幂等；
- 按固定 ordinal 组装完整 evidence_refs 与 staged result。

### 13.4 Review 路由

`accuracy_challenge` 与 `quality_reflection` 各自使用 fresh conversation 和独立固定 ordinal。它们不得复用 produce_article 的 conversation、continuation、mutation identity 或恢复分支。

## 14. 十二 Product 同时触发时的实际运行

十二是 Product 数量，不等于并发槽数量。

```text

  -> Runtime 最多领取 10 个 active job
  -> 其余 job 等待 claim

每个 active Product
  -> 自己执行静态 Flow
  -> 只有当前确实需要 Browser 时才入 FIFO
```

```text

-> profile
-> attachment
-> prompt
-> submit
-> submission reconcile
-> normalProviderWaitYield
```

不要求每个 Child 后都切换任务。切换点是 Provider 已确认接单并且当前无未决 mutation，而不是任意 Child 边界。

## 15. Provider In-flight Capacity 的终态边界

- 当前只有每 attempt 的 `max_provider_turns`，它不是整机 Provider 并发容量；
- 当前没有经真实 Provider 证明的独立 P；
- 先新增 P 会引入无事实依据的容量 authority 或 ledger。

未来即使增加 P，也必须满足：

- 只阻止新的 Provider submit；
- 不改变 Browser FIFO；
- 不阻止 readback、checkpoint、continuation 或 recovery；
- 不成为 Product 优先级；

## 18. 验收矩阵

### 18.1 身份与边界验收

- `pluginVersion` 从 durable identity 一直进入 Browser permit、MAC、Extension validator、WAL 与 recovery lookup；
- Provider `logicalMutationId` 包含冻结 Effect Identity，明确不包含 `actionOrdinal`；
- `actionOrdinal` 只作为 Product sequence invariant 独立验证；
- 同 identity、不同 ordinal 必须 sequence-drift fail-close，且 mutation count 不增加；
- prior attempt 或 prior pluginVersion 事实不能授权当前 attempt 的物理动作；
- `callRecoveryScope` 多 target、多 attempt 或多 version 时失败关闭；
- Product API 与日志中不存在 targetRef、documentRef、DOM、selector 或 WAL row 泄漏。

### 18.2 FIFO 与 cooperative yield 验收

最小真实场景使用两个 SEO job：

```text
A 取得 Browser
-> submit confirmed
-> park/release

B 随后取得 Browser
-> submit 或短动作

A 未到 nextCheckAt
-> FIFO 中不存在 A

A 到期
-> 进入当时 FIFO 队尾
-> exact reacquire 原 Target
-> 短 probe
```

必须证明：

- 一个 active lane；
- 最大 10 waiter；
- acquire 顺序严格 FIFO；
- normal、inspection、recovery 没有 priority 字段或旁路；
- wait 期间 Browser lane 可被另一 job 使用；
- Interaction Burst 结束前不做无意义 Child 级切换；
- park/reacquire 后仍是原 exact conversation。

### 18.3 Browser 故障矩阵

- submit 前崩溃：原 exact Target 与所需后置事实仍可安全只读 rehydrate 时，同 attempt 继续；否则当前 attempt typed fail-close，只由 Website 安全接受的新 attempt 重新执行；
- 同 attempt 中，已有 verified evidence 的 target-local call 在新 Target generation 的物理 mutation count 必须为 0；
- WAL `PREPARED` 后、dispatch 前崩溃：不得冒充已发送；
- `DISPATCHED` 后崩溃：只读补核，mutation count 保持 1；
- `CONFIRMED` 后、wait 前崩溃：跳过 submit，恢复原 Target；
- `REJECTED` 后崩溃：同 identity 返回原失败，不重发；
- park 后 service worker registry 丢失：当前 attempt typed fail-close，不猜 tab；
- 一个 job 的 parked/recovery 现场不阻断其他 job 的 FIFO；
- normalProviderWaitYield 有 pending mutation 时必须拒绝；
- recoveryPark 在合法 `DISPATCHED` 现场必须允许并释放 FIFO。

### 18.4 Forensics 故障矩阵

- append 前崩溃：重启后允许生成并 append 唯一 evidence；
- append 已成功、返回前崩溃：重启后按 exact identity 找回原 recordRef；
- readback 后、Product push 前崩溃：重启后仍返回原 recordRef；
- 同 exact identity 不同 proof 内容：identity conflict fail-close；
- target-local 新 Target generation 不得通过生成新 proof 规避该 identity conflict；
- record 或 artifact integrity mismatch：fail-close；
- 重启前 1..N 与重启后 N+1..M 形成完整、有序、无重复 evidence_refs；
- execution_receipt_hash 绑定完整集合；
- Runtime Log 不持久化 proof 正文。

### 18.5 Continuation 故障矩阵

- persist insert 前崩溃；
- persist insert 后、返回前崩溃；
- acquire lane 后崩溃；
- advance DB commit 前崩溃；
- advance DB commit 后、Child 返回前崩溃；
- advance 成功后、Forensics append 前崩溃；
- release 成功后、Child 返回前崩溃；
- 相同内容重放返回原成功；
- 不同内容、错误 plugin/owner/subject/authorization、错误 lane version 必须失败关闭；
- 不创建第二 continuationRef 或第二 lane Owner。

### 18.6 Deadline 验收

- 首次 wait 的 absoluteDeadline 等于 durable Provider effect confirmedAt + timeoutMs；
- Provider terminalAt 首次写入后不可变，后续诊断、补核或 readback 不得刷新该时间；
- 进程在等待 55 分钟后重启，不得重新获得 60 分钟；
- 连续多次重启总等待仍不超过同一 absoluteDeadline；
- 未到 nextCheckAt 不入 FIFO；
- 到达 deadline 立即 typed timeout；
- runtime lease/abort 更早到达时立即停止；
- 不存在 wait 表、Ticket 或持久 nextCheckAt。

### 18.7 Attempt 与禁重提验收

- 同 attempt/call 的 submit/upload 物理 mutation count 始终最多 1；
- 同 attempt/exact call 已有 verified evidence 后，target-local 物理 mutation 不得因新 Target generation 再次执行；
- 原 exact Target 丢失或所需事实不可只读 rehydrate 时，当前 attempt 必须 typed fail-close；
- lease、进程、Target、build 变化不能创建新 Provider effect identity；
- 前 attempt 有 `DISPATCHED` 债务时禁止接受新 attempt；
- 前 attempt 安全 terminal 且 Website 接受后，新 attempt 使用新 identity 可正常重试；
- 不把“当前 attempt fail-close”错误升级成“业务 job 永久禁止生产”；
- accepted attempt 总数继续服从现役上限。

### 18.8 业务完成验收

- SEO proceed、decline、accuracy_challenge、quality_reflection 各自 exact Child sequence 与固定 ordinal 成立；
- SEO 进程重启后 research/article/image raw output 可从原 Owner 重建；
- 最终 evidence_refs 完整；
- generated image artifact/receipt 完整；
- staged result、Outbox delivered 仍不得报告 completed；
- Website domain consumer admission receipt 到达后才 completed；
- 其余十一未施工 Product 保持零 Provider 动作的 `PRODUCT_FLOW_NOT_IMPLEMENTED`。

```text
  != Website 业务完成
```

最终候选只有在以下条件同时成立时，才能进入其对应的 READY/RELEASE 裁决：

- 使用 clean、固定 Git candidate；
- active law、Blueprint、实现与生成物一致；
- 全部直属验收通过；
- 唯一完整 CI 通过；
- 全新独立只读治理审计通过；
- 真实 Chrome、真实 Provider、真实进程重启与动态 recovery proof 通过；
- 双仓边界需要的 Website admission proof 成立。

本文自身不宣告 CHANGE、READY、CI_FULL_PASS、RELEASE 或生产完成。

## 20. 十项冻结审计缺口的最终封口

| 冻结审计缺口 | 本方案的最终处理 |
|---|---|
| 1. `actionOrdinal` 被误写入 Effect Identity | 第 5 节将 Effect Identity 与 Sequence Invariant 完全分离，并要求 pluginVersion 端到端打穿 |
| 2. 多 Owner 事实被压成统一恢复状态 | 第 6 节定义无持久化 `readCallFacts` 正交投影，禁止统一 state/phase/nextStep |
| 3. `evidence_refs` 重启后丢失 | 第 8 节由唯一 Forensics Owner 提供 exact-call 确定性 ref、readback 与有序恢复 |
| 4. Continuation 只修 persist、未修 advance | 第 9 节要求 persist、advance、release 的内容幂等和 DB-commit/return 崩溃恢复 |
| 5. wait timeout 随重启刷新 | 第 10 节用 durable Provider effect confirmedAt 派生 immutable absoluteDeadline |
| 6. “绝不重提”被误解为 job 永久不能重试 | 第 12 节限定同一 attempt/call 禁重提，并保留安全新 attempt |
| 7. V12 被当成未核验的远端 canonical | 第 0 节分离 Git V11 base 与用户 V12 dirty candidate，要求工单绑定 exact commit/patch/hash |
| 8. target-local 跨 Target generation 重做与唯一 evidence identity 冲突 | 第 5.5 节禁止同 attempt 已有 verified evidence 后跨代次重做，无法只读恢复则结束 attempt |
| 9. 入口一次性读取所有 exact facts 存在动态 input 循环 | 第 7 节改为 Product-owned Progressive Exact Fact Replay，先恢复上游输出再计算下一 inputHash |
| 10. `readCallFacts.failure` 没有唯一 durable Owner | 第 6 节删除该投影，当前 typed failure 直接终止 attempt，不建 per-call failure history |

两个附加窄修正也已闭合：

- `atomicStepRecovery` 与 `callRecoveryScope` 分工保留，不合并成万能查询；
- normal Provider wait park 要求零 pending mutation，recovery park 则允许并保护 `DISPATCHED` 现场。

两个实施约束不新建架构，但必须进入验收：

- Browser WAL 必须提供 immutable terminalAt，不得用会继续变化的 `updated_at` 重置 absolute deadline；
- parked Target registry 仍属扩展内存现场，service worker 丢失时 fail-close，必须由真实 Chrome/MV3 证明，不新增第二 durable registry。

## 21. 最终冻结句

> **Website 决定谁可以进厂并拥有最终业务真相；每个 Product 决定自己做什么以及如何解释恢复事实；GPT Wait 决定什么时候值得回来检查；Browser Authority 决定能否安全离开和精确回来；所有已经具备资格的 Browser 请求只进入同一个 FIFO。系统通过持久事实避免重复不可逆动作，而不是通过中央状态机记住流程位置。**

这就是 AGENT 智慧调度的最终方案。本方案在方案层已 `GO`，不再重开架构论证；后续只能依 exact candidate 执行 authority 对齐、实施工单、片区删除+重构和完整验收。
