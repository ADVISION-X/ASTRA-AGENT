## 六、删除审判（为什么不新增，只复用）

对本方案将要新增的每一行校验代码逐项回答：

1. **为什么必需**：GPT 是外部 Provider，其回传的 JSON 目前只在字段名/类型层面做最基础检查；缺少 `exact`（多余或缺失字段）、`commonReport`（双层结构、覆盖数组、引用数组形状）、`locked`（身份字段未被模型悄悄改写）、`parseReview`（review 结论落在合法枚举与数量范围内）这四类校验时，一个格式漂移或被模型改写身份字段的回答有可能在 AGENT 侧无声通过，只依赖网站侧摄入校验（`bazi-agent-result-validation.ts`）兜底——这是单层防护对多层防护的实际差距，不是假设风险。
2. **真实 GAP 是什么**：见第五节逐行代码证据，不是猜测。
3. **谁是真实消费者**：Website 领域 consumer（`bazi-agent-result-validation.ts`）已经是这批数据的下游消费者；AGENT 侧补上同等校验，是在数据交给 Website 之前先行失败关闭，避免无谓的一次完整 Provider 往返（Provider effect 有代价、且法案禁止重复 submit）产出一个注定会被网站拒收的结果。
4. **唯一 Owner**：`productResultValidation` 已经是唯一校验工具 Owner，本方案不新建第二个校验器、第二个 registry 或第二个 DSL,只是让三个 bazi Plugin 像其它已核实同类 Plugin 一样调用它。
5. **删除后会在哪里失真**：若不做，三个 bazi Plugin 会继续是已核实的至少 10 个同类 Plugin 中结构校验密度最低的一组，且 `bazi_ai_full_analysis` 会继续是唯一没有任何身份锁定的正式产品——这个失真现在就可以用代码差异表格证明，不是未来假设。
6. **是否有更短方案**：有——直接复用现役 `productResultValidation.exact`/`commonReport`/`stringArray`/`parseReview`（零新增工具），仅 BZ03 的嵌套身份锁定和 BZ05 的异名 hash 锁定需要各写 2-4 行局部比较代码（不抽成新函数、不跨文件共享，因为目前只有一处消费者，且抽成共享工具需要改 `src/mediator/**`，超出本方案禁止范围）。
7. **它替代了什么，旧路径怎么删除**：不替代任何现有代码路径，纯新增校验语句，无需删除；唯一被"内容替换"的是三处原先只查两个 key 是否存在的 review 校验，改为调用 `result.parseReview(...)` 后，原先那两行浅层检查物理删除（不保留 dead code、不留兼容分支）。
