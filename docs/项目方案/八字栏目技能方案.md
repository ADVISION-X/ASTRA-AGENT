## 0. 一句话结论

八字栏目有五个商品，但只有三个 AI Product Skill：

1. `bazi-chart-interpretation`：BZ05 全盘深度解读；
2. `bazi-ai-full-analysis`：BZ03 专项问题深度分析；
3. `bazi-report-followup`：BZ04 针对 approved BZ05 或 BZ03 的一次续问。

BZ01 基础排盘和 BZ02 PDF 导出是 Website 确定性产品，**不要 Skill、不要 GPT、不要 AGENT job**。三个 AI Product 各自保留一份 Plugin、一份 Skill、一份普通静态 TypeScript Flow；**不要“八字栏目总 Skill”、共享业务 Flow、第二队列、第二结果、第二完成裁决或兼容桥**。

当前三个 Plugin 的源码虽有可执行外形，但现役 AGENT 法案和 V6 Blueprint 明确规定：除已单独施工的 SEO Product 外，其余 Product 必须 `PRODUCT_FLOW_NOT_IMPLEMENTED` 且零 Provider/页面动作。因此当前八字可执行源码只是**尚未被现役 authority 接纳的候选漂移**，不是可直接保留的生产基线。终态施工必须先获得冻结 authority 的另行明确授权并接纳本文定义的三个 Flow；在此之前，八字 route 只能失败关闭。

终态还必须闭合以下 P0：

- BZ05、BZ03 各自先形成私有、非 canonical 的 base checkpoint，再由自己的 Product 建立隔离 formal child；正式 AI 必须独立复核锁定事实、完整 READY 和非约束 prior interpretation；
- Website 在 Provider 调用前冻结并下发 exact semantic manifest、question snapshot/ordered units、完整 nested output contract，不能在结果回来后临时发明分母；
- 六条 review 必须拿到完整锁定上下文和 Provider 可见 review 输出合同，但只产生 finding/plan，不产生第二报告；
- primary 必须走 Bazi domain admission，再由 Commercial fulfillment 签发 exact Delivery Manifest，最后才允许 V6 completed；review 则在 review finding/plan 入库后完成，二者不能混写；
- confirmed submit 后的 timeout、Target、Document、channel、进程重启和 attempt cap 都只读恢复，不得靠错误码 allowlist 降格或重发；
- 原八字 task 的失败必须投影到原商业履约和 UI，不能无限显示“运行中”。

## 5. 三份 Skill 的终态

### 5.1 每份 Skill 都要

- 声明唯一 product/action/review 范围；
- 区分锁定事实、READY 原文、private base prior interpretation、用户自述、formal 新推断和现实待核事实；
- private base 只是私有、非 canonical、非约束先验；formal 必须重新核对锁定事实和完整 READY，允许明确不同意 base；
- 对唯一盘或完整候选集分别给稳定结论、分支、差异和不确定性；
- 重要判断说明盘面/古籍依据、条件、反证和限制；
- 专业层与白话层保持结论、条件、时序、风险和不确定性等值；
- 禁止恐吓、宿命绝对化、现实保证、法事营销，以及冒充医疗、法律、财务或紧急服务；
- `accuracy_challenge` 只核事实/证据/覆盖/推理；`quality_reflection` 只核表达/完整性/合同摩擦；只出 finding，不改结果。

### 5.2 每份 Skill 都不要

- 输出字段表、JSON schema、task 动态值或 Website 事实副本；
- 模型名、reasoning tier、Child 名、ordinal、timeout、selector；
- checkpoint、fork、continuation、重试、状态机和业务完成算法；
- 付款、授权、入库、发布、用户终态或 Website verdict；
- include 另一八字 Skill 或成为另一 Plugin 的执行真源。

### 5.3 BZ05 Skill

要：对 exact chart/candidate set、完整 READY、nonbinding base 和 BZ02 semantic manifest 独立全盘解读；覆盖全部 required anchors；综合月令、旺衰、根气、干支、十神、格局、调候、病药、化象、合冲刑害、运限和古籍分歧；给出专业/白话双层、引用、不确定性、限制和安全说明。

### 5.5 BZ04 Skill

要：只接受 approved BZ05/BZ03 Delivery Manifest 绑定的 exact task/result/hash/auth/continuation；只答新 frozen question；明确父事实、父判断条件、当前解释、新推断和现实待核事项；说明补充是否改变父结论适用条件。

### 5.6 两份本地、字节等值的 private-base turn contract

BZ05/BZ03 的 base 回合不发送两份不同 Product Skill。两 Product 分别在自己目录直接拥有一份本地 `private-base-turn-contract` TypeScript 对象；两份 Prompt、base profile、turn marker 和 canonical base-v2 子合同组合由 active Bazi authority 冻结同一分母，在构建时必须 exact bytes/hash 等值。两 Product 零互相 import、re-export 或隐式调用；小量本地重复是现役基础法案要求的 Owner 隔离，不是第二语义真相。

- `decision: no_issue | issues`；

## 7. Product Flow 与恢复

### 7.1 BZ05/BZ03 primary：private base → isolated formal child

每个 Product 在自己的 `flow.ts` 直接写完整静态顺序。private-base 首 Prompt 只组合该 Product 本地的 §5.6 turn contract，并先通过两本地副本的同版 bytes/hash 等值门；Product 自己的 Skill 只在 formal/review Prompt 组合，不进 base 回合。

```text
01  Product 计算 exact reusable-base identity/frontier，经现有 `readContinuationExact(frontier_ref)` + opaque grant 作 zero/one read
02  zero 时在任何 Provider mutation 前经产品中性 reservation Child 以同 identity 原子插入opaque reservation，且只有抢到 lane/fence 的 creator 可 prepare clean chat；one 时逐项验证complete row/read grant 并跳到18

09  reconcile exact base attachment
10  write 本Product本地 private-base Prompt/profile/turn contract + marker
11  reconcile exact draft
12  submit private base exactly once
13  reconcile submitted base turn
14  wait stable base response
15  checkpoint raw DOM + semantic text before parsing
16  Product 从同artifact读raw，用projected current-v2 exact contract的产品中性evaluator得到opaque semantic-admission receipt

36  failure-only release in finally
```

恢复规则：

- `readCallFacts` 先于每个 mutation；当前 attempt 已有证据就读回；
- reusable-base identity 精确由 `owner_scope_hash + privacy_subject_ref + chart contract/version + chart/candidate hash + READY corpus/set hash + base output contract version + equality-accepted local base profile hash + equality-accepted local private-base Prompt/turn-contract hash` 组成；问题、经历、订单、支付和 formal product output 均不得进入；任一成员变化即失效并形成不同 identity；
- `plugin_id/product_id/job_id` 也不进入 reusable-base identity；BZ05 与 BZ03 在其余成员全等且同一 active base-contract version 时，Prompt/profile bytes/hash 必须天然等值并命中同一 row。同版不等是合同漂移，必须失败关闭，不得各建一份；只有 canonical Prompt/profile/contract 真实换版才形成新 identity；
- 同 identity 只允许零或一条 shared store 的 opaque reusable-origin row；zero 才以 unique identity 原子保留 reservation，然后才允许首次 Provider effect；one 只读 reservation/complete 事实。这不新增公开业务 status 或可扩展 phase graph；complete 只由同 row 的 artifact/semantic-admission receipt/grant 必需字段全部非空机械派生。reservation 保留 creator job、lane/fence、effect identity 和 origin provenance；creator crash 由原 task/effect 只读恢复，其它 task 不得偷取或重发。只有权威撤权且证明零 confirmed effect 才可在同 row/fence 上作有证据的撤销/转交；多条、多义、grant 错配均失败关闭；
- Product 侧用稳定 `owner_scope/privacy_subject/base_authorization` 计算 opaque identity/grant hashes，shared row 只保存hash和origin provenance；origin job/plugin/authorization 仅是来源证明。后续 paid task 必须先独立验证它自己的 current authorization 与 exact privacy scope，再经同一 `readContinuationExact(frontier_ref)` 和 owner-scoped immutable read grant 读 origin artifact；不得要求 current job/plugin/authorization 字符串等于 origin，也不得开第二 API/store；
- base origin 已持久化时，02-16 Provider mutation 增量必须为零；BZ05/BZ03 是否复用只由各自 Product 根据上述 exact facts 决定；
- base semantic invalid 时原raw/evidence不变、row不complete、零grant/fork，当前attempt以结构化失败返回。只有 Website 对同 creator task 新建的 accepted attempt 可在原 reservation/fence 上用新exact effect identity继续；旧raw作为task-owned artifact保留而不覆盖，其它 paid task 不得偷取或重发；
- fork 是独立 exact Provider effect；commit 后 return 前崩溃时按同一 task/effect identity 读回 child，绝不二次 fork；
- formal submit `CONFIRMED` 后，timeout、Target、Document、channel、process restart、lease change、attempt cap 均只读原 turn；
- 只有 Provider 明确 terminal-negative、永久业务撤权、receipt/artifact 损坏或多义，才失去 confirmed 成果恢复资格；
- formal receipt 对 BZ05/BZ03 都绑定 exact `base_artifact_hash + fork source checkpoint + child conversation/continuation relation`；BZ03 formal input/output 还机械核对该 relation；
- base raw 和 formal raw 都保存；业务结果只来自 formal raw；
- private base 不公开、不入商业结果、不产生 public route/job/report。

### 7.2 产品中性 opaque reservation Child 与既有读面

冻结 GPT law/Blueprint 另行获批后，在现有 continuation Child 组只增一个 `reserve_exact_gpt_continuation_once` 类型化原子 Child。它同时服务“无 source checkpoint 的 reusable-origin reservation”和“绑 exact source checkpoint 的 derived-continuation reservation”，共享层只见 opaque identity/owner/subject/authorization-grant/source-checkpoint hashes、lane/fence 和 receipt，不见 Bazi、private base、BZ05/BZ03、Prompt、nextStep 或业务 status。Product 只决定调用时点和输入 facts；Session Controller 只经 store port 执行 reserve/complete/acquire 的 CAS。

读回不增第三 query kind：仍走 `ProductGptTools.readContinuationExact` 的 `frontier_ref` variant，只在其中加 exact current-authorization 与 opaque read-grant hashes。无grant的普通 frontier 仍严格要求 origin task/plugin/auth 等值；有grant时也只返回 opaque origin/artifact/receipt facts，由 Product 核对自己的 owner/privacy/authorization 后决定复用。不得让 `readCallFacts` 承担 continuation 查询，不得让只读入口写 Store，不得让 Product 直接 import Store。

### 7.3 新的窄 fork Child

current GPT Capability 没有 exact checkpoint fork，这是已证实的必要 GAP。经冻结 authority 单独批准后，新增一个 typed atomic Child（最终名称由 authority 固定）：

```text
input  = exact source conversation identity + exact base turn/checkpoint receipt + Product exact call identity
effect = Browser 在 Provider 页面执行一次 exact fork
output = exact child conversation identity + source checkpoint relation + mutation/evidence receipt
```

要：Product 决定调用时点、source 和后继；GPT 只解释页面语义；Browser 执行物理动作；Forensics 保存证据；WAL 提供 `DISPATCHED/CONFIRMED/REJECTED`。Production GPT Runtime 必须把 fork 纳入 `providerEffectIds`，并让 `ProductGptFactQuery/readCallFacts(task_exact_effect)` 按同 task/plugin/version/call/input/source-checkpoint 跨 accepted attempt 返回零或唯一 exact fork effect；pending/多义失败关闭。

不要：共享层决定要不要 fork、latest conversation、近似 checkpoint、same-conversation fallback、第二 continuation store、fork 后重复 base、公开 fork route。

如果真实 Provider 没有可唯一证明的 fork 后置条件，Dynamic Proof 失败，三个 Product 不上线。

## 9. 失败、恢复与 UI
