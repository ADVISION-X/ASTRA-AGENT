# Website 自动触发的 GPT 系统自完善完整实现方案

> 状态：设计阻断
>
> 本文件是本需求当前唯一方案。它只定义未来建设方式；本轮不得创建 Skill、不得创建 Codex 自动化、不得修改法案、施工图、生产代码、数据库、Browser/GPT 状态或 `/系统分析/` 运行目录，也不构成 CHANGE、READY、RELEASE 或生产完成证明。

## 0. 最终纠偏裁决

此前方案把 Codex 变成了复盘发起者和主要分析者，属于 Owner 倒置。正确机制必须是：

```text
Website 已接纳 primary 工单
  -> Website 自动产生归属于原产品的 quality_reflection 候选
  -> Website 仅在自然空闲业务槽位授权一张复盘
  -> 原 Product Plugin 自动生成本产品专属开放问题
  -> 现役 GPT/Browser 能力自动发送并读回答案
  -> Website 校验、持久化并签发复盘接纳回执
  -> AGENT 现役结果收敛路径自动投影到 /系统分析/
  -> Codex 次日只读系统产物，核验后才决定是否调用闭环方案 Skill
```

因此：

1. **不能把它新建成第十三个 Product Plugin。** 现役法案要求 `scheduled_quality_reflection` 保留原 `subject_product_id`，并以既有 `quality_reflection` action 路由回原 Product Plugin。
2. **它在业务意义上是一种产品归属型复盘动作。** Website 是触发、授权、任务、接纳和持久化 Owner；原 Product Plugin 是本产品问题、Prompt 和 GPT Flow Owner。
3. **Codex 不发送复盘问题。** Codex 只消费已由系统自动完成并落盘的复盘产物。
4. **Skill 不是自动发送机制。** 只有 Website、AGENT Product Plugin、GPT/Browser 和结果接纳链完成生产接线后，才有资格建设下游 Codex Skill。

## 1. 当前需求与不可妥协终点

### 1.1 业务终点

在不抢占正常工单、不预留业务容量、不产生追赶债务的前提下，Website 从已经成功业务入库的 primary 工单中按产品独立百分比选择复盘候选；当且仅当 claim 时点没有任何可领取的正常业务工单且仍有业务容量时，自动授权至多一张复盘。

该复盘由原 Product Plugin 调用 GPT。GPT 必须读取当前工单资料、当前重建的生产 Prompt、两仓云仓源码和适用 authority，先开放分析、后结构化输出。Website 接纳结果后，AGENT 自动将同一结果和 Website 回执投影到本地 `/系统分析/`。Codex 每日只读上一自然日真实产物，达到停止门的不再折腾；只有被当前 authority、源码或运行证据证实的 GAP 才进入 `closed-loop-implementation-design`。

### 1.2 绝对约束

- 原 primary 工单完成永远不等待复盘。
- 正常业务绝对优先；复盘没有保留席位、最低吞吐、超时补偿或强制追赶。
- 复盘可以长期饥饿；`0` 张复盘是合法日结果，不是调度失败。
- 已取得 accepted attempt，特别是 Provider effect 已 `DISPATCHED/CONFIRMED` 的复盘，必须沿现役恢复链收敛；不得为新业务强杀或重发。
- 不能把十二个 Product Plugin 汇总成一个平均样本池。
- 不能让 GPT 的分数直接改代码、Prompt、原结果、Website verdict 或用户终态。
- 不能要求或保存隐藏 chain-of-thought；只允许可公开核验的系统模型、证据链、观察、推断、未知与结论摘要。

## 3. 当前已有事实与第一直接断裂

### 3.1 已有主链

Website 已有：

- `ai_quality_reflection_plans`；
- `ensureMissingAiQualityReflectionPlans(20)`；
- `materializeDueAiQualityReflections(client, 20)`；
- commercial maintenance 自动调用；
- `quality_reflection` task、subject identity、snapshot、result consumer、finding、completion receipt；
- `ai-quality-reflection-export.v1`。

AGENT 已有：

- 十二个 Product Plugin；
- 十三个可复盘 primary product/action 分层；
- 每个对应 `quality_reflection` route；
- 现役 GPT/Browser/Forensics/V6 结果回传链。

### 3.2 第一直接断裂

第一直接断裂不是“没有自动调用”，而是：**现役自动调用的 Owner 和顺序不足以证明它只使用自然空闲槽位。**

当前 maintenance 会先批量补 plan，再批量物化至多二十张 review job；当前 new-job selector 对所有任务仍按 `created_at, job_id` FIFO。旧复盘可以排在后来进入的正常业务之前，因此复盘可能占用业务席位。该事实不满足用户已经确认的“正常业务绝对优先、允许复盘长期饥饿”。

### 3.3 其余直接 GAP

1. 现役 scheduled policy 对所有 reviewable completed jobs 补 plan，没有逐产品百分比选择。
2. plan 一小时后批量物化，形成可积压 review job；没有“过期即放弃、不追赶”的新业务授权边界。
3. 现役 `website-agent-review-output.v1` 只有 `decision + issues[]`，无法无损表达开放分析、authority/source 读取、未知项和十一维评分。
4. 现役 review snapshot 只给出 subject result、材料引用和 evidence catalog；不能证明 GPT 实际读到全部原资料内容，也不能证明它看到当前重建的生产 Prompt。
5. 现役 export 只导出 finding；`no_issue`、完整 scorecard、raw analysis 和 Website receipt 都不能成为 Codex 的完整日输入。
6. 当前没有生产动态证据证明用户已授权的 GPT GitHub 连接能在真实复盘会话中读取双仓并绑定精确 commit。
7. 当前没有由系统自动写入 `/系统分析/` 的 result + Website admission receipt 投影。
8. 当前不存在合格的下游 Skill；已撤回的旧 Skill 不得恢复或引用。

```text

```

有限分母是十二个 Product Plugin 下的十三个 reviewable primary product/action。某 subject 只可能是：未命中抽样、命中但 24 小时内没有空闲槽、已开始复盘、复盘已由 Website 接纳、或依法取消。只有“Website 已接纳复盘”进入 `/系统分析/` 和 Codex 评分分母；未命中或饥饿不是质量样本，也不制造缺失告警。

禁止以下 Owner：

- 新的“系统自完善 Product Plugin”；
- Website 中的 Product Prompt/问题 Owner；
- AGENT 中的复盘 scheduler 或 Website task 决策器；
- Codex 作为 GPT 复盘发送者；

## 5. Website 自动触发与零抢占调度

### 5.1 触发对象

触发对象不是新产品，而是现役：

```text
product_id = 原 primary 的 product_id
action_id = quality_reflection
review_policy = scheduled-quality-reflection.v2
subject_task_ref/result_ref/result_hash = 原 primary 的已接纳结果
```

Website 继续用原 task 表、原 plan 表、原 claim、原 result consumer 和原 review ledger。不得创建第二 queue、第二 scheduler、第二 job 类型表或第二 review store。

### 5.2 候选产生

primary 取得 Website domain admission 后不触发同步 GPT。现役 Website maintenance 只做以下轻量工作：

1. 从已 admission 的十三个 reviewable primary product/action 中读取候选；
2. 按第 6 节的确定性百分比决定是否采样；
3. 对命中的 subject 以 `subject_job_id + policy_version` 幂等创建一张 scheduled plan；
4. 不在 maintenance 中物化 review job；
5. 候选只在 admission 后 24 小时内有效；超过窗口仍未取得空闲槽时，plan 进入现役 `cancelled` 终态并清理 snapshot，不补发、不累计追赶债务。

24 小时窗口的唯一消费者是“防止历史复盘抢占未来空窗”。删除它会使旧候选无限积压；增加长期 backlog、积分债务或最低完成率均无消费者，禁止新增。

### 5.3 自然空闲的精确定义

Website 在同一次 V6 claim transaction、同一 device capacity lock 内按以下顺序裁决：

1. 先收敛全部已 accepted 的 recoverable attempt；其中已开始的 reflection 也必须收敛，不能强杀。
2. 计算剩余新 grant 容量。
3. 从唯一 job 表选择所有当前可领取的**正常业务**，直到填满剩余容量。正常业务指 `action_id != quality_reflection`；人工 `accuracy_challenge` 属于用户/管理员显式业务，也排在自动复盘之前。
4. 只有本事务观察到正常业务候选为零、仍有容量、当前没有另一张 accepted reflection，才从 due 且未过期 plan 中物化并 grant **至多一张** `quality_reflection`。
5. 如果在复盘 grant 之后才到达新业务，已 accepted reflection 不被抢占；新业务使用其余容量或等待该原子 Provider turn 收敛。这是现实副作用安全边界，不是假装数学零延迟。

这一定义不承诺复盘吞吐。连续有正常业务时，复盘可以永久为零。

### 5.4 旧计划切换

未来施工切换前：

- 停止现役 maintenance 的批量 materialization；
- 已 accepted 或已有 `DISPATCHED/CONFIRMED` effect 的 review 继续按原合同收敛；
- 尚未物化的旧 `scheduled-quality-reflection.v1` plan 由 Website 在一次可审计事务中标记 `cancelled`，不触发 Provider；
- 已物化但从未 accepted 的旧 review job 由 Website 按现役撤权/取消路径关闭；
- 不删除历史 result、finding、receipt、WAL 或 effect fact；
- 不保留 v1/v2 双 materializer、fallback 或兼容 reader。

## 6. 十二 Product Plugin 的精确抽样

### 6.1 抽检与全检的唯一含义

- **GPT 抽检**：Website 只让命中本表百分比的 admitted primary 成为 24 小时复盘候选；它控制真实 GPT 负载。
- **GPT 全检**：某一 product/action 的比例为 100%；当前仅付款截图观察采用。100% 仍只表示“全部进入候选”，不承诺取得空闲槽。
- **Codex 核验**：对实际完成并落盘的 GPT 复盘 100% 核验，不再做第二轮百分比抽样。

这样只有一层百分比，不会出现“GPT 全跑一遍、Codex 再抽一次”的重复成本和概念混淆。

### 6.3 可复算选样

Website 只使用确定性公式，不建立 sampling 表或人工清单：

```text
bucket = first_uint64(
  sha256(policy_version + "\0" + product_id + "\0" + primary_action_id + "\0" + subject_job_id)
) mod 10000

selected = bucket < rate_percent * 100
```

同一 policy version 和 subject 永远得到同一结果。百分比按 product/action 单独计算，不保证小流量产品每日最少一张；否则“最低一张”会变成保留容量和追赶债务。政策率未来只能在 confirmed GAP 的唯一方案中逐产品调整，不允许 GPT 自己修改。

上线 canary 阶段不新增“校准状态机”。需要对某个 product/action 临时全检时，只能在同一 Website sampling policy 中把该分层的比例原位改为 100%，并绑定明确验收与恢复率；不得从一个产品推导其它产品。改变了该产品的 Skill、Prompt、材料合同、result contract 或 consumer 后，闭环方案必须判断是否需要把**受影响分层**临时升到 100%；没有当前 GAP 和消费者证据时不得自动扩大全检。

## 7. GPT 真正取得的输入

### 7.1 工单资料包

review task 必须让原 Product Plugin 真实取得并交给 GPT：

- subject job/product/action/request hash；
- subject result ref/hash 和 Website domain admission receipt/hash；
- 原业务参数的合法投影；
- 原工单全部 material 的 role、ordinal、display name、media type、bytes、hash 与真实内容；
- 原 result payload；
- 与当前 subject 对应的公开运行证据引用；
- review policy 和唯一输出合同。

不得只给 material ref 列表却声称 GPT 看过内容。原材料继续引用 Website 现役 object/blob，不复制第二份长期存储；review job 只建立现役 task material binding。

### 7.2 当前生产 Prompt

Website 不得保存或下发 Product Prompt。原 Product Plugin 在 review 执行时，用冻结 subject task/material 和**当前 Product 源码**调用同一纯 Prompt builder，重建“如果当前版本处理这张 subject，会提交什么生产 Prompt”，并把该文本作为本次 GPT review turn 内的被审证据。

必须明确标注：

- `current_reconstructed_prompt`：当前版本的可复算 Prompt；
- `historical_executed_prompt`：若现役 Forensics 没有权威保存，则为 `not_observable`，不得把当前重建值冒充历史值。

不得为历史 Prompt 新建数据库、Website 字段或第二 Forensics store。用户当前要优化的是现役系统；当前重建 Prompt 已满足真实 consumer。若未来另有“逐字追溯历史执行 Prompt”的明确需求，再单独证明其存储必要性。

### 7.3 双仓云仓源码

用户已说明当前 GPT 账号拥有 GitHub 权限，但“权限已开”不等于“本生产 Flow 已证明能读”。目标机制要求 GPT 使用该连接直接读取：

- `ADVISION-X/xuanxue-web` 当前云仓 `main`；
- `ADVISION-X/AGENT` 当前云仓 `main`；
- 从本 product/action 的 authority、producer、consumer、Prompt builder、合同和 tests 继续追踪，不限于预选摘要。

GPT 必须返回每仓的 `observed_commit` 和 `repo@commit:path#symbol-or-line` anchor。`source_status=exact` 的含义是：GPT 明确声明它从云仓 `main` 观察到该 40 位 commit，且本仓所有 anchor 都精确绑定同一 commit；Codex 还能从远端对象读回这些 anchor。它不是“GPT 说看过了”即可成立。无法得到精确 commit 时仍保存其分析，但标记 `SOURCE_UNVERIFIED`，该结果不能通过高分停止门，也不能直接形成修复方案。

生产启用前必须做真实 canary：在 fresh GPT chat 中，每仓读取一个由验收者临时选择、未把答案写进 Prompt 的 exact path，返回 commit、anchor 和一条内容事实；Codex 对同一 remote commit 独立核验。两仓都通过后才能声称“GPT 能拿到双仓云仓源代码”。不得用本地源码附件、人工粘贴摘要或默认分支猜测静默降级。

### 7.4 当前分析过程

允许 GPT 和 Codex 保存的是可公开核验的分析产物：使用了哪些 authority/material/source、系统模型、事实、推断、未知、替代解释、第一直接断裂和下游影响。不得要求 GPT 暴露隐藏思维链。

- 每一项 `>= 4`；

- 两仓 source binding 均为 exact；
- 无 `material|critical` finding；
- 无 subject/material/identity/privacy/effect/admission/second-owner 硬门；

- 证实是当前 GAP：交给闭环方案 Skill；

## 14. 验收矩阵

### 14.1 自动触发与容量

- primary admission 不等待 plan、GPT 或本地投影。
- 正常工单存在时 new reflection grant 恒为零。
- 多个空闲容量也至多新 grant 一张 reflection。
- 连续业务 7/30/90 天时 reflection 可为零，系统不积累补偿债务。
- accepted reflection 的 submit 至多一次；新业务到达不导致 replay。

### 14.2 GPT 输入与开放性

- GPT 真实读到 material bytes，不只是 ref 清单。
- 当前重建 Prompt 可由同一 Product builder + subject 输入复算。
- GPT 能用自己的话说明意图、产品特有风险和未知。
- 输出允许零 finding；无最低字数；开放分析先于 scorecard。
- 人为注入“代码与法案冲突”时只报告 lower-level drift。
- 两仓 exact path/commit/content canary 可由 Codex独立复核。

### 14.3 持久化与 Codex 边界

- Provider 回答但 Website 未 admission：`/系统分析/` 文件为零。
- Website admission receipt 读回后：恰好一个 immutable 文件。
- reconciliation 重放：同 hash 零新增，异 hash 不覆盖，Provider submit 增量零。
- Codex 只读文件不会创建 Website task 或 GPT turn。
- `>=92` 且所有硬门通过：无修复方案变更。
- 只有 confirmed current GAP：进入 closed-loop 方案；仍不自动施工。

### 14.4 原生质量

```text
AGENT:   npm run quality:check -- CHANGE|READY|RELEASE
Website: pnpm quality:check -- CHANGE|READY|RELEASE
```

每仓只认唯一原生 verdict；GPT 分数、Skill 自检、单测、canary 和文件落盘都不能冒充 READY/RELEASE。

## 16. 四个问题的直接答案

1. **GPT 能不能拿到双仓云仓源代码？** 设计上能，依赖用户已开放的 GitHub 连接；当前还不能宣称生产已证明。必须通过两仓 fresh-chat exact commit canary，失败时保存为 `SOURCE_UNVERIFIED`，不得降级冒充。
2. **GPT 能不能明白问题意图？** 目标 Prompt 先让 GPT 自述系统目标、产品特有风险和未知，再自由分析，最后评分；若只重做业务答案、泛化代码审查或逐格填表，Codex 判 `REVIEW_INTENT_MISUNDERSTOOD`。
3. **本地结果能不能帮助 Codex？** 能，但文件必须由系统在 Website admission readback 后自动写入，包含 raw v2、subject identity、result hash 和 Website receipt；只有这些事实齐全，Codex 才能复算评分、核验 anchor 和启动闭环方案。
4. **抽检和全检是否精确划分？** 是。Website 对十三个 product/action 分层用各自百分比选择 GPT 候选；付款截图 100%。Codex 对实际完成的复盘 100% 核验。产品之间不合并分母、不平均、不互相放行或封锁。

1. 用户审阅并明确批准本方案；
2. 用户明确授权命中的 frozen active law、Blueprint 和跨仓合同原位替换；

5. 两仓 GPT GitHub canary 证明技术可行；
6. 删除门复核后没有可以删除且不损害闭环的新增结构。
