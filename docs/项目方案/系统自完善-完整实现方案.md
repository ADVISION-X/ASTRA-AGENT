## 0. 终态裁决

AI分析复盘中心不是第二质量系统，不重新完成业务，不给 AI 做满意度问卷，不生成第二份正式结果。

它只做一件事：对已经取得 Website 业务接纳完成事实的真实工单，使用原 Product 的 quality_reflection 路由执行一次结构化生产后审计，把 Prompt、资料组织、结果表达、合同摩擦、上下游交接和工具/流程摩擦投影成现役 finding；Website 保存唯一事实；Codex 后置读取当前双仓代码、法案、施工图和质检对 finding 二次核真。

唯一终态链：

```text
Website primary business completed
  -> existing ai_quality_reflection_plans
  -> completed_at + 1h due
  -> existing materializer creates original-product quality_reflection job
  -> Website claim: normal new business first; new reflection only when no eligible normal new job
  -> original Product Plugin engineering audit prompt
  -> existing GPT / Browser / WAL / Runtime
  -> existing website-agent-review-output.v1
  -> Website only checks JSON/basic field types and preserves the complete reply
  -> existing review challenge + findings + completion receipt
  -> /admin/ai-acceptance existing reflection center + existing export
  -> scheduled Codex read-only verification against current dual repos
  -> confirmed current GAP only -> closed-loop-implementation-design
```

不新增 Product Plugin、review executor、队列、scheduler、数据库、状态机、review schema、AGENT 本地投影、第二质量 verdict。

## 1. 硬边界

### 1.1 AGENT 基础设施零改

本项目禁止修改：

- src/capabilities/**
- src/lib/**
- src/mediator/**
- Browser / Target / Document / WAL
- Runtime DB / Outbox / Attempt / Lease / Fence / Recovery
- GPT Child / GPT public facade
- startup / app-shell / runtime-log-spine
- AGENT 生成的 website-agent route-policy projection

AGENT 只允许修改原十二个 src/plugins/<product>/** 下的 Product-owned SKILL 与 Product-owned Prompt/Flow；每个 Product 仍走现役 quality_reflection action。

### 1.2 Website 不持有 Product Prompt

Website 只拥有 subject identity、材料事实、业务完成事实、route contract、review plan、finding、receipt、导出和管理员投影。Product Skill、Provider-facing Prompt、模型策略和 Product Flow 继续只属于 AGENT Product。

### 1.3 复盘 AI 不读云仓源码

Provider 复盘只针对冻结工单事实与当前 Product 自身规则生成 finding。双仓源码、active law、Blueprint、实现和质检的核真属于后置 Codex。

理由：现役 finding consumer 强制 target_ref/evidence_refs 来自冻结 evidence_ref_catalog；让 Provider 直接生成 GitHub source anchor 会迫使现役 evidence contract、route contract 和 AGENT 基础设施扩张，且与“先积累问题线索、再交给 Codex 核真”的职责重复。

### 1.4 复盘不是准确性 challenge

quality_reflection 审计生产环境与链路摩擦；manual accuracy_challenge 继续负责人工发起的准确性复核。二者不得合并。

### 1.5 AI 回复只做基本格式接纳

Provider 回复的保存与完成只允许以下门禁：

1. 现役 result envelope、job/product/action、subject/plan identity、对象 ref/hash/bytes/readback、事务幂等与 completion receipt 必须成立。
2. payload 是可解析 JSON object。
3. payload 含 `decision` 与 `issues[]`；`decision` 只区分 `no_issue` / `issues`，并与数组空/非空一致。
4. 每个 issue 是 object，现役八个 finding 字段具有基本类型：七个非空 string 与一个 string array；`evidence_refs` 允许空数组。

除此以外不得阻断保存、finding 投影或 reflection 完成。特别禁止把以下内容作为 admission gate：category/confidence 枚举、evidence/target 是否命中 frozen catalog、issue 数量上限、单字段字符数、未知附加字段、观点正确性、结论质量、是否重新回答原业务、是否给出 score/review_summary/repair_plan。

Provider-facing Prompt 仍可要求理想格式、证据引用和职责边界；这些要求只用于提高输出质量。违反这些要求的回复仍保存并进入 `pending_triage`，由后台和 Codex 后置核真，不得触发同一 Provider 请求重做。

## 2. 当前直接 GAP

### GAP-01：复盘对象不是“真正已完成工单”

当前 services/api/src/ai-production/quality-reflection-schedule-repository.ts 的 completedEligibleJob、persistQualityReflectionPlan、ensureMissingAiQualityReflectionPlans 只以 terminal_status=completed + result_json 非空作为资格，并以 terminalized_at + 1h 计算 due_at。

但系统真实业务完成只在 services/api/src/ai-production/business-result-consumer.ts 成功写入 status=completed、business_consumed_at、business_consumer_ref、business_consumption_hash 及领域/复盘 receipt 后成立。

第一直接断裂：技术结果完成被提前当成复盘的业务完成。

### GAP-02：现役 Product quality_reflection Prompt 过薄

十二个 Product 当前复盘指令主要只有“复核表达、完整性、合同摩擦与质量风险，返回 finding”。它不能稳定重建并检查：目标 -> 材料 -> Prompt -> Result Contract -> 回答 -> Website 接纳。

### GAP-03：新复盘与正常新业务同一 created_at FIFO

job-claim-selection.ts 当前按 created_at,job_id 读取 new candidate。已经物化的旧 quality_reflection 可能排在后来进入的正常业务前面。

### GAP-04：Codex 导出缺少复盘执行身份

现役 reflections/export 只导 finding；没有 child_job_id、snapshot_hash、structured_output_hash、finding_count，Codex 不能从一条 finding 精确绑定产生它的 reflection job/result。

### GAP-05：AI 回复保存被语义门禁卡死

现役 `website-agent-result-payload-contract.ts` 与 `quality-reflection-finding-repository.ts` 重复执行内容级校验：固定 category/confidence 白名单、1-50 issues、每条至少一个 evidence ref、target/evidence 必须命中 frozen catalog，以及多个文本长度上限。

真实运输顺序已经先保存 `result_payload` object 与 result envelope，再由 business result consumer 读取 payload。第一直接断裂发生在 consumer：已保存且身份/hash/bytes 完整的 AI 回复，因为主观内容或引用质量不符合规则而不能完成消费，进而把内容质量问题错误升级为生产恢复问题。

不得增加第三材料，不修改 40-route canonical artifact，不修改 AGENT projection。

```text

subject.route_contract
subject.business_completion
```

其中 business_completion 固定投影现役字段：

### 3.2 原材料边界

现役两材料合同不允许重新附加 subject 的原始附件集合，因此 quality_reflection 不冒充“重新查看所有二进制原件”。它检查材料包的 identity、role、ordinal、media type、hash、组织与实际结果的消费迹象；需要重新判断原图、原 ZIP、原 PDF 内容准确性的事项属于 accuracy_challenge 或后续人工/专项验证。

这条边界必须写进 Product audit protocol，禁止模型声称看过未附加的原材料正文。

## 4. 调度终态

### 4.1 资格

每张支持 quality_reflection 的 primary 工单只要满足以下条件，就创建一张现役 plan：

```text

r.business_consumed_at IS NOT NULL
j.result_json IS NOT NULL
action_id NOT IN (accuracy_challenge, quality_reflection)
product supports quality_reflection
no existing plan for subject_job_id
```

不做逐产品百分比抽样，不做评分触发，不做人工名单。

### 4.2 时钟

```text
captured_at = business_consumed_at
due_at      = business_consumed_at + 1 hour
```

现役 90 天 snapshot retention 保留。不得增加“完成后 N 分钟”的第二时钟。

### 4.3 正常业务绝对优先

不恢复已删除 service_class，不建 priority 表，不建第二 queue。

只在 Website 现役 selectV6ClaimableJobs() 内改 new-grant 选择逻辑：

1. accepted/recoverable attempt 继续按现役逻辑收敛，包括已开始的 reflection；不得强杀。
2. ordinary new candidate 扫描时，遇到尚未 accepted 的 quality_reflection 先保存为最多一个 deferred candidate，不立即 selected。
3. 继续沿当前 cursor 扫描并执行现役 route/material/privacy/manifest eligibility 检查。
4. 只要发现一个可领取的非 quality_reflection new job，本次 claim 的 new reflection grant 数恒为 0。
5. 扫描结束仍没有可领取的 normal new job、仍有 new capacity 时，才 selected 最早的一个 deferred reflection。
6. 单次 claim 最多新 grant 一张 reflection。
7. exactJobIds、deliveryOnly、source handoff、recoverable 路径语义不改变。

这只改变 new job 的选择顺序，不产生新状态。

## 5. Product 工程审计协议

每个 Product 自己拥有 quality_reflection Prompt。禁止中央 shared audit Prompt/executor。

共同协议名固定为 post-completion-production-audit.v1，但协议正文物理落在各 Product SKILL/Prompt 内；公共基础设施不知道其文本。

### 5.1 执行阶段

每个 Product 的 quality_reflection 单 turn 固定执行以下阶段：

#### A0 Subject Gate

- 核对 review_policy、subject task/result/hash、audit_protocol、business_completion。
- 明确这是已完成工单的后置审计。
- 禁止重新回答原业务问题，禁止生成第二正式结果。

#### A1 Goal Reconstruction

- 从 subject parameters、当前 Product Skill、subject route contract 重建原业务目标、非目标和交付边界。
- 不从最终回答倒推并改写原目标。

#### A2 Current Prompt Audit

- Product 使用自己现役 primary Prompt builder 或同文件纯函数，根据冻结 subject 参数与 material metadata 形成 current reconstructed prompt。
- 只审计“当前代码处理同一 subject 会形成的 Prompt”；不得声称它等于历史 executed Prompt。
- 检查目标是否明确、约束是否冲突或重复、Prompt 与材料角色/route contract 是否对齐、是否存在必须猜测的隐式要求。

#### A3 Material Package Audit

- 检查 role/ordinal/display name/media type/hash/subject-parent identity 是否清楚。
- 检查 Product 需要的信息是否在 material manifest 中有明确来源。
- 不读取不存在于本次 review task 的原始二进制正文，不伪造内容级结论。

#### A4 Result Audit

- 对 subject_result 检查目标覆盖、重复、遗漏、表达阻力、条件/不确定性、引用/证据使用和 result contract 造成的摩擦。
- 不用新的正式答案替换它。

#### A5 Handoff Audit

- 检查 frozen task -> Product -> result contract -> Website business completion 的事实链。
- 只使用 review_context 中的冻结事实，不评价未观察源码。

#### A6 Root-cause Fold

- 同一根因造成的多个症状只保留一条 finding。
- finding 指向最早的直接断裂，而不是堆下游症状。
- 没有可证问题时 decision=no_issue。

#### A7 Emit

严格返回现役 website-agent-review-output.v1：decision + issues[]。

每条 issue 继续只含：

```text
category
target_type
target_ref
observation
evidence_refs
impact
confidence
suggested_inspection
```

不得新增 score、review_summary、authority_trace、source_anchor、emotion、satisfaction、repair_plan、第二结果字段。

### 5.2 finding 规则

- 允许 0 finding。
- 不设最低字数、最低 finding 数量、最高 finding 数量、字段字符数或评分阈值。
- observation 只写观察到的事实与必要限定；推断必须明确写为推断。
- Prompt 要求尽量引用 frozen evidence_ref_catalog，但 Website 不校验 membership；空 `evidence_refs` 也必须保存。
- suggested_inspection 只告诉 Codex 下一步核什么，不给出施工方案。
- 禁止为了覆盖 category 而制造 finding。

以上均为 Product 输出质量指导，不是 Website 保存门禁。category/confidence 的推荐值继续提供给模型和后台筛选，但 Website 接受任意非空 string；未知附加字段保留在原始 result payload，finding 投影只消费现役八字段。

## 14. 最终施工定义

```text
真业务完成事实
+ 一小时后台复盘
```
