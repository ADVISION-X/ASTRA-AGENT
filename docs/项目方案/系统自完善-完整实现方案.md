## 1. 需求、Owner 与业务终点

### 1.1 需求

对 Website 成功接纳并持久化的每一张 primary 工单，建立一张独立、非阻塞的系统复盘任务。复盘 GPT 必须同时利用：

1. 该工单冻结的业务身份、资料包、结果和可公开执行证据；
2. 精确绑定的 AGENT 与 Website 云仓候选源代码；
3. Product Plugin 当前 Skill、Prompt 构造、Flow、合同、consumer、失败与恢复边界；
4. 当前复盘上下文中可公开的观察、假设、证据路径和结论摘要。

GPT 对双仓必须先按上位规范到实现的固定顺序完成 authority gate：先读法案系统建设说明书、基础/功能法案和适用依赖，再读 Blueprint、spec、Manifest、registry 投影，最后才读实现代码、证据和历史。authority 未闭合时不得评价代码；代码冲突只能报告为下级漂移，不能反向改写法案。

GPT 在 authority gate 通过后自主重建系统并开放深挖，再进行反向攻击和删除反事实，最后填写固定评分卡。评分达到稳定阈值且不存在硬门问题时，只归档和进入趋势观察，不启动无收益的改造；低分或硬门问题只获得 Codex 深查资格，不能直接授权修改。

每天由 Codex 回读上一自然日的全部复盘结果，但不对所有高分结果一律执行同等深查：风险结果全检，达到停止门的结果按十二个 Product Plugin 各自的比例抽检。抽检率、最低样本、全检触发和退出条件都按 Product Plugin 独立计算，禁止把十二个产品汇总成一个平均分或共享样本池。只有被当前源代码、法案、施工图、合同或运行证据证实的 GAP，才进入现役 `closed-loop-implementation-design`；由该 Skill 按 GAP 的真实需求 Owner 选择或更新唯一方案，不把所有产品问题追加到本建设方案形成台账。

本方案区分两个覆盖层，避免“抽检”含义不清：

1. **GPT 复盘覆盖率：100%**。每个取得 Website admission 的 reviewable primary job 都产生一份非阻塞 GPT 复盘，满足“每个工单完成后补充一轮询问”的原始要求；
2. **Codex 深度核验覆盖率：风险全检 + 高分按产品百分比抽检**。百分比只作用于已经满足 `ARCHIVE_ONLY` 候选条件的复盘，不允许低分、缺证据或硬门结果借抽检逃逸。

### 1.2 唯一 Owner

| 原子责任 | 唯一 Owner | 权威输出 |
| --- | --- | --- |
| primary 工单业务完成 | Website 对应领域 consumer | 同一 `job_id + result_payload_hash` 的 domain admission/delivery readback |

| 复盘接纳和 finding 持久化 | Website `ai-acceptance` | 原始 result hash、plan completion receipt、review findings |
| 每日导出 | Website 现役 reflection export consumer | candidate-bound、hash-bound export |

### 1.3 权威业务终点

本机制的完成终点不是 GPT 已回答、文件已落盘或得分已计算，而是：

1. 昨日分母内每个 Website-admitted primary job 都能读回恰好一份 reflection plan；
2. 每个 plan 都能读回完成、失败、恢复中、取消中的现役状态；
3. 完成 plan 能读回原始 GPT result hash、finding count 与 completion receipt；
4. 当日首次成功 Website export 的 canonical snapshot hash 校验通过，返回的原始 bytes 只写一次到 `/Users/nexgen/Documents/AGENT/系统分析/<日期>/原始复盘导出.json`；文件 SHA-256 记录在同日唯一核验结论中；
5. 当日十二个 Product Plugin 各自的 admitted 分母、全检数、抽检率、应抽数、实抽数和选中 job identity 均可复算；
6. Codex 对进入全检或抽中的每条候选 finding 给出已证实、已过时、证据不足、重复或 authority 冲突的唯一核验结果；
7. 只有已证实 GAP 才交给现役闭环方案 Skill；没有已证实 GAP 时不得为了“持续优化”制造或更新任何方案。本文件只在自完善机制自身存在 confirmed GAP 时更新。

原 primary 工单的业务完成永远不等待上述复盘终点。

## 4. 当前事实与第一直接断裂

### 4.1 已有合法主链

Website 已有：

- `ai_quality_reflection_plans`；
- completed primary job 快照；
- `quality_reflection` task 物化；
- `website-agent-review-output.v1` 接收；
- challenge、finding、人工 triage、plan completion receipt；
- 管理员 reflection export。

AGENT 已有：

- 每个现役 primary Product Plugin 自有的 `quality_reflection` route；
- clean GPT chat、同一 V6 task/result 主链、现役 Browser WAL 与 Forensics；
- Product Skill 中的“只审不改”边界；
- Website route policy 的 current projection。

### 4.2 第一直接断裂

Website `ai-acceptance` 已实现以下函数，但当前源代码没有任何运行时 consumer：

- `ensureAiQualityReflectionPlan`；
- `ensureMissingAiQualityReflectionPlans`；
- `materializeDueAiQualityReflections`；
- `expireAiQualityReflectionSnapshots`。

因此第一处直接断裂是：**Website 已拥有 plan producer 与 result consumer，却没有 Owner 调用 producer/物化器，completed primary job 不会自动进入 reflection 主链。** 下游 consequence 是没有可靠的逐工单 GPT 复盘、没有完整日导出，也没有 Codex 日读输入。

### 4.3 同一主链内的直接 GAP

1. `ensureAiQualityReflectionPlan` 会跳过同 lineage 的较旧 completed job，持久化时还会 supersede 同 lineage 的待执行 plan；这与“每张工单恰好一份复盘”冲突。
2. 现有 export 只读取 `ai_production_review_findings`；`decision=no_issue` 的完成复盘没有 finding row，不能证明逐工单覆盖。
3. 现有输出只有 `decision + issues[]`，不能表达开放式系统模型、意外发现、未知项、删除反事实和逐维评分。
4. 当前 claim 按 `created_at, job_id` 选择；物化后的 reflection job 可能排在后来创建的 primary job 前面，存在辅助复盘占用用户业务席位的风险。
5. 当前本地不存在 `/Users/nexgen/Documents/AGENT/系统分析/` 的唯一投影合同和 Codex 日读 Skill。
6. 当前冻结边界禁止 Prompt 正文进入 Browser reply、日志、WAL、proof 或跨仓 task/result。目标设计允许复盘 GPT 通过云仓读取 Prompt 构造源代码，也允许读取当前授权复盘包和可公开执行证据，但当前没有动态证明生产 GPT 身份已连接并能读取两个私有云仓的 exact commit；在预检完成前不能把“可读取”写成已证实事实，也不得伪称已取得未被真实提供的历史 Prompt bytes 或隐藏思维链。
7. 当前方案此前只有全局三十张校准和七日 finding 趋势，没有十二个 Product Plugin 各自的抽检率、最低样本、全检触发、退出条件和专属问题分母；这会让高流量产品吞掉低流量产品，也无法证明 Codex 的日读结论针对了正确产品。
8. 当前方案此前要求 GPT 读取双仓源码，却没有冻结“authority 先于实现”的读取顺序；GPT 即使拥有 GitHub 权限，也可能先观察代码后反向挑选支持代码的规则，把现状误当规范，导致整个自完善机制优化到错误方向。

### 5.2 分母

复盘分母精确为目标日内取得 Website 业务 admission 的全部 primary action；排除：

- `accuracy_challenge`；
- `quality_reflection`；
- 未取得 Website 业务 admission 的 staged/terminal/Outbox 结果；
- 已取消、已删除或 privacy 已关闭且依法无法复盘的任务；
- 无 review route 的 `localization_static_catalog + produce_locale_catalog`，除非未来另获 active law 和合同授权。

每个分母成员只能出现以下投影终态之一：

| 终态 | 含义 | 原 primary 状态 |
| --- | --- | --- |
| `scheduled` | plan 已持久，未到期 | 保持 completed |
| `materialized` | reflection job 已创建 | 保持 completed |
| `completed` | 原始 result hash、findings 与 receipt 已入库 | 保持 completed |
| `recovery_pending` | reflection 自身按现役 attempt 恢复 | 保持 completed |
| `cancelled` | privacy/授权撤销 | 保持 completed 或依法删除 |
| `missing_projection` | 查询时应有 plan 而不存在；仅为只读导出投影，不新增 DB 状态 | 保持 completed，Website scheduler 修复 |

不得保留 `superseded` 作为“每张工单复盘”正常终态。历史行按迁移事实处理，目标代码物理删除同-lineage supersede producer 与唯一 scheduled-lineage index。

## 7. GPT 深度复盘设计

### 7.1 核心原则：开放分析在前，评分在后

固定评分维度只负责让不同工单可比较，不得成为 GPT 的思考边界。Provider-facing 指令必须明确：

1. 在看到评分维度后也不能按维度逐格复述；先自主重建实际系统；
2. 可以提出不属于既有类别的意外观察，但最终 finding category 必须归入 canonical 枚举；无法无损归类时写入 `unknowns`，不得硬塞；
3. 不设最少 finding 数量，不要求“必须找问题”，也不奖励内容长度；
4. 必须区分事实、推断、未知和建议核查；
5. 必须寻找第一直接断裂与最高杠杆点，而不是罗列最后报错或润色意见；
6. 必须检查删除一个结构是否仍能闭环，优先发现重复 Owner、第二真相、无 consumer 输出和兼容残留；
7. 评分在全部开放分析完成后给出；GPT 看不到 Codex 的分流阈值；
8. 不输出修复代码，不改原结果，不替 Website/Codex 作最终裁决。

### 7.2 GPT 必须真实取得的输入

#### A. Website 冻结 subject 包

- subject job/product/action/request hash；
- subject result ref/hash 与 Website business admission receipt/hash；
- 原始业务参数的允许投影；
- 原始资料的完整 role、ordinal、display name、media type、bytes、hash 与可读取内容；
- result payload；
- evidence ref catalog；
- failure/recovery/admission 的脱敏事实摘要；
- review policy 与输出合同。

原材料不得复制成第二存储。reflection task 继续引用 Website 已有 material object/blob；只有当前 task-owned 临时下载与 Provider 上传别名可存在，settle/abort 后按现役 Owner 清理。

#### B. 精确云仓源代码

这里描述的是目标能力合同，不是已经取得的生产事实。用户已确认其 GPT 账号已经开放 GitHub 权限；这是合法能力输入，但不自动证明生产复盘会话能读取两个私有仓库的任意指定 commit。当前代码只能证明 AGENT 会把 Prompt 和批准附件提交给 GPT，不能证明 GitHub connector 的实际 repo scope、commit scope 和内容 readback。因此施工前仍必须把“双仓云仓访问预检”列为独立阻断门，预检未通过时不得用源码附件、粘贴摘要或本地 checkout 静默降级冒充云仓读取。

复盘任务必须向 GPT 声明并要求读取：

- `ADVISION-X/AGENT@<requested_commit>`；
- `ADVISION-X/xuanxue-web@<requested_commit>`；
- 当前 product/action 的 Product Skill、Prompt 构造、Flow、route policy、跨仓 spec、Website sender/consumer、状态转换与相关 tests；
- 与 finding 直接相关的 active law 与 Blueprint 位置。

目标访问方式只有一个：当前生产 GPT 身份通过已授权的云仓连接直接读取两个仓库的 commit tree 与文件内容。它不要求 GPT 一次把全仓所有 bytes 装进上下文，但必须允许 GPT 从 Product 专属起始路径继续追到真实 producer、consumer、合同、测试及关联 authority，而不是只能看到预先挑选的几个片段。

首次启用以及 GPT 身份、云仓连接、权限范围或仓库可见性改变后，分别对两个仓执行真实预检：

1. 在 fresh chat 中请求打开一个精确 commit，而不是默认分支的当前页面；
2. 每仓读取由 Codex 临时选定、未在固定 Prompt 中泄漏答案的一个已存在路径；完整 authority、Product 和 consumer 覆盖由随后的真实 canary 负责，不在预检重复；
3. 返回该路径的 symbol/line anchor 和一条可由指定 commit 独立核验的内容事实；不强制 connector 未承诺暴露的 blob OID；
4. Codex 从同一远端 commit 独立读回并核对；
5. 两仓全部相等才允许当次 canary 继续；预检证据进入现役 RELEASE proof，不新增 `cloud_source_capability` 运行状态、表或登记文件。任一仓无权限、只看到默认分支、commit 漂移、路径不可读或内容事实不符时停止启用复盘，不进入弱化模式。

GPT 必须返回每仓 `requested_commit`、`observed_commit` 和 `exact|mismatch|unverified`。任一仓不是 `exact` 时，评分为不可用于高分停止门；仍可保存观察，但 Codex 必须按 `SOURCE_BINDING_NOT_EXACT` 重新核验。

不允许只说“已查看云仓”。每条源码 finding 至少给出一个：

```text
repo@commit:path#symbol-or-line-anchor
```

Website 只校验结构、仓名、commit 格式和非空 anchor；Codex 次日验证路径、symbol/line 与内容是否真的支持 finding。

因此对“GPT 能不能拿到双仓云仓源代码”的准确回答是：**目标机制可以做到，但当前尚无动态证据证明生产 GPT 身份已经做到；只有上述双仓预检和逐次 exact binding 通过后才允许声称能做到。**

#### C. 当前分析过程

“分析过程”只指可公开和可复核的信息：

- 当前系统模型；
- 使用了哪些材料、源码 anchor 和运行证据；
- 哪些是观察、哪些是假设；
- 从第一直接断裂到下游 consequence 的简明理由；
- 未能取得的事实和为何不能取得；
- 反证或替代解释。

不得请求“展示完整思维过程”“逐 token 推理”或其它隐藏 chain-of-thought。

#### D. 法案先于代码的强制阅读顺序

GitHub 权限只解决“能够读取”，不决定“什么拥有解释主权”。GPT 对两个仓库的读取必须遵守每仓现役《法案系统建设说明书》第 4.2 节的单向 authority 顺序；不得从实现反推、缩小、扩张或改写上位规范。

开始时允许机械读取仓库根目录和文件树以定位下列对象，但在 `AUTHORITY_GATE=SATISFIED` 前不得形成任何代码质量、架构合理性或修复结论。每仓的强制顺序为：

```text
0. 本次 reflection 的 subject identity、用户目标、允许范围和明确非目标
1. 仓库根 AGENTS.md：只取得操作与授权边界，不把它冒充 active law source
2. docs/governance/法案系统建设说明书-冻结定稿版.md
3. .github/instructions/agent-rules/基础法案.md
4. .github/instructions/agent-rules/功能法案.md
5. 与当前 product/action、Owner、合同、状态和证据直接相关的 active lawIds 及 dependsOnLawIds 闭包
6. active law 明确需要的系统或 capabilityDomain Blueprint
7. active law/Blueprint 引用的 spec、跨仓 provider contract 与 consumer dependency
8. 相关 capabilityDomain 的 Owner Manifest
9. 唯一 law-registry.generated.json：只核对投影是否忠实，不从 registry 创造或修改规范
10. 当前 exact commit 的实现代码：入口、producer、consumer、状态、持久化和恢复
11. 当前候选 tests、原生 quality 声明和获准运行证据
12. Git 历史、旧报告和讨论材料：只用于解释漂移，永不取得当前主权
```

双仓之间也有固定顺序：先读取 Website 的业务需求、admission、canonical provider contract 和 ai-acceptance authority；再读取 AGENT 的 consumer dependency、Product Plugin、GPT/Browser/Runtime authority；随后才比较两仓 handoff 和实现。Website 的业务主权不能被 AGENT 实现反推，AGENT 的 Product/GPT/Browser 内部主权也不能被 Website 猜测替代。

进入代码阶段前，GPT 必须先在自己的工作上下文中形成一份 authority gate：

- 当前 subject 对应的 Website 与 AGENT applicable lawIds；
- 每个相关 Owner 及其权威输出；
- 适用 Blueprint/spec/Manifest/registry refs；
- 高低层冲突、缺失、陈旧投影或无法确定项；
- 代码阶段允许验证的明确法案义务和禁止项。

任一适用 active law、依赖闭包、Owner 或跨仓合同无法确定时，固定为 `AUTHORITY_UNRESOLVED`，停止产生代码优劣和改造结论。下级对象与上级冲突时只允许报告 `LOWER_LEVEL_DRIFT`：指出上级期望、下级实际和 downstream effect；不得以“代码已经这样运行”为由降低法案，也不得用 generated registry、测试、历史报告或 GPT 自己的最佳实践覆盖 active authority。

代码阅读完成后，结论必须按以下单向链表达：

```text
适用 authority 原文义务
-> Blueprint/spec/Owner 应有结构
-> 当前 exact-commit 实现事实
-> 相等或 GAP
-> consumer 后果与证据
```

禁止的反向链为：

```text
看到实现
-> 猜测设计意图
-> 选择支持该实现的历史文档或局部规则
-> 宣称法案应当如此
```

### 7.3 Provider-facing 开放式主问题

以下文本是目标语义，施工时由各 Product Plugin 在自己的 Skill/Flow 内持有，不建立中央 Prompt Owner：

> 你现在不是表单审核员，也不是为了给当前系统找几个措辞问题。请把本次已完成工单当作一个真实生产样本，结合冻结资料包、实际结果、可公开执行证据，以及指定 commit 的 AGENT 与 Website 云仓源代码，自主重建它从 Website 需求、材料形成、任务签发、Product Skill、Prompt、GPT/Browser 执行、结果合同、Website consumer、业务入库到用户终点的真实链路。
>
> 读取仓库时必须先完成 authority gate，再读取和评价实现。先按项目固定权威顺序读取 AGENTS、法案系统建设说明书、基础法案、功能法案、适用 lawIds 及依赖、Blueprint、spec/跨仓合同、Owner Manifest 和唯一 registry 投影；只有明确当前义务、禁止、Owner 和 handoff 后才允许读取代码、测试、证据与历史。代码只能被上位规范评价，不能反向解释、降低或改写法案；下级冲突一律报告为 drift，authority 无法确定则停止相关代码结论。
>
> 在填写任何评分之前，先自由分析：这套链路真正想解决什么；每个环节为什么存在；相邻 handoff 是否把 consumer 真正需要的语义无歧义地交付；资料是否帮助了模型还是制造了噪声；Prompt 是否清楚、自然、完整并与资料和输出合同一致；Product Skill、Flow、Prompt、合同和 consumer 是否互相支持；是否存在隐藏假设、矛盾、重复 Owner、第二真相、无 consumer 的输出、过度设计、历史兼容残留、错误恢复、证据冒充完成或可删除但仍保留的结构。
>
> 不要受下方评分维度限制。优先报告你意外发现、原问题没有问到、但可能真正影响正确性、连贯性、稳定性、效率或可理解性的事项。寻找第一直接断裂和最高杠杆改进点；不要把同一根因拆成多条，也不要为达到数量而制造 finding。若系统已经足够好，应明确说明你实际追踪了哪些链路、看到了哪些支持证据，以及为什么继续修改只会产生边际收益。
>
> 对每个结论区分事实、推断和未知。源码结论绑定精确 repo、commit、path 与 symbol/line；运行结论绑定获准 evidence ref。无法看到精确源码、材料或证据时必须写入 unknowns，不得补猜。你可以给出建议核查方向，但不得改写原结果、输出修复代码、替 Website 作业务裁决或把自己的分数称为质量 PASS。
>
> 完成上述开放分析后，再按固定评分定义给分。不要猜测评分阈值；阈值不属于你的任务。

主问题开头必须再用自然语言明确一次意图：本轮不是重新回答原业务问题，也不是只审核原结果文本，而是把这张已完成工单作为真实样本，研究“资料包、Product Skill、Prompt、执行链、结果合同和 Website consumer 怎样共同影响系统表现”。GPT 在 `independent_analysis.review_intent` 中用自己的话说明它理解的复盘目的、当前 Product 的特有风险以及本轮明确不做什么。若它只是重做业务答案、逐格评分、泛化代码审查或提出无 subject 证据的改造，Codex 裁决为 `REVIEW_INTENT_MISUNDERSTOOD`，该产品当前结果进入全检，不能进入高分归档。

权重合计 100。安全、隐私、权限、身份错配、未知外部 effect、业务 admission 与第二 Owner 不进入可被高分抵消的普通权重，而属于硬门。

### 7.6 0–5 评分锚点

| 分数 | 定义 |
| ---: | --- |
| 5 | 已追踪关键路径，证据支持当前设计；没有会改善正确性、稳定性、效率或理解成本的具体改动。 |
| 4 | 存在明确但轻微的摩擦；预计不会改变结果、引起返工或造成实际误解。 |
| 3 | 存在局部且有证据的缺口；可能导致重复阅读、歧义、漏项、低效或不稳定结果。 |
| 2 | 存在重大缺口或冲突；很可能导致错误、不完整、拒收、重复执行或恢复困难。 |
| 1 | 核心输入、指令或链路大面积不可用，成功主要依赖猜测或偶然。 |
| 0 | 已证实该维度的核心合同缺失或完全失败；不是“没看到”。未取得证据必须使用 `not_observable`。 |

Codex 从 Website 导出的原始 scorecard 唯一重算：

```text
weighted_score = round(sum(weight * score / 5))
```

任一维度 `not_observable` 时不计算可用于停止门的总分，只在当日 `Codex核验结论.md` 标记 `score_eligible=false` 与已观察 partial score；不得把缺证据当零分或高分。

### 7.7 高分停止门与硬门

GPT 不知道以下阈值。Website 不持久化第二套 score facts；Codex 从原始 result 确定性计算并在同一份当日核验结论中分流：

#### `ARCHIVE_ONLY`

必须同时满足：

- `score_eligible=true`；
- `weighted_score >= 92`；
- 十一项单项均 `>=4`；
- `authority_trace` satisfied 且两仓 `source_status=exact`；
- `critical` finding 为零；
- `material` finding 为零；
- 没有硬门 code；
- 当前日与前六日不存在同一 `category + target_type + target_ref` 在三个独立 subject job 重复出现。

结果：保存原始复盘和停止理由，不启动源码深查，不更新迭代方案。轻微 finding 只参加七日趋势，避免边际改造。

#### `VERIFY`

满足任一：

- `weighted_score < 92`；
- 任一单项 `<4`；
- `score_eligible=false`；
- 有 `material|critical` finding 或任一硬门；
- 同一轻微 finding 模式七日内出现在至少三个独立 subject job。

结果：Codex 只读核验，不自动形成代码工单。只有核验为 `CONFIRMED_CURRENT_GAP` 才进入闭环方案。

`VERIFY` 内按“硬门优先、其余 weighted score 从低到高”处理；这只是当次读取顺序，不保存 `PRIORITY_VERIFY` 第三状态。

#### 硬门 code

- `SOURCE_BINDING_NOT_EXACT`
- `AUTHORITY_GATE_FAILED`
- `REVIEW_INTENT_MISUNDERSTOOD`
- `SUBJECT_IDENTITY_MISMATCH`
- `REQUIRED_MATERIAL_MISSING_OR_UNREADABLE`
- `OUTPUT_CONTRACT_UNSATISFIABLE`
- `SAFETY_OR_PRIVACY_BOUNDARY_CONFLICT`
- `EVIDENCE_IDENTITY_INVALID`
- `UNKNOWN_PROVIDER_EFFECT_REPLAY_RISK`
- `BUSINESS_ADMISSION_FALSE_COMPLETION`
- `SECOND_OWNER_OR_SECOND_TRUTH_DETECTED`

### 7.8 阈值校准

`92` 在生产启用前只是冻结候选值。校准不能用“全系统三十张、覆盖六种 route”的混合样本；那会让高流量产品吞掉低流量产品。每个 Product Plugin 的每个 reviewable primary action 都建立独立校准分层，首批二十张真实、已 Website-admitted 的工单全部进入 Codex 全检。`localization-production` 的 report 与 article 是两个独立分层；`localization_static_catalog` 当前没有 review route，不混入其中。

只有某一个产品分层同时满足以下条件，才只为该分层启用 `ARCHIVE_ONLY` 和第 7.10 节抽检率；其它产品保持自己的当前模式：

- 二十张样本中硬门 false negative 为零；
- 被 GPT 评为 `>=92` 的样本中，没有被 Codex 证实的 material/critical GAP；
- scorecard 十一项无缺项、乱序、重复或证据空洞；
- 同一材料与 source binding 的重复评估不存在会跨越 `ARCHIVE_ONLY/VERIFY` 的无解释大幅漂移；
- Website、AGENT 的真实 Provider proof 和 Website durable readback 通过各自现役 RELEASE evidence route。

该分层校准失败时只对该产品继续全检，不连带放开或封锁其它产品；只修改该 Product Plugin 自己的复盘问题或共同唯一 rubric/contract 中确有共享根因的部分，不并行维护旧阈值或第二评分器。

### 7.10 按产品独立的全检与百分比抽检

#### 定义

- **GPT 全量复盘**：第 5.2 节分母内每张工单都执行一次 `quality_reflection`；这是数据采集层，不等于 Codex 已验证；
- **Codex 全检**：某产品分层当日全部 GPT 复盘逐 job 核对双仓 anchor、subject、材料、finding、分数和 hard gate；
- **Codex 抽检**：只对已经满足 `ARCHIVE_ONLY` 候选条件的高分结果按下表抽取；所有 `VERIFY`、缺失、失败和 hard gate 行仍逐 job 全检，不计入可跳过池。

#### 稳态抽检率

| Product Plugin / primary action | 高分候选抽检率 | 当日非零分母最低抽数 | 原因 |
| --- | ---: | ---: | --- |
| `bazi-chart-interpretation / produce` | 20% | 1 | 全盘覆盖面广，但身份与候选已有强合同 |
| `bazi-ai-full-analysis / produce` | 30% | 1 | 问题、父报告、时间和现实限制组合复杂 |
| `bazi-report-followup / followup` | 25% | 1 | 父子绑定和 delta 边界易漂移 |
| `qimen-professional-answer / produce` | 30% | 1 | 盘局、候选、规则和时序耦合较强 |
| `qimen-report-followup / followup` | 25% | 1 | 需持续防止重排局和父结论覆盖 |
| `hehun-ai-analysis / produce` | 40% | 1 | 双人身份、隐私与比较方法风险高 |
| `hehun-report-followup / followup` | 35% | 1 | 双人案卷、授权和关系变化风险高 |
| `naming-bazi-analysis-and-naming / produce` | 35% | 1 | Requirement 与 Unicode 字符一致性要求高 |
| `naming-from-existing-bazi-report / produce` | 30% | 1 | source relation 和禁止重排盘必须持续验证 |
| `public-knowledge-article-pipeline / produce_article` | 40% | 1 | 公开发布、引用真实性和独立性外部影响高 |
| `localization-production / report_translation` | 30% | 1 | 个体报告语义、术语和风险强度不得漂移 |
| `localization-production / article_translation` | 35% | 1 | 公开主张、引用和 locale 表达同时受约束 |
| `payment-screenshot-observation / observe` | 100% | 全部 | 涉及付款证据、隐私和越权裁决，稳定期仍不降级 |

对每个分层令 `N` 为当日 `ARCHIVE_ONLY` 候选数、`r` 为该行比例；`N=0` 时抽零，`N>0` 时 `K=min(N,max(1,ceil(N*r)))`。Codex 按 `sha256(export_snapshot_hash + product_id + action_id + subject_job_id)` 升序取前 `K`，只把公式、`N/K` 和选中 job 写入当日唯一《Codex核验结论.md》的对应产品章节；完整排名可从同一原始 export 复算，不在报告复制，不人工挑“看起来可疑”的样本，也不新增抽检清单文件。

#### 产品级全检触发与退出

以下任一事实只把命中的 `Product Plugin + primary action` 切到 `PRODUCT_FULL_INSPECTION`，禁止默认一锅端其它产品：

- 首次校准尚未完成；
- 抽中的高分结果被 Codex 证实存在 GPT 漏报的 material/critical GAP 或 hard gate；
- Product Skill、Prompt 构造、材料合同、result contract、Website consumer 或相关 active authority 的 commit/hash 改变；
- 七日内同一 minor pattern 命中三个独立 subject，或评分出现无法由材料解释的跨档漂移；
- 云仓权限、source binding、导出覆盖或本产品 identity 分母失真。

该产品至少连续全检二十张真实工单且跨越七个自然日，期间 hard-gate false negative 为零、`>=92` 中无 confirmed material/critical GAP、抽检身份和 source anchors 全部闭合，才恢复自己的稳态比例。若变化位于多个产品共同消费的真实代码/合同，先列出精确 affected product/action；每个受影响分层分别进入全检、分别满足退出条件，仍不得用一个产品的结果替另一个产品放行。

## 8. Website 合同、持久化与调度

### 8.1 复用现有表

继续使用：

- `ai_quality_reflection_plans`；
- `ai_production_jobs` / `ai_production_job_runtime`；
- `ai_production_review_challenges`；
- `ai_production_review_findings`；
- 现役 result object store 与 business review receipt 字段。

v2 原始 JSON 继续进入现役 result object store，plan/challenge/finding 只保存现役已经需要的 result hash、issues 和 receipt；不得为 score、eligibility、hard gate、source binding 或 authority trace 新增列、表或第二 ledger。唯一允许的 schema 变更是第 8.2 节删除旧 scheduled-lineage 唯一索引；若现役 result object/export 无法读回 v2 原始 JSON，则本方案保持阻断，不以新分析表绕过。

### 8.2 每张工单恰好一个 plan

- idempotency key 固定为 `subject_job_id + reflection_contract_version`；
- 删除“新 lineage completed job 跳过旧 job”的查询；
- 删除将同 lineage scheduled plan 更新为 `superseded` 的写入；
- 删除 `ai_quality_reflection_one_scheduled_lineage_idx`；
- 保留 subject job 唯一约束；
- existing `superseded` 历史行不自动重放、不改状态；只作为旧事实保留且不进入 cutover 后正常分母。不得为了历史补齐新建迁移状态或触发 Provider effect。

### 8.3 非阻塞与单队列

- primary admission transaction 不调用 GPT、不等待 plan materialization；
- admission commit 后由现役 Website 长运行 background owner 执行 ensure/sweep；
- crash window 由 `ensureMissingAiQualityReflectionPlans` 按 subject job 幂等补齐；
- 仍使用同一 `ai_production_jobs`、同一 V6 claim、同一 Browser FIFO/lane；
- `selectV6ClaimableJobs` 的 new-job 选择在同一 SQL 中按 `quality_reflection` 最后排序，primary/followup 始终优先；recoverable accepted attempt 继续按现役规则优先收敛，不因任务类别丢弃已发生 effect；
- reflection 失败、超时、结果未知或 recovery_pending 都不得回写 primary 状态、撤销 admission 或阻塞后续 primary job。

### 8.4 唯一导出

原位升级现有 `/api/commercial/platform/ai-acceptance/reflections/export`，不新增第二 endpoint。JSON 导出按目标自然日的 primary `business_consumed_at` 建立分母，并 LEFT JOIN plan、reflection job、challenge、findings、原始 result ref/hash 与 receipt。

每个 primary job 恰好一行，至少包括：

- subject identity/result/admission facts；
- plan identity/status/due time；
- reflection job/result/receipt identity；
- result object store 读回并经 `result_payload_hash` 校验的完整 `website-agent-quality-reflection-output.v2`，不把 scorecard、authority trace、analysis、issues 或 unknowns 再扁平复制为第二字段集；
- 现役 finding identity/status，供 Codex 与原始 v2 finding 对等核查；
- `missing_projection` 原因；
- export window、generated_at、row_count、first/last cursor 与 snapshot hash。

`no_issue` 必须形成行；没有 plan 也必须形成 `missing_projection` 行。不提供 CSV、第二 schema 或第二导出。

## 12. 跨仓施工与部署顺序

1. 等当前双仓 dirty 施工面归属明确并形成可分离的 clean candidate。
2. 精确解冻并在同一方案内修订 Website active law、Blueprint 与 canonical provider contract；同步 AGENT dependency/Blueprint，不运行旧新双版本。
3. Website 停止创建/物化新的 quality_reflection；等待已有 review jobs terminal，DISPATCHED/CONFIRMED effect 必须按原合同完成或保持恢复，不能删除或重放。
4. 关闭 V6 新 claim admission并 drain live leases；冻结 cutover 时两个仓的 exact commit/hash。
5. 先部署 Website v2 provider/consumer 与 schema，再部署 AGENT v2 dependency/Product routes；合同 hash 不一致期间 V6 保持关闭。
6. 双仓各自运行唯一 `quality:check CHANGE`；形成各自 clean commit 后运行 READY。
7. 重新建立 AGENT session，使 current control contract/route hash 精确一致；开放 V6。
8. 先用一张已授权 review canary 证明 Provider output -> Website score/readback；再开放 plan materialization。
9. 各 product/action 分层完成自己的二十张校准后，只为该分层启用 archive-only 和稳态抽检；未达标分层继续全检。
10. 各仓按 active law 运行 RELEASE dynamic proof。任何一仓 RELEASE 不替代另一仓，也不替代 Website 实际 reflection durable readback。

## 13. 分层验收

### 13.1 Static/Contract

- route count 与 Product ownership 不漂移；
- quality_reflection v2 精确 schema、十一维度和权重单一来源；Codex Skill 是唯一 score recompute consumer，Website 中无 score facts；
- authority trace schema、hard gates 和第 7.2.D 节固定顺序只有一份语义来源；registry 在任何判断中只作 projection，不得排到 active law 之前；
- 十二个 Product Plugin 的复盘问题分别存在于本 Product Owner 内；localization report/article 必须分层；问题是否真正不同由第13.3节真实 GPT 正反样本验证，不新增无法可靠判断语义的静态 inspector；
- accuracy_challenge 合同不被无关扩张；
- v1 quality-reflection parser/fixture/branch 物理为零；
- 中央 Runtime 不持有 Product Prompt、专业问题或手写 Product 路由表；
- 系统中无第二 queue/store/ledger/verdict。

### 13.2 Integration/State

- 同 lineage 两张 primary -> 两个 plan；
- duplicate ensure -> 一个 plan；
- no finding -> completed plan + export row；
- material/critical finding -> 现役 pending triage finding；分数只进入当日 Codex 核验结论；
- missing plan -> export `missing_projection`；
- reflection failure -> primary completed 不变；
- primary 与 reflection 同时 eligible -> primary 先 grant；
- confirmed reflection effect 恢复 -> submit 增量零。
- 每产品当日 `N/K`、最低一张、稳定 hash 排名和选中 job 可从同一 export 精确复算；
- 一个产品触发 full inspection 时其它产品模式不变；共享代码变化只影响精确列出的 product/action。

### 13.3 Real GPT/Browser

- GPT 真实读取两仓指定 commit，并在唯一 authority trace 内返回 exact source binding；
- 云仓连接预检能在每仓打开 Codex 临时选定的一个随机路径，并由 exact commit 内容事实证明不是默认分支猜测；
- GPT 在打开实现文件前先给出双仓适用 lawIds、依赖闭包、Owner、Blueprint/spec/Manifest 和 registry projection 核对；
- 代码与 active law 故意构造冲突时，GPT 报 `LOWER_LEVEL_DRIFT`，不使用代码、测试、generated registry 或历史材料反向降低法案；适用 authority 缺失时停止代码结论；
- GPT 先产生维度外开放观察，再生成完整 scorecard；
- 十二 Product Plugin 分别证明 GPT 理解本产品复盘意图；至少包含一个“泛化复盘问题无法发现、产品专属问题能够发现”的正例和一个不应制造 finding 的反例；
- 允许真实 `no_issue`，不强制 finding；
- Prompt 中不存在 92 阈值；
- exact review task 的 Browser WAL、observed response artifact、result receipt 和 Website review receipt 全部同 identity 可读回。

### 13.4 Website durable readback

至少两张同 lineage primary、一个 `no_issue`、一个 `issues`、一个 reflection failure/recovery 样本证明：

- primary admission 不受复盘影响；
- plan、job、result hash、findings、receipt、export row 对等；
- Website canonical snapshot hash 校验通过；`/系统分析/<日期>/原始复盘导出.json` 为首次成功 response exact bytes，其独立文件 SHA-256 在同日核验结论中可读回且重跑不覆盖；
- `/系统分析/<日期>/Codex核验结论.md` 的每产品分数、分母、比例、排名和选中 job 可从原始 export 复算，十三个分层不互相平均；
- 每个被核验 job 的 authority trace 可以从双仓 exact commit 重放，且结论按 `authority -> expected structure -> implementation fact -> GAP -> consequence` 表达；
- Codex 核验分类引用的 commit/path/anchor 可从当前云仓读取。

### 13.5 原生质量入口

```text
AGENT:   npm run quality:check -- CHANGE
Website: pnpm quality:check -- CHANGE

AGENT:   npm run quality:check -- READY
Website: pnpm quality:check -- READY

AGENT:   npm run quality:check -- RELEASE
Website: pnpm quality:check -- RELEASE
```

只运行各仓唯一原生 verdict。评分、每日报告、Skill 自检、单测或真实 GPT 样本都不得自行发布 PASS。

| --- | --- | --- | --- |

## 15. 停止、恢复与执行准入

### 15.1 必须停止

- 用户未明确授权 frozen active law/Blueprint/contract 修改；
- 双仓相关 dirty overlay 无法归属或安全分离；
- cloud requested commit 无法精确读取；
- 生产 GPT 身份未通过双仓 exact-commit 云仓访问预检，或权限/连接变化后未重新预检；
- GPT 未完成适用法案依赖闭包、Owner 或跨仓合同的 authority gate，或 authority trace 顺序/内容无法由 exact commit 复核；
- GPT 使用实现代码、generated registry、测试、证据、历史报告或讨论材料覆盖、降低或重写上位 authority；
- review job 已有 DISPATCHED/CONFIRMED 未收束 effect；
- Website/AGENT route contract hash 不一致；
- primary material、subject result 或 admission identity 不闭合；
- 每日 export hash/分母不闭合；
- 任一产品的抽检 N/K、hash 排名、全检触发或退出条件不可复算；
- 新 Skill 或方案目标路径存在无法区分的用户修改。

### 15.2 恢复

- Website plan/job 恢复只沿现役 attempt、lease/fence、result consumer；
- AGENT Provider effect 恢复只沿现役 Browser WAL 和 confirmed readback，禁止第二 submit；
- 本地日导出失败只重新读取同一 Website export identity，不触发 GPT 重跑；
- Codex 核验失败保留原始导出并写失败原因，不产生修复方案；
- rollback 不删除已持久化 plan、result、finding、receipt 或用户原始 primary 结果。

### 15.3 可施工条件

本方案只有在以下事实同时成立后，状态才可由“设计阻断”改为“可施工”：

1. 用户明确批准命中 frozen 条款的 active law、Blueprint 和跨仓合同原位替换；
2. 双仓相关施工面 clean，或所有现有修改归属明确且能形成同一授权 candidate；
3. 施工 Codex 完成第3.3节重绑定；
4. v2合同、评分分母、阈值校准、source binding、非阻塞 claim 和日导出没有未决 Owner/consumer；
5. 删除反事实没有出现可进一步删除且不损害当前闭环的结构；
6. 多仓 drain、cutover、回退和同一身份 readback 可执行。

在此之前只允许继续讨论和精确更新本文件，不得创建最终 Skill 或进入生产施工。
