## 第一轮：从“找 DOM”回到“拥有哪一个状态变化”

- 日期：2026-09-02
- 参与者：项目负责人、GPT
- 主题：子能力是否需要一套统一、生产级、可长期稳定的建设模式
- 本轮性质：原则讨论和当前事实对齐，不施工、不修改现役法案或 Blueprint、不宣称生产验收通过

### 一、问题是怎么提出来的

项目负责人提出：当前子能力迭代次数过多，希望找到一套统一模式，使每个子能力在自己的范畴内达到接近“不失败”的稳定程度。

本轮输入观点把问题进一步收紧为：

> 子能力的规矩，不能围绕“怎么找到 DOM”来定，而必须围绕“这个子能力究竟拥有哪一个状态变化”来定。

这句话指出了过去容易反复的根源：如果先从 selector、弹窗、按钮和页面结构出发，规则会跟着每一次 DOM 变化被动生长；如果先冻结一个子能力唯一拥有的状态变化，DOM 只是在当前 Provider 页面上实现和证明这个状态变化的私有绑定。

### 二、本轮先形成的总判断

我们认可“统一模式”，但不把它理解为“所有子能力使用同一段代码、同一个通用执行器或同一套 selector”。统一的是合同骨架和证明方法，不是把不同状态变化重新揉成一个大 Flow。

一句话版本：

> 一个生产级子能力，是一个边界封闭、结果可证明、失败不乱动、恢复不重做的精确状态变化单元。

“几乎不失败”也需要重新定义。外部 Provider 页面不受本项目控制，因此不能承诺页面任意变化后仍然成功。真正可承诺的稳定性是：

- 已知且受支持的状态，确定完成；
- 瞬时 hydration、重绘或尚未 ready 的状态，在本 Child 获准的边界和期限内 fresh read，条件一成立就完成；
- 未知、缺失、多义或合同漂移的状态，不猜、不误点，以明确 typed reason 和零额外 mutation 失败关闭；
- 已经确认的不可逆 effect 永不因 DOM、Target、Document、进程或重试变化而再次执行；
- 一个 Child 漂移时，故障和修复收口在它自己的语义面，不把 Product Flow、其他 Child 或 Browser Authority 一起改坏。

换成最直白的话：稳定不是“永远不报错”，而是“该成的时候稳定成，不认识的时候绝不乱动，已经做过的绝不再做一遍”。

### 三、先把 Owner 分清楚

本轮按现役 authority 校正后的责任边界如下：

| 层 | 唯一拥有的东西 | 不能取得的东西 |
| --- | --- | --- |
| Product Plugin | 完整业务 Flow、Child 顺序、分支、重复、跳过、Prompt、模型策略、结果组装和下一步 | Target、Document、selector、WAL、物理 dispatch |
| GPT Child | 一个原子 Provider 页面或 continuation 意图、该意图的私有 DOM 合同、前置、至多一次动作请求、直接后置证明和 typed result | 业务下一步、跨 Child Flow、业务终态、Browser 私有身份 |
| Browser Authority | exact Target/Document、物理 dispatch 安全、mutation WAL、DOM 原子观察事实、mutation outcome | Product 顺序、业务恢复裁决、GPT 语义终态 |
| Forensics / continuation 等现役 Owner | 各自唯一的 evidence、artifact、continuation row/CAS 事实 | Product Flow、第二恢复状态机、第二业务结论 |
| Website | 业务任务、公开状态、领域接收、最终入库与业务回执 | GPT 页面点击顺序和 Browser 物理动作 |

因此，后面所说“Child 拥有一个状态变化”，准确含义是：Child 拥有这个原子语义变化的定义、资格和直接证明；物理点击、填充或文件挂载仍由 Browser Authority 安全执行，WAL 也仍由 Browser Owner 持有。不能因为引入 `WRITE_SET`，就把 Browser 的物理真相或持久化所有权搬进 Child。

### 四、统一生产模式的第一版骨架

本轮暂定把统一模式叫作“精确状态变化合同”。名称只是会议用语，不是要新增框架或公共抽象。

每个 Child 至少要能回答下面这些问题：

| 合同项 | 必须回答的问题 |
| --- | --- |
| `child_id + version` | 这是哪个稳定意图？DOM 合同何时算升版？ |
| `authority_surface` | 它操作的是 Provider 当前页面状态，还是现役 continuation row/CAS？对应事实由谁拥有？ |
| `semantic_goal` | 完成后，哪一个语义状态必须成立？ |
| `input_identity` | 哪些输入共同确定本次 exact call/effect？ |
| `READ_SET` | 为证明前置和后置，最少需要读取哪些语义事实？每个事实来自哪个 Owner？ |
| `WRITE_SET` | 本 Child 唯一获准改变哪个语义变量？纯观察 Child 必须为空。 |
| `precondition` | 什么状态下它才有资格观察或请求动作？ |
| `already_satisfied` | 目标本来已经成立时，如何以零 mutation 成功？如果该 Child 不允许此分支，也要明确写出。 |
| `allowed_transition` | 唯一允许的 `before -> after` 是什么？最多可以请求几次动作？ |
| `positive_postcondition` | 什么直接事实能唯一证明成功？ |
| `negative_postconditions` | 动作后有哪些互斥失败结果，如何完整收束而不再次动作？ |
| `forbidden_effects` | 哪些相邻状态即使看见异常也绝对不能顺手修改？ |
| `observation_policy` | 哪些情况可 fresh read，期限由谁提供，什么条件立即结束？ |
| `replay_policy` | 它是 observation-only、target-local-per-generation，还是 provider-effect-once？崩溃后先读什么权威事实？ |
| `typed_result + evidence` | 成功值、失败码、候选数量、前后 Document、mutation outcome、直接后置和 evidence 如何绑定本次 exact identity？ |
| `verification_matrix` | 正常、已满足、缺失、多义、stale、Document 漂移、dispatch 未决、后置失败和重启分别如何证明？ |

这套骨架同时适用于页面 Child 和 continuation Child，但两者不能被强行实现为同一种底层动作：页面 Child 依赖 Browser Authority；continuation Child 依赖现役唯一 row/store 的 exact CAS。统一的是“精确身份、前置、零或一次变化、直接后置、失败关闭、幂等读回”，不是统一成 DOM 工具。

### 五、`READ_SET / WRITE_SET` 的划法

这是下一轮最重要的工作，本轮先确定边界。

#### 1. 集合里写语义事实，不写 selector

例如 `attachment_control_state=OPEN` 是语义状态；`button#composer-plus-btn...` 是当前 DOM 私有绑定。前者进入状态合同，后者留在对应 DOM contract。

#### 2. 允许为了证明自己的目标跨面读取，禁止顺手跨面写入

`prepare_clean_gpt_chat` 为了证明“fresh chat”，可以读取 composer、prior turn、attachment、generating 等事实；但它只有在其余 fresh 条件都成立、唯一污染只是旧 draft 时，才可清空 draft。发现附件残留不能顺手删除附件，发现 generating 不能顺手停止生成。

所以“读可以交叉”不是任意读取。每个跨面读取都必须说明：它为什么是本 Child 前置或后置不可缺少的证明，以及由哪个唯一 Owner 提供。

#### 3. 一个 mutation Child 原则上只有一个语义写目标

如果一个 Child 需要同时改变两个彼此独立、由不同语义面拥有的状态变量，优先判断为边界过宽或接口设计错误，而不是扩大 `WRITE_SET`。

#### 4. 不把底层记账误写成 Child 的业务写集合

Browser WAL 的 PREPARED/DISPATCHED/CONFIRMED/REJECTED、Forensics evidence append、continuation store CAS 都各有自己的 Owner。Child 可以通过唯一 Facade 请求并取得这些事实，但不能声称自己拥有 Browser WAL 或第二份 evidence/store。

### 六、DOM 变化的处理原则

本轮接受三类处理，并拒绝第四类“猜”：

1. **瞬时状态**：hydration、重绘、ready 尚未形成。只在该 Child 已声明的期限和 fresh-read 规则内重查；不能复用 stale node，不能产生额外 mutation。
2. **已被真实观察并证明的并存 Variant**：由对应语义面的单一 DOM contract 显式记录，互斥、可识别、各自有真实 Chrome 证据。
3. **未知漂移**：候选为零、多义、结构或后置不再闭合时，返回精确 typed failure，零猜测、零替代动作。
4. **明确拒绝**：selector1 失败后试 selector2、再试文字、再试坐标、最后点第一个；也拒绝 AI 猜 DOM、自愈点击和跨 Child 补救。

外部环境中能冻结的变量应尽量成为明确前置，例如 Provider origin、UI locale、响应式尺寸和账号能力环境。这里暂不指定它们的 Owner，也不新建“环境服务”；下一轮要逐项判断应该由现役哪个 Owner 提供和验证，不能让 26 个 Child 各自兼容一遍。

### 七、“Observation 优先语义化，Mutation 继续 exact”的当前判断

这个方向值得继续验证，但本轮不把它定成已经可施工的结论。

当前代码事实是：Browser `find` 已允许 owner-defined exact selector 或 `role/name/testId/label` 属性型 locator 二选一；GPT 当前 `findCount()` 包装仍只暴露 selector。需要注意，现有 `BrowserSemanticLocator` 实际上会转换为受限属性 selector，它不是 AI locator，也不是自动理解 accessibility name 的万能语义引擎。

因此较稳妥的提议是：

- Observation 尽量使用已经在真实页面证明稳定的机器语义身份，减少对无意义 DOM 层级的依赖；
- Mutation 前仍由对应 Child 用当前 fresh Document 唯一重验 exact 候选、前置和 Browser permit；
- 不建立全局 selector 仓库，不把 selector 从局部 Owner 抽成公共 Flow；
- 不因为已有 locator 类型就立即改造全部 mutation API，先用一两个真实 Child 验证收益和失败边界。

### 八、当前工作树快照暴露出的真实差距

以下只是 2026-09-02 当前脏工作树的只读观察，不是质量 verdict，也不代表用户已有修改错误：

1. 好的基础已经存在：GPT DOM 事实按 `attachment.contract.ts`、`execution-profile.contract.ts`、`model-selection-v2.contract.ts` 等局部文件归属；模型合同也会复用 execution-profile 的同源事实，没有必要重建全局 selector 系统。
2. 现有 `ChildCapabilityContract` 已有 Target kind、Document transition、precondition、bounded observation/at-most-one mutation、postcondition、evidence 和 replay policy，但 `contractFor()` 大量使用统一的通用文字，尚未逐 Child 机械表达 `authority_surface / READ_SET / WRITE_SET / forbidden_effects / 完备正负后置`。
3. Browser `find` 已支持 locator 或 selector 二选一，GPT `findCount()` 当前只接受 selector，说明“Observation 语义化”有可复用基础，但尚未在 GPT Child 形成统一、经实证的用法。
4. 当前现役 GPT Blueprint 的公开分母写为 26 个 Child；当前 `src/capabilities/gpt/contract.ts` 快照列出的数组分母为 23 个，未列入 Blueprint 中的 reserve、complete、fork 三项。由于相关法案、Blueprint 和源码都处在用户已有修改的脏工作树中，本轮只记录“分母尚未闭合”，不据此下实现缺陷结论。下一轮制作逐 Child 状态表之前，必须先绑定同一最终候选。

### 九、一个 Child 的最低验证矩阵

一个 Child 不能只证明 happy path。最低应覆盖：

| 场景 | 预期 |
| --- | --- |
| 目标已成立 | 明确允许时零 mutation 成功；不允许时明确失败 |
| 唯一合法前置成立 | mutation Child 至多一次动作，直接后置通过 |
| 候选为零 | 零 mutation，typed missing/drift |
| 候选多于一个 | 零 mutation，typed ambiguous |
| node stale / 瞬时未 ready | 丢弃旧 node，按本 Child 规则 fresh read；未获准时直接失败 |
| Target/Document 不成立 | 保留原生 typed cause，不伪装成普通节点缺失 |
| dispatch 后正向后置不成立 | 不换候选、不做第二次动作，按冻结负向判据收束 |
| dispatch 结果未决 | 先读 Browser WAL 和当前页面后置，禁止盲重放 |
| 已 CONFIRMED 后进程或页面变化 | 保留原 effect，同一恢复只读回证，重复 mutation 为零 |
| 相邻状态异常 | `forbidden_effects` 对应 mutation 增量全部为零 |

验证至少分四层：确定性状态表、故障注入、真实 Chrome 当前 DOM、不可逆 effect 的重启/恢复。Child 的四层通过只证明这个原子能力，不等于 Product 已完成，更不等于 Website 已入库、READY、RELEASE 或全系统生产成功。

### 十、如何衡量“稳定”，本轮先定指标含义、不拍数字

后续不能再只用“测试过了几次”判断稳定。建议至少记录：

- 受支持状态下的确定完成率；
- 未知状态下的零误操作率；
- 不可逆 effect 的重复执行次数；
- 缺失、多义、stale、Target/Document 等失败原因是否精确分类；
- 一个 DOM 漂移是否只影响对应语义面；
- 修复一个 Child 时需要改动多少其他 Child、Product Flow 或公共层；
- 真实生产中各失败码的分母、频率和首次出现时间。

具体阈值必须等有真实运行分母后再定。当前先坚持两条硬线：错误 DOM 下误 mutation 必须为零；已经确认的不可逆 effect 重复执行必须为零。

### 十一、本轮已形成的共识

1. 子能力统一规则围绕“拥有哪一个精确状态变化”，不围绕“怎样找 DOM”。
2. 统一的是合同骨架和证明纪律，不新建通用 Flow、执行器、registry 或第二治理系统。
3. Product 继续唯一拥有完整 Flow；Child 不调用 Child，不决定下一步。
4. `READ_SET` 可以包含证明本 Child 目标所必需的相邻事实；`WRITE_SET` 必须收口到唯一语义变化，纯观察 Child 为空。
5. selector 和 DOM Variant 留在对应语义面的单一私有合同；未知 DOM 失败关闭，禁止猜测 fallback。
6. mutation 必须遵守“唯一证明 -> 至多一次 dispatch -> 直接后置证明”；已确认 effect 永不重做。
7. 生产级稳定包含安全失败、故障隔离、幂等恢复和局部可维修性，不等于永不出现外部漂移。
8. 当前最值得做的不是再发明子能力系统，而是先把现有原子 Child 的状态所有权和验证矩阵逐项补齐。

### 十二、本轮明确否决的方向

- 新建《子能力总法案》《DOM 变化法案》《Locator 法案》等多套平行 authority；
- 全局 `GPT_SELECTORS`、selector fallback 链或 AI 猜 DOM；
- Child 之间互相调用、互相修页面、顺手处理未知弹窗；
- 为“统一”建立通用 executor、workflow、planner、bus、DSL、中央恢复器或第二状态表；
- 把 Child 层通过冒充 Product 完成、Website 入库、READY 或 RELEASE；
- 还没有绑定最终候选和真实消费者，就直接给全部 Child 增加新字段、新抽象或新持久化。

### 十三、下一轮未决问题

下一轮先讨论并形成“26 个现役 Child 状态所有权表”，但在开始前必须解决分母闭合问题。表格至少需要这些列：

| 列 | 要解决的问题 |
| --- | --- |
| Child | 当前最终候选中真实存在的 child_id/version |
| State Surface | Provider page / continuation row |
| Semantic Goal | 唯一完成状态 |
| `READ_SET` | 语义事实、来源 Owner、读取必要性 |
| `WRITE_SET` | 唯一允许变化；观察 Child 为空 |
| Forbidden Effects | 明确不能碰的相邻状态 |
| Already Satisfied | 是否允许零 mutation 成功 |
| Transition | 唯一 `before -> after` 与最多动作数 |
| Postconditions | 完备的正向/负向直接判据 |
| Replay | observation-only / target-local / provider-effect-once / exact CAS |
| Drift Cases | missing / ambiguous / stale / Target / Document / variant |
| Evidence | 必须绑定的 proof 字段 |
| Verification | 确定性、故障注入、真实 Chrome、恢复证据 |

仍需继续讨论：

1. `READ_SET / WRITE_SET` 最终应该只进入现役 GPT Blueprint 和 Inspector，还是也需要进入 TypeScript contract；不能因为字段好看就立即加结构。
2. 26 个 Child 的状态变量应该按哪些语义面分组，哪些跨读是真正必要，哪些是边界泄漏。
3. Provider locale、窗口尺寸、账号能力和 Origin 分别由哪个现役 Owner 冻结与验证。
4. 属性型 locator 在真实 Chrome 中能替代哪些脆弱结构 selector；哪些名字看似语义，实际仍只是容易漂移的页面属性。
5. DOM Variant 何时允许共存，何时必须升版，旧 Variant 何时删除以及由什么真实证据验收。
6. 稳定性指标取得真实分母后，各项生产门槛应该是多少。

## 第二轮：目标不是边界清晰，而是 Child 本体足够强壮

- 日期：2026-09-02
- 参与者：项目负责人、GPT
- 触发原因：项目负责人指出第一轮把 Owner 边界讲得过重，没有直接回答“如何得到强壮的子能力”
- 本轮性质：纠偏并建立强壮 Child 的标准模型；继续讨论，不施工、不修改现役 authority

### 一、对第一轮方向的正式修正

第一轮的边界判断仍然成立，但优先级判断需要修正：

> 边界清晰只是强壮 Child 的护栏，不是强壮本身。

项目真正要解决的是：Child 在自己的语义范围内，能不能独立看懂局部状态，适应已经支持的页面变化，在瞬时变化中自己收敛，只执行一次正确动作，完成后自己证明，无法完成时留下足够精确的病历。

因此，第一轮提出“下一步先制作 26 个 Child 的 `READ_SET / WRITE_SET` 表”被本轮暂停。正确顺序改为：

1. 先把一个生产级强壮 Child 的标准运行模型定透；
2. 用不同类型的代表 Child 摧毁式验证这个模型没有偏科；
3. 模型成立后，再用它审视全部现役 Child。

本轮接受项目负责人提出的总原则：

> **内部极强，外部极窄。**

“外部极窄”由现役 Owner 边界保证；本轮主要回答“内部极强”怎样形成。

### 二、强壮 Child 不是一组功能，而是一个局部认知闭环

本轮把强壮 Child 定义为：

> 一个对自己负责的局部状态拥有完整认知、确定决策、有界收敛、一次动作、直接结算和精确诊断能力的小型生产级执行单元。

它的内部闭环是：

```text
取得同一时刻、同一 Document 的局部事实
  -> 识别当前属于哪一个已支持 DOM Variant
  -> 判定当前语义状态
  -> SATISFIED：零动作成功
  -> ACTIONABLE：动作前再次精确重验，至多 dispatch 一次
  -> TRANSIENT：在获准期限内丢弃旧事实并 fresh observe
  -> UNKNOWN / AMBIGUOUS：零动作失败并留下 drift evidence
  -> dispatch 以后只读结算正向或负向后置，永不回到第二次动作
```

这不是 Product Flow，也不是持久化状态机。它只存在于一个 Child 的一次 exact call 内，只围绕这个 Child 自己的语义目标收敛。

### 三、状态和 DOM Variant 必须分成两个维度

项目负责人提出的 `SATISFIED / ACTABLE / TRANSIENT / KNOWN_VARIANT / AMBIGUOUS / UNKNOWN_DRIFT` 抓住了核心，但 `KNOWN_VARIANT` 与其它项不是同一维度。强壮模型需要把“页面由哪套合同解释”和“当前该做什么”分开，否则容易把 DOM 版本误当成运行状态。

#### 维度 A：合同识别

| 识别结果 | 含义 |
| --- | --- |
| `SUPPORTED_VARIANT(vN)` | 当前同一快照完整满足一个已经真实 Chrome 验证的 Variant |
| `MULTIPLE_SUPPORTED` | 同时满足多个本应互斥的 Variant，合同多义 |
| `UNKNOWN_VARIANT` | 没有任何已支持 Variant 能完整解释当前事实 |

#### 维度 B：动作判定

| 判定结果 | 含义 |
| --- | --- |
| `SATISFIED` | 本 Child 的完整语义目标已经成立，且允许零 mutation 成功 |
| `ACTIONABLE` | 当前前置完整、唯一动作资格成立 |
| `TRANSIENT` | 有明确机器事实证明页面处于该 Child 允许等待的瞬时状态 |
| `TERMINAL_NEGATIVE` | 已知且完整的负向状态已经成立，本次不能成功 |

合同识别不是唯一 supported variant，或动作判定出现多个结果时，都不得动作。

dispatch 后进入单独的结算判定：

| 结算结果 | 含义 |
| --- | --- |
| `POSTCONDITION_SATISFIED` | 直接正向后置完整成立，成功 |
| `POSTCONDITION_PENDING` | 有明确瞬时事实，可在原 deadline 内继续只读观察 |
| `POSTCONDITION_REJECTED` | 冻结的已知负向后置成立，失败但结果确定 |
| `POSTCONDITION_DRIFT` | 正负后置都不能解释当前页面，失败并报告漂移 |

关键硬线：进入 dispatch 后，Child 的 mutation budget 立即归零。后续即使出现 `POSTCONDITION_DRIFT`，也只能读回和报病，不能换候选再点一次。

### 四、强壮性的第一根支柱：一致观察快照

多事实定位只有在这些事实来自同一时刻、同一 Target、同一 Document、同一 DOM 世代时才可信。

如果按顺序分别读取：

```text
popup = 1
entry = 1
expanded = 0
simple = 1
advanced = 0
```

而 React 恰好在这些读取之间重绘，就可能把动画前、动画中、动画后的事实拼成一套现实中从未同时存在过的“合法状态”。这叫撕裂观察。它会让证据越多，误判反而越隐蔽。

当前 `open_gpt_model_selector_v2` 的拓扑读取正是六次顺序 `findCount()`，所以它是验证强壮模型的好样板：不是说当前逻辑一定错误，而是当前接口尚未证明六个计数属于同一局部快照。

强壮 Child 的观察器必须满足以下一种证明方式：

- 在一次受控 Browser observation 中返回完整局部拓扑；或
- 每个事实都绑定同一可验证 DOM snapshot/document revision，任一变化就丢弃整组事实并重新观察。

不能只丢弃 stale 的那一个节点，然后保留同组其它旧事实继续拼装。

如果现役 Browser Facade 无法提供这种一致性，说明这里存在一个需要单独论证的 producer/consumer 接口 GAP；本轮只识别问题，不据此授权修改 Browser 接口。

### 五、强壮性的第二根支柱：多事实充分证明，不是 fallback 或打分

强壮定位不应是 `selector A OR selector B OR 文本 OR 第一个节点`，也不应是“六个特征中了四个，可信度 80%”。生产 mutation 不能由概率分数授权。

每个受支持 Variant 必须是一组完整布尔合同：

```text
Variant V1 := A AND B AND C AND unique(candidate)
Variant V2 := D AND E AND F AND unique(candidate)
```

并且 V1、V2 必须互斥。不能拿 V1 的 role、V2 的 testId、另一个节点的文本和第三个区域的位置拼成一个候选。

一个事实可以被定义为：

- `identity_fact`：缺失就不能证明对象身份；
- `state_fact`：决定 SATISFIED、ACTIONABLE 或 TRANSIENT；
- `corroborating_fact`：只增强诊断，不参与 mutation 许可。

“一个 DOM 属性改变不应该马上杀死 Child”不能成为无条件规则。准确说法应是：

> 不该把与语义身份无关、已证明不必要的脆弱结构属性列为 identity fact；但任何已经承担身份或动作许可的必需事实发生变化，都必须停止，直到新的充分证据组合被真实验证为受支持 Variant。

这样得到的是可解释的韧性，不是把合同放松到什么都像。

### 六、强壮性的第三根支柱：职责内有界收敛

“局部自愈”这个方向成立，但为了避免它演变成未知页面上的自动修理，本轮把它收紧为“职责内有界收敛”。

允许的收敛包括：

- hydration 尚未完成且有明确 readiness 信号；
- React 重绘导致 node stale，丢弃整份局部快照后 fresh observe；
- panel 动画或 ready/spinner 等已知瞬时状态；
- Provider wait Child 已获准的短 probe、动态 backoff、park/reacquire；
- 动作后正向后置尚在形成，继续只读结算。

不允许把以下情况自动叫作 `TRANSIENT`：

- 单纯候选为零，但没有任何已证明的 hydration/readiness 信号；
- 同时出现多个候选；
- 未知弹窗或未知页面结构；
- exact Target/Document 已失效；
- 已 dispatch 后为了“再试一次”回到 ACTIONABLE；
- 调用另一个 Child 帮自己恢复前置。

每个 `TRANSIENT` 都必须回答：由哪个机器事实证明、由谁提供 deadline、下一次 fresh observe 丢弃哪些旧事实、什么时候必须停止。没有这些答案，就不是自愈，只是拖延报错。

### 七、强壮性的第四根支柱：语义幂等不能一刀切

“先判断目标是否已经实现”是强壮性的核心，但不是所有 Child 都能靠当前 DOM 得出 `SATISFIED`。

不同 Child 的完整语义目标不同：

- `open_gpt_model_selector_v2` 的目标是 advanced panel 已打开；`ALREADY_OPEN` 可以零 mutation 成功。
- `select_exact_gpt_model_v2` 的现役完整目标不仅是目标 radio 已选中，还包括 profile 恢复到 collapsed entry + active simple panel。因此 advanced panel 中 `aria-checked=true` 并不等于整个 Child 已 SATISFIED；按当前现役合同仍需点击唯一精确 radio一次以完成收束。
- `submit_exact_gpt_turn_once` 是不可逆 Provider effect。不能仅凭页面“看起来已有 user turn”就自报 SATISFIED；零 mutation 恢复必须由 exact Browser WAL、Forensics confirmed receipt 和 task-owned locator 等现役权威事实闭合。
- observation-only Child 的 `WRITE_SET` 为空，它的强壮性体现为准确观察和有界收敛，不存在“再执行一次动作”的问题。

因此，每个 Child 必须单独定义 `satisfied_predicate` 以及它可以信任的 authority。不能为了让所有 Child 看起来幂等，给它们统一塞一个宽松的 DOM already-done 判断。

### 八、强壮性的第五根支柱：动作门与动作后结算彻底分开

mutation Child 内部应明确分成两段：

#### 动作前

1. 读取一致快照；
2. 识别唯一 supported Variant；
3. 判定唯一 ACTIONABLE；
4. 在 dispatch 临界点重新验证 exact candidate、Document 和前置；
5. Browser WAL 先行；
6. 至多一次物理 dispatch。

#### 动作后

1. mutation budget 固定为零；
2. 只读 fresh snapshot；
3. 在同一冻结的正向/负向后置集合内结算；
4. pending 只能继续只读，不能产生第二动作；
5. 正负后置都不闭合时报告 drift，不把“click 没抛异常”当成功。

这比“动作后自己验尸”再精确一步：Child 不是只看成功后置，还必须预先冻结可接受的负向后置，使 dispatch 后的所有允许结果都能被收束。否则一旦正向没出现，系统仍然不知道动作到底发生了什么。

### 九、强壮性的第六根支柱：可直接维修的病历

强壮 Child 的失败包必须让维护者不打开整条 Product Flow，也能知道它自己的哪一块合同变了。

建议的安全诊断投影至少包含：

```text
child_id / child_contract_version
exact_call_identity_hash
expected_semantic_goal
document_ref_hash
variant_evaluation = V1(no: fact_x_missing), V2(no: candidate_ambiguous)
classified_state
safe_fact_counts / safe_fact_codes
mutation_budget_before / mutation_outcome
positive_postcondition / negative_postcondition evaluation
innermost typed cause
evidence_ref / evidence_hash
```

它不应只返回 `CANDIDATE_COUNT_0`，也不能把 selector、原始 DOM、Prompt、Provider 正文、Target/Document 私有身份直接写进日志或持久 proof。若确实需要完整 DOM artifact，必须继续走现役 task-owned artifact/Forensics Owner 允许的路径，不能为 drift 新建第二 evidence store。

“容易修”不是多记日志，而是把预期合同和实际安全事实逐项对照，并让故障天然定位到单个 Child + 单个 Variant + 单个判据。

### 十、强壮性的第七根支柱：摧毁式验收必须验证状态模型

摧毁式验收不能只是随机删 DOM。每一个破坏都要对应预期分类，证明 Child 真的理解自己的状态空间。

#### 1. 身份破坏

- 删除一个必需 identity fact；
- 改变 role、testId、aria、label/name；
- 产生两个完整候选；
- 把不同 Variant 的部分事实混在一起；
- 改 wrapper、顺序或无关 class，验证不必要结构是否真的不会杀死 Child。

#### 2. 时序破坏

- hydration 延迟；
- 动画中间态；
- node stale；
- 一组事实读取中途发生 DOM generation 变化；
- postcondition 延迟形成。

#### 3. 动作破坏

- 已经 SATISFIED；
- ACTIONABLE 但 dispatch 前 candidate 漂移；
- dispatch 成功但正向后置缺失；
- 明确负向后置成立；
- dispatch 后进程中断；
- postcondition pending 到 deadline。

#### 4. 恢复破坏

- WAL PREPARED / DISPATCHED / CONFIRMED / REJECTED；
- 同 attempt 新 Document；
- 原 Target 丢失；
- 已确认 Provider effect 后重启；
- evidence 缺失、多义或 hash 漂移。

#### 5. 隔离破坏

- 相邻 panel、附件、draft、模型、conversation 状态异常；
- 验证本 Child 不顺手修改它们；
- 一个 Child 的 drift 不改变下一个 Child、Product Flow 或 Browser 全局状态。

验收结论必须逐项证明三件事：该继续工作的确实继续；该有界收敛的确实收敛；未知和多义状态的额外 mutation 为零。

### 十一、强壮 Child 的标准运行算法（讨论版）

```text
mutation_budget = Child contract 声明值（0 或 1）
deadline = Product 输入或 Child 现役合同明确拥有的期限

PRE-DISPATCH LOOP:
  snapshot = fresh coherent observation
  variant = recognize_supported_variant(snapshot)

  if variant is UNKNOWN or MULTIPLE:
    fail drift/ambiguous with mutation=0

  state = classify(snapshot, variant)

  if state is SATISFIED:
    return success with mutation=0

  if state is TRANSIENT and deadline remains:
    yield/backoff/park only as this Child is authorized
    discard the whole snapshot
    continue

  if state is TERMINAL_NEGATIVE:
    fail with mutation=0

  if state is ACTIONABLE:
    exact revalidate at dispatch boundary
    Browser WAL prepare
    dispatch once
    mutation_budget = 0
    break

POST-DISPATCH SETTLEMENT LOOP:
  snapshot = fresh coherent observation
  result = classify_frozen_postconditions(snapshot)

  if POSTCONDITION_SATISFIED:
    return success

  if POSTCONDITION_PENDING and deadline remains:
    discard snapshot and continue read-only

  if POSTCONDITION_REJECTED or POSTCONDITION_DRIFT or deadline reached:
    fail with exact mutation outcome and evidence

  never return to dispatch
```

这段算法表达的是每个 Child 必须具备的行为模型，不代表要新增一个共享 runtime executor。是否有任何底层代码值得复用，必须等代表 Child 实证后按真实消费者和 Owner 另行判断。

### 十二、我们究竟如何把强壮 Child 造出来

不是先修改 26 个 Child，也不是先给合同加十几个字段。建议按下面顺序得到它：

#### 第一步：选一个“局部动作型”样板

先用 `open_gpt_model_selector_v2`。它同时具备 SATISFIED、ACTIONABLE、动画/hydration、局部拓扑、一次点击和直接后置，适合把一致快照、Variant、分类器、一次动作和结算跑通。

#### 第二步：先写真实状态空间，不先写 selector

从真实 Chrome 收集 `ALREADY_OPEN`、`OPENABLE`、动画中间态、已知负向和未知漂移。为每个状态写完整事实组合、互斥关系和允许结果。

#### 第三步：建立 Child 私有的观察器与纯分类器

观察器只负责取得同一快照的安全事实；分类器是确定性的纯判定：相同 snapshot 必须永远得到相同 Variant、state 和 reason。分类器不点击、不等待、不读全局 Flow。

#### 第四步：接上一次动作与只读结算

只有分类器输出唯一 ACTIONABLE 才请求 Browser dispatch。dispatch 后彻底关闭动作门，只跑冻结的结算判据。

#### 第五步：先摧毁样板，再谈标准成立

让 wrapper、属性、节点数量、时序、Document、dispatch 和恢复逐项出故障。任何未知状态误点一次，模型都还没有成立。

#### 第六步：用三种不同原型防止模型偏科

一个 open Child 不能代表全部 26 个 Child。标准模型至少还要能解释：

- `reconcile_gpt_attachment_set`：纯观察、长 deadline、stale/no-layout、集合完整性；
- `submit_exact_gpt_turn_once`：不可逆 provider-effect-once、WAL、已确认后绝不重做；
- `advance_gpt_continuation_lane`：非 DOM 的 exact CAS、commit-before-return 幂等读回。

这不是先改四个 Child，而是用四类现役真实消费者检验同一个标准模型没有被“打开一个面板”的例子带偏。

#### 第七步：模型经实证后，再决定怎样进入现役系统

届时再判断哪些只是 Blueprint 的标准章节，哪些必须进入 Child TypeScript contract，哪些需要 Inspector 机械检查，哪些已有 Browser primitive 可以直接复用。没有实证消费者的公共抽象、字段和接口一律不提前增加。

### 十三、本轮形成的新共识

1. 项目要的首先是 Child 本体强壮；Owner 边界只负责让这种强壮不越界。
2. 强壮 Child 的核心是局部认知闭环，而不是 selector 数量、重试次数或 fallback 数量。
3. 多事实必须来自一致快照；撕裂观察是当前强壮性模型必须正面解决的问题。
4. DOM Variant 和运行状态分属两个维度；每个 Variant 是完整、互斥、经真实验证的充分证据组合。
5. 局部自愈只允许有明确瞬时事实的有界收敛，不认识的页面不能靠等待或试错变成认识。
6. SATISFIED 必须按每个 Child 的完整语义目标和可信 authority 单独定义，不能一刀切。
7. dispatch 前是动作许可，dispatch 后是只读结算；两者之间是不可返回的单向门。
8. 强壮 Child 必须同时具备安全 drift 病历和摧毁式验收，确保未知状态零误操作、已确认 effect 零重复。
9. 下一步不做 26 项状态表，先把标准模型在代表性 Child 上推演和证伪。

### 十四、下一轮议题

下一轮只聚焦一个问题：

> 以 `open_gpt_model_selector_v2` 为样板，它的完整一致观察快照、受支持 Variant、状态分类表、瞬时条件、动作门、正负后置和 drift 病历究竟应该长什么样？

这一轮仍先做设计推演，不自动进入代码施工。样板模型经讨论闭合后，再决定是否以及如何产生实施工单。
