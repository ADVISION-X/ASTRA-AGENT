> 状态：可施工（第一版设计经法案二次核对后发现风险，已推翻重设计；本版为第二版，W0 现场核实已用当前真实故障完成，第一直接断裂已改判到更精确的位置）。

## 修订记录（第二版，覆盖第一版 W1/W2）

第一版把第一直接断裂归因于"`assertLive()` 只被动挂在 send 路径上 + 45 分钟容忍窗口过长"，提出的修复是新增一个独立 `setInterval` 主动轮询 `assertLive()`（候选 A）并缩短容忍常量（候选 B）。对 `.github/instructions/agent-rules/功能法案.md` 中 `LAW-LOCAL-BROWSER-SESSION-002-V6`（`appliesTo: src/lib/browser/**`）做第二遍逐条核对时，发现其 forbidden 列表包含以下裸短语条款：`不得发生：agent reconnect`、`不得发生：idle or diagnostic-triggered disconnect`、`不得发生：heartbeat authority minting`、`不得发生：45-second authority expiry`、`不得发生：second keepalive transport`。这些条款的措辞方式（短语式、非段落式）与本法其余条款一致，是对历史上已经出现并被否决过的具体坏设计的永久性禁止标记。候选 A（服务器侧新增一个独立周期定时器，专门用来判断连接是否该断)，在措辞上与"idle/diagnostic-triggered disconnect"和"second keepalive transport"高度贴近，且全仓检索确认 AGENT 服务器端当前一个 `setInterval` 都没有（唯一一处 `setInterval` 是扩展自己发心跳的 `extension-heartbeat.ts`），新增服务器侧定时器会是这个代码库里第一个这类结构，与法案条款要防的模式风险重合度太高，即使能辩称"检测标准复用现有 `assertLive()`、没有新开机制"，也不是能反向攻击站得住脚的最短方案。

## 1. 需求、业务终点与语义澄清

目标行为：AGENT 与其 Chrome 扩展之间用于下发浏览器指令的连接健康状态，必须被**主动、持续**地监控，一旦不健康就必须让服务器端权威状态（`BrowserAuthorityIssuer`）在有界时间内正确复位，从而让扩展侧已有的自动配对轮询（`PairingAutoBootstrap`，现役、每分钟一次）在下一轮自然拿到新配对密钥并重新连接——不新增第二套重连机制，只让现有的自愈路径真正被触发。

非目标：不重新设计配对/认证协议；不改动扩展的 Target 认领、DOM 观察、GPT Child 执行逻辑；不解决"浏览器环境本身卡住"（如 Chrome 崩溃、页面被 DevTools 占用）这类由现役 `BROWSER_DEVTOOLS_CONFLICT`/`BROWSER_TARGET_INVALID` 等既有错误码已经覆盖的场景。

## 4. 现役实现重建（第一直接断裂）

连接健康由三层组成，逐层核对如下：

1. **权威状态**：`BrowserAuthorityIssuer`（服务器端，纯内存）只有两态：`PRESENT`（持有一份签名的 `BrowserAuthorityCertificateV1`）/`ABSENT`。`commitAuthenticationProof()` 置为 PRESENT（唯一调用方 `transport-actor.ts::commitAuthentication`，由扩展完成配对握手后触发）；`revokeCurrent(reasonCode)` 置回 ABSENT。
2. **失活检测**：`BrowserAuthorityWebSocket.assertLive(now)`（`browser-authority-websocket.ts:136-142`）是**唯一**判断"连接是否还活着"的地方：`now - active.lastHeartbeatAt > BROWSER_MISSED_HEARTBEAT_TOLERANCE_MS` 则判定失活并调用 `revoke()`→`clearActive()`→`options.onRevoked()`，经 `browser-infrastructure-supervisor.ts` 接线后最终调用 `transport.disconnect()`→`issuer.revokeCurrent()`，correctly 把权威状态复位为 ABSENT。**这条闭环链路本身是完整、正确的**，问题不在这里。
3. **触发时机**：全仓搜索确认 `assertLive()` 只在三处被调用（`browser-authority-websocket.ts:164/214/239`），全部在**即将真正发送一条浏览器指令之前**（`send()`/`observe()`/等价方法的开头）。全仓搜索确认 `browser-infrastructure-supervisor.ts` 及其余任何文件都没有用 `setInterval`/`setTimeout` 之类的独立定时器**主动**调用它——它是纯粹**被动、按需**触发的。

4. **扩展侧的自愈触发路径**：`PairingAutoBootstrap`（扩展侧，现役）已经有三个独立触发源持续调用其 `attempt()`：`runtime.onStartup`、每次导航到 `127.0.0.1:4173/*`、以及 `chrome.alarms` 每 60 秒一次的固定轮询——三者叠加，正常情况下扩展最长 60 秒就会主动问一次服务器"我现在该不该重新配对"。`attempt()`→`run()` 内部先向 `GET /api/browser-authority/pairing` 取一次 `state.authority`；只有该值为 `"absent"` 时服务器才会随之下发一次性配对密钥，`run()` 才会调用 `actor.pair()` 真正建连——`state.authority === "present"` 时函数直接返回，不做任何事（`pairing-auto-bootstrap.ts:109`）。
5. **该 GET 端点的服务器实现**：`create-workbench-server.ts:82-89` 把这个端点直接接到 `workbench.readBrowserExtensionBootstrapState()` → `workbench.ts:34-37` → `BrowserInfrastructureSupervisor.readOperatorPairingState()`（`browser-infrastructure-supervisor.ts:230-235`）。该方法的实现是：`{ authority: this.issuer.current().kind === "PRESENT" ? "present" : "absent", pairingSecret: this.websocket.readOperatorPairingSecret() }`——**直接读取 `issuer` 的当前记忆值，从不调用 `this.websocket.assertLive()`**。

**第一直接断裂（第二版，替换第一版结论）**：第 2 层的失活检测（`assertLive`）本身完整正确，但它的三个既有调用点全部挂在"即将发送一条真实浏览器指令"这条路径上；而扩展侧唯一会去读取服务器权威判断、进而决定要不要重新配对的地方——`readOperatorPairingState()`——恰恰是这三个调用点之外的第四个、也是频率最高（≤60 秒一次）、最贴近用户红线（"AGENT 启动后必须自动连上"）的决策点，却完全没有接上 `assertLive()`。后果是：一旦连接进入"服务器仍相信 PRESENT，但底层连接已经失活"的状态（无论具体成因是心跳中断、扩展进程被系统回收、还是本次故障里发现的另一个问题——见下），只要没有任何 job 恰好去发一条真实指令，这个脱节就永远不会被服务器自己发现；而扩展每 60 秒一次的轮询,因为读到的还是服务器口中的 stale "present"，也永远不会重新申请配对密钥。这不需要新增任何触发源——扩展侧的轮询已经存在且足够频繁，缺的只是服务器在回答这个已有问题时,没有先用已有的判断方法核实一下自己的记忆是否还成立。

**本次真实故障的现场核实（W0，已用当前真实故障完成，非人工模拟）**：施工前用当前仍在运行的 AGENT 进程（HEAD 未变，故障未处理）直接核实：
- `curl http://127.0.0.1:4173/api/health` 与 `/api/browser-authority/pairing` 均报告 `authority: "present"`、`authenticated: true`；`lsof -i :4173` 确认 Chrome 与 AGENT 之间确有一条 `ESTABLISHED` 的真实 TCP 连接——即当前这一刻,连接本身是活的,权威判断也没有脱节。
- 但运行日志（`.grasseye-local/runtime-logs/agent/<当前 runId>-0001.jsonl`）显示：进程启动约 40 秒后（`23:16:27.876Z`）曾发生一次 `browser.infrastructure` span，`typedIdentity.producerId:"authority-revoked"`，以 `outcome:"failed" failure.code:"BROWSER_EXTENSION_CHANNEL_UNAVAILABLE"` 结束；约 86 秒后（`23:17:53-54Z`）3 个生产 job 的 `gpt.child`（`capabilityCallId:"fresh-chat:prepare_clean_gpt_chat"`）先后 `span.started`；此后到本次核实时刻（约 30 分钟后）**没有任何一个 `gpt.child`/`browser.infrastructure` span 产生任何后续事件**（既未成功也未失败），3 个 job 只靠 `job.lease-renew` 每约 15 秒续租一次维持"存活"，`cloud.claim` 因 `CAPACITY_ZERO` 也无法再接新 job。

**核实结论**：连接层面确实存在过一次"权威判断与真实连接脱节后无法自愈"的窗口（这正是第一直接断裂描述的缺口，第二版修复直接命中它），但连接后来显然已经恢复（当前 TCP 已建立、已认证）——说明本次事故实际上是两个独立问题叠加：(a) 连接自愈缺口本身（本方案修复目标）；(b) 3 个已经在旧连接/旧 authority epoch 下发出的 `prepare_clean_gpt_chat` 相关指令或 Target 认领请求，在连接经历了一次失活-恢复之后，永久卡在无人处理、无超时、无重试的状态，即使新连接已经建立也不会自动恢复。(b) 与"连接能否自愈"是不同责任面（前者是连接生命周期，后者是指令/Target 认领跨 authority epoch 的孤儿恢复），不落在用户本次给出的红线（"必须建立起连接"）范围内，本方案不处理，也不能假装顺带修好；已通过 `spawn_task` 另行登记，避免和当前方案的验收标准混在一起。

## 6. 故障与合同闭环

第一直接断裂：`readOperatorPairingState()`（服务器侧，`browser-infrastructure-supervisor.ts:230-235`）是扩展侧唯一的配对决策依据来源，但直接读取 `issuer.current().kind` 的记忆值，从未调用本模块已经拥有、已经在法律上站得住脚的 `assertLive()` 核实这个记忆是否还成立。

合同 handoff：`PairingAutoBootstrap.run()`（扩展侧，既有，每 ≤60 秒一次）→ `GET /api/browser-authority/pairing`（既有 HTTP handoff）→ `readOperatorPairingState()`（服务器侧）→ `issuer.current().kind`。这条 handoff 的契约本身没有问题（扩展如实读取、ABSENT 时正确重新配对）；缺口在服务器侧回答这个问题之前没有核实自己的记忆，不在 handoff 的字段/身份/协议本身。

## 7. 删除反事实

**候选 A'（第二版最终采用）：在 `readOperatorPairingState()` 内，仅当当前记忆为 PRESENT 时，追加一次 `this.websocket.assertLive()` 调用，吞掉其可能抛出的 `BROWSER_LIVENESS_EXPIRED`（该方法的返回值不需要使用，只需要它在内部已经会做的"过期则 revoke”副作用发生），再读取 `issuer.current().kind` 作为最终返回值。**
1. 当前需求必需？是——这是扩展侧唯一会去读取服务器判断、从而决定要不要重新配对的地方，不接上核实就永远可能读到 stale "present"。
2. 真实 GAP？见第 4/6 节：`assertLive()` 的三个既有调用点都不会在"扩展只是来问一句"时被触发。
3. 真实消费者？`PairingAutoBootstrap`（扩展侧，通过 HTTP 响应间接消费这次核实的结果）；`BrowserInfrastructureSupervisor` 自身是唯一有资格做这次核实的 Owner（已持有 `issuer`、`websocket` 的引用）。
4. 唯一 Owner？`browser-infrastructure-supervisor.ts`，不新增 Owner。
5. 不加的后果？维持现状：连接失活后，只要没有 job 恰好发真实指令，服务器会一直如实"记得"一个已经不成立的 PRESENT，扩展的高频轮询也无法发现，即本次故障的连接层面缺口。
6. 更短方案？不存在——`assertLive()` 已经是现成、正确、已被三处复用的判断方法，本修复不改它的判断逻辑，也不新增触发源，只是在第四个决策点接上同一个已有方法的第四次调用，是能想到的最小改动；比第一版的"新增定时器"更短，因为它连一个新的时间语义（周期）都不需要引入,复用扩展侧已经存在的轮询节奏。
7. 替代关系？不替代任何东西；不删除任何既有代码，只在一个方法体内新增两行(核实 + 吞异常)。
判定：**采用**。

**候选 B'（第一版候选 B，重新裁决为不采用）：缩短 `BROWSER_MISSED_HEARTBEAT_TOLERANCE_MS`。**
1. 当前需求必需？否——候选 A' 生效后，"多久能发现失活"由扩展侧既有轮询节奏（≤60 秒，外加 `runtime.onStartup`/tab-导航两个即时触发源）决定，而不再是容忍常量本身；只要容忍常量小于"两次轮询间隔的量级"，具体数值已经不影响红线是否满足。
2. 真实 GAP？没有——第一版认为"45 分钟本身就是缺口"是在假设检测只能被动触发的前提下成立的；候选 A' 已经解决了触发时机问题，常量取值变成了独立的、非本次红线必需的优化项。
3. 真实消费者？`assertLive()`；改动它不是不可以，但不是本次真实故障要求的。
4. 唯一 Owner？`browser-protocol.generated.ts`。
5. 不改的后果？无——保持现状完全不影响本方案红线的满足。
